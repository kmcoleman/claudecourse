# Module 0 Setup Kit — Design

**Status:** draft for review · 22 July 2026
**Parent:** [Meridian UAR Capstone Program](./2026-07-15-uar-capstone-design.md)
**Depends on:** [Meridian Data Generator](./2026-07-15-data-generator-design.md) (built & merged) — with one small prerequisite enhancement (see *Generator prerequisite*).
**Position:** second sub-project. The kit every learner clones and builds their capstone inside. It fixes the environment, the data, the MCP interface, and — most importantly — the frozen `run_review → findings.json` contract that the learner's eval, the UI, and the grading agent all bind to.

---

## Purpose

Give each learner a clone-and-go starting point so nobody loses capstone Week 1 to a Python install, a bad API key, or an ambiguous interface. The kit ships:

- the pre-generated Q3 Meridian dataset (data + the MCP server) — **no answer key**,
- the frozen `run_review(export_dir, limit) -> findings.json` contract and its JSON Schema,
- a single read-only MCP server exposing Meridian's systems of record,
- a two-tier smoke test (offline green light + opt-in live-API check),
- a devcontainer, `.env` wiring, `Makefile`, `CLAUDE.md`, and README.

The learner replaces the `run_review` stub and grows the system across Modules 1–6. The kit itself never changes after Module 0.

**No ground truth in the kit.** Learners never receive the answer key. They build their system, run it against the shipped Q3 data, and **submit their `findings.json`**. The instructor holds the answer key and evaluates the submitted output against it. This makes the kit simpler (no key to protect *within* the learner's own repo) and makes hard-coding-to-the-key impossible by construction — the learner has no key to code to.

**Downstream implication (flagged, not solved here).** Module 5 (evals), as sketched in the parent spec, had learners "score against the labeled Q3 key." Because learners have no key, Module 5 must be reconceived into something achievable without ground truth (schema/coverage validation, self-consistency checks, or a small learner-hand-labeled eval). That is the Module 5 sub-project's problem; it also means the parent program spec's grading section needs a small reconciliation. Out of scope for Module 0 beyond this note.

## The kit boundary

**The kit is a separate repo, `meridian-capstone`.** It contains only the *outputs* of the generator plus scaffolding — never generator source.

Why: the generator plants the findings and writes the answer key. If its source (or the key) reached learners, they could reverse-engineer how findings are planted and hard-code to them. So:

- The **instructor** runs the generator (the existing `meridian` repo) to produce `data/2026-Q3/` and the answer key. The instructor commits **only `data/2026-Q3/`** into the kit and **keeps the answer key** for grading.
- The kit repo never imports or vendors the generator package, and never contains the answer key.

This is the one non-negotiable separation; everything else is convenience.

## The frozen contract

Fixed in Module 0, never changed. Adding a field later would break the grader, so it must be complete now.

### Entry point

```python
# contract/run_review.py
def run_review(export_dir: Path, limit: int | None = None) -> list[dict]:
    """Review the access data in export_dir and return a list of findings,
    each conforming to contract/findings.schema.json.

    limit caps how many candidates reach the agent layer — for cheap
    iteration while debugging. None means the full run. Grading always
    calls with limit=None.
    """
```

Returns findings **in memory** (a list of dicts). A thin CLI — `python -m contract.run_review data/2026-Q3 > findings.json` — writes them for the UI and inspection. The grader imports the function and calls it directly. The Module 0 stub is `return []`.

### A finding

Two shapes, keyed by `scope`. Example (account-scoped):

```json
{
  "scope": "account",
  "account_id": "A004217",
  "employee_id": "E00918",
  "app": "Active Directory",
  "entitlement": "Domain Admin",
  "category": "terminated_access",
  "severity": "critical",
  "recommendation": "revoke",
  "rationale": "Employee terminated 2026-06-15; Domain Admin remains active with no revocation ticket.",
  "evidence": [
    {"source": "hr_roster", "detail": "term_date=2026-06-15, status=terminated"},
    {"source": "entitlements", "detail": "AD/Domain Admin, last_login 2026-06-10, still present"}
  ],
  "policy_citations": ["TERM-1"],
  "confidence": 0.98
}
```

Fields, all required unless noted:

| Field | Type | Notes |
|---|---|---|
| `scope` | `"account"` \| `"application"` | drives which subject fields apply |
| `account_id` | string \| null | required for account scope; null for application scope |
| `employee_id` | string \| null | null for orphans and application scope |
| `app` | string | the flagged app |
| `entitlement` | string \| null | the role; null for application scope |
| `category` | enum | `terminated_access, orphan_account, no_approval, grant_before_hire, dormant_privileged, contractor_overstay, privilege_creep, sod_conflict, coverage_gap, other` |
| `severity` | `critical\|high\|medium\|low` | |
| `recommendation` | `revoke\|review\|retain` | |
| `rationale` | string | human-readable why — what a reviewer reads |
| `evidence` | array of `{source, detail}` | ≥1 item; `source` names the system/file, `detail` the data point |
| `policy_citations` | array of string | policy clause IDs (e.g. `ACP-4.2`); may be empty |
| `confidence` | number 0–1 | |

Application-scoped findings (the coverage-gap case) set `account_id`, `employee_id`, and `entitlement` to null and use `app` as the subject.

**Rationale for the required set.** `rationale` and `evidence` are required so every finding is reviewable — that is the entire job of the agents' evidence-writer, and a finding with no evidence is the noise that gets real UAR tools ignored. The `category` enum is aligned to the answer key's categories so the grader can match a learner's finding to a planted case on subject **and** category; `other` lets a learner surface something genuine that wasn't planted without being schema-invalid.

### JSON Schema note

`findings.schema.json` encodes the account-vs-application conditional (an `if/then`/`oneOf` on `scope`: account requires `account_id`; application requires `app` and nulls the account fields). The exact encoding is a build-time detail; the field table above is the contract.

## The MCP server

`mcp/server.py` — a single, read-only MCP server exposing Meridian's systems of record as **per-entity lookups**. It reads a data directory from `MERIDIAN_DATA_DIR` (default `data/2026-Q3`); at grading the grader points that env var at the Q4 export and every tool serves the new quarter automatically.

### Course simplification (documented, load-bearing caveat)

In a real client, each system is its own connector — Workday for HR, Okta/AD for identity, ServiceNow for ticketing — and an agent would talk to several MCP servers (or several APIs). **This course collapses them into one server for setup simplicity.** The kit's README and `CLAUDE.md` state this explicitly, note how the tools map to distinct real systems, and flag that a production design would separate them. Learners should carry that caveat into real engagements. (Chosen over a multi-server topology to keep Module 0 frictionless; the trade-off is that a single server slightly softens the "siloed systems" premise, which the README addresses in prose.)

### Tools

*Transactional systems (per-quarter data, from the export CSVs/JSON):*

- `get_employee(employee_id) -> object | null` — HR record: name, dept, title, hire_date, term_date, employment_type, status. `null` when no record exists (the orphan signal). No manager/org-chart field — the data does not carry one; "who vouched" is a ticket's `approver`, not a reporting line.
- `get_account(account_id) -> object | null` — the IAM view of one account: `account_name` and every entitlement row (`app, role, granted_date, granted_by, last_login`). IAM data only — it does not join HR/tickets, so the agent still correlates.
- `search_tickets(account_id, app=None) -> array` — access-request tickets for an account, optionally filtered by app: `ticket_id, app, role, requested_date, approver, status`.
- `get_prior_review(account_id) -> array` — last quarter's decisions for an account: `app, reviewer, decision, review_date`. Empty when none (which, combined with `get_application`, is how the coverage gap is reasoned about).

*Reference data (structured, not prose):*

- `get_application(app_name) -> object | null` — app catalog entry: `tier, implementation_date, roles, privileged_roles, owning_dept`. The `implementation_date` is what makes the coverage-gap challenge solvable — the agent distinguishes "skipped review" (old app, absent from prior review = gap) from "new this quarter" (recent date = expected).
- `is_approved_service_account(name) -> boolean` — the registry check behind the service-account traps.
- `get_sod_matrix() -> object` — the structured conflict pairs and the Controller exemption (`{conflicts, exemptions}`). Prose rationale (ACP-4.2) lives in policy → Skills; the structured matrix is a lookup here.

### Design boundary

No tool returns a joined dossier or a bulk dump. Each answers one question about one entity — how you query production systems, and it keeps the deterministic bulk join in the Ledger (from files). This boundary is itself the "reconciliation is code, judgment is agents" lesson. **Prose policy is deliberately not served here** — the five policy docs become Agent Skills in Module 2. Live system data → MCP; policy knowledge → Skills.

## Generator prerequisite

For the MCP server's reference tools to serve the *right* per-quarter data — especially `implementation_date`, which varies by seed — the export directory must be self-contained. This requires a small enhancement to the already-merged generator: it must additionally emit three reference files into each export dir, alongside the existing CSVs/JSON:

- `applications.json` — the app catalog stamped with **this quarter's effective** `implementation_date` (i.e. the per-seed new-app date override reflected), plus `tier, roles, privileged_roles, owning_dept`.
- `sod_matrix.json` — `{conflicts, exemptions}` from the world's SoD matrix.
- `service_accounts.json` — the approved service-account registry.

This is a few lines in the generator's `emit.py` + `generate.py` (writers already exist for the other files), plus a coherence check that the emitted `applications.json` `implementation_date` for the new app is in-quarter. It is a prerequisite task in the implementation plan and is done in the generator repo, then the refreshed export is committed into the kit.

## Smoke test — the two-tier green light

**`make check` (offline, deterministic, free, CI-able)** — `tests/test_smoke.py`:

1. **Data loads** — every export file present and parseable (HR/IAM/tickets/prior-review CSVs+JSON, the three reference JSONs, the policies).
2. **The contract wires up** — `run_review(data/2026-Q3)` returns a list; `examples/sample_findings.json` validates against `findings.schema.json`; the stub's empty output validates too. Proves schema + entry point + validator agree before any real logic.
3. **The MCP server answers** — it starts and sample tool calls return correct data (`get_employee` on a known ID; `get_application` returns an `implementation_date`).

**`make check-api` (opt-in, one paid call)** — `tests/test_api.py`: a single real Claude call through the Agent SDK confirming the learner's `ANTHROPIC_API_KEY` and billing work. Separated so the offline light stays free/CI-able and so a dead key is caught at setup, not mid-Module-3.

## Dev environment

- `.devcontainer/` — Python 3.11+, deps pinned (Claude Agent SDK, the Python MCP SDK, `jsonschema`, `pytest`), the MCP server pre-registered in `.mcp.json`, VS Code extensions. One clone → container builds → `make check` goes green.
- `.env.example` → `ANTHROPIC_API_KEY=`; README step 1 is copying it to `.env`.
- `Makefile`: `check`, `check-api`, `mcp` (run the server), `help`.
- `CLAUDE.md` — project memory: repo layout, the frozen contract, the MCP tools, and the rules of the road (honor the contract signature exactly, since the instructor's grader calls it; the `limit` param is for cheap iteration; submit `findings.json` produced by `run_review`; the single MCP server is a course simplification of what would be separate connectors at a real client).
- `README.md` — the 10-minute onboarding path.

## Deferred (explicitly not in Module 0)

- **Web UI / the Surface** → Module 4. Module 0 is data + contract + MCP + environment only, so the kit stays small and the green light is unambiguous.
- **Policy as Skills** → Module 2. The kit ships the prose policies as files; turning them into Agent Skills is the learner's Module 2 work.
- **The Ledger, agents, evals** → Modules 1, 3, 5. The kit ships only the stub and the interfaces they build against.

## Instructor-side kit export

The instructor produces the kit's data by running the generator and copying **only the export directory** (never the answer key) into the kit. This is a small target in the *generator* repo — e.g. `make kit-export OUT=../meridian-capstone/data/2026-Q3` — which generates the quarter, emits the export (including the three reference JSONs), and copies it into the kit, deliberately leaving `answer_key.json` behind in the generator repo where the instructor grades against it. Making it a script (not a manual runbook) removes the risk of accidentally copying the key across the boundary.
