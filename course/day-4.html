Module 3 · Subagent decomposition

One orchestrator, many specialists.

Meridian has 22 apps, roughly 1,200 users, and around 15,000 entitlements. Your current pipeline works — but it chokes on scale, because it's one giant prompt trying to reason about everything at once. Today you decompose the problem.

The fix isn't a bigger prompt. It's division of labor: one orchestrator that holds the plan, and a small team of specialists that each do one job well and report back. It's how you'd staff a real review — a data person, a policy person, a writer — except your specialists are subagents.

What you'll build today

An orchestrator + specialist team: three subagents (a ledger-reader, a policy-applier, and a findings-writer) coordinated by one orchestrator, running end to end against Meridian's full Q3 data to produce a complete findings.json — then the enforcement layer that makes that run audit-ready: PreToolUse and PostToolUse hooks that log every file write and block secrets from leaking.

What you'll learn

  • What an agent's tools are — its senses and hands — and why fewer tools means tighter behavior
  • What a subagent is, and why decomposition beats one huge prompt at scale
  • What MCP is, and how it lets a specialist talk to the Meridian data server
  • How to give each specialist a narrow scope and wire them in sequence
  • How to run the full pipeline end to end and read findings counted by severity
  • What hooks are — how you guarantee behavior instead of just asking for it — and use them as your audit and enforcement layer

Cycle 1

What are tools?

≈ 45 min
Concept

Before you split work across subagents, understand the thing each agent actually works with: its tools. An agent's tools are its senses and hands — reading a file, writing one, running a shell command, searching the codebase. Claude Code can only do what its tools let it do, and every tool call is a decision the agent makes on its own.

What is a tool?

A tool is one specific action an agent is allowed to take — Read a file, Write or Edit one, run a shell command with Bash, Grep for text, Glob for filenames. Give the agent a tool and it can reach for it whenever it judges the moment is right. Take a tool away and that whole class of action becomes impossible — not discouraged, impossible.

Blast radius. The set of tools an agent holds is its blast radius — the full range of what it could do if it misjudged a single call. A read-only agent can be wrong but not harmful. An agent with unrestricted Bash on a production box could delete data or leak a secret with one decision. This is the compliance instinct applied to agents: you shrink the blast radius by granting fewer tools, so tighter scope means safer behavior.

What is MCP?

MCP (Model Context Protocol) is a standard way for Claude to talk to an outside tool or data source — a shared language between the model and, say, a data server. The Meridian kit ships an MCP server that exposes its access data through clean, UAR-specific tools, so a specialist can ask for exactly the rows it needs instead of loading everything. Its tools: get_ledger, get_entitlements, and get_person.

Cycle 2

Subagents & the first specialist

≈ 90 min
Concept

A subagent is a helper Claude that's handed one narrowly-scoped job and its own slice of context — its own small set of tools and nothing more. The orchestrator is the Claude that holds the overall plan: it breaks the work into pieces, delegates each piece to the right specialist, and assembles the results. Same idea as a review lead who doesn't do every task personally but knows who should.

Why decompose? A single prompt asked to reason about 15,000 entitlements at once runs out of room — it loses track, mixes cases, and slows down. Split the work and each specialist keeps a small, clean context: the ledger-reader thinks only about data, the policy-applier thinks only about Skills, the findings-writer thinks only about output shape. Small scopes stay sharp.

Here's the delegation map you'll build — one orchestrator, three specialists:

Delegation map 
            orchestrator
           /     |      \
  ledger-reader  policy-applier  findings-writer
   (reads MCP)   (applies Skills)  (writes findings.json)

Start with one specialist and prove it works before building the whole team. The ledger-reader is the natural first pick: its only job is to fetch access data from the Meridian MCP server and hand it back. If it can round-trip — ask for rows, get rows — the hardest wiring of the day is behind you. The kit's MCP server already exists; you just start it and point a subagent at it.

Concept

Cycle 5

Hooks: the enforcement layer

≈ 90 min
Concept

Everything so far has asked the system to behave — a rule in CLAUDE.md, a narrow scope on a subagent. Hooks are how you guarantee behavior instead of requesting it. A hook is code that runs automatically around every tool call, whether the agent wants it to or not. For compliance, that makes hooks your audit and enforcement primitive: the layer that proves what happened and stops what mustn't.

What is a PreToolUse hook?

A PreToolUse hook runs before a tool call executes. Because it goes first, it can block the call, modify its input, or log it. That's your enforcement point: catch a write before it happens, or record it for the audit trail before anything touches disk.

What is a PostToolUse hook?

A PostToolUse hook runs after a tool call, so it can react to what came back — inspect the result, flag it, or refuse to let it stand. You'll use one to scan output for anything that looks like a leaked secret and stop it cold.

Two hooks, two jobs — one records, one guards:

The enforcement layer 
PreToolUse   (file write)  → append to audit/2026-Q3.jsonl   [ AUDIT ]
PostToolUse  (any output)  → scan for secrets, block on hit   [ GUARD ]
Task
  1. Add a PreToolUse hook that audits every file write.

    Why: this is your audit trail. Before any write lands, the hook appends one line — timestamp, tool name, target path — to the quarter's audit log, so every change is on the record.

    Claude Code prompt 
    Add a PreToolUse hook that fires on every file-writing tool
(Write, Edit) and appends one JSON line to audit/2026-Q3.jsonl:
the timestamp, the tool name, and the target path.
  2. Add a PostToolUse hook that blocks leaked secrets.

    Why: this is your guardrail. After a tool runs, the hook scans the output for obvious secret patterns and blocks the call if it finds one — the system can't emit a credential even if it tries.

    Claude Code prompt 
    Add a PostToolUse hook that scans tool output for obvious secrets —
patterns like sk-, ANTHROPIC_API_KEY, or "password:" — and blocks
the tool call if any match, with a clear message about what it caught.
  3. Run the pipeline again and watch the audit log fill.

    Why: with the hooks in place, re-run the Q3 review and tail the audit file — every write the pipeline makes should show up as a line.

    Claude Code prompt 
    Run run_review(export_dir='data/2026-Q3', limit=None) again, then
show me the last 10 lines of audit/2026-Q3.jsonl so I can see the
hook recorded each write.
    tail -n 3 audit/2026-Q3.jsonl {"ts":"2026-07-23T14:02:11Z","tool":"Write","path":"findings.json"} {"ts":"2026-07-23T14:02:11Z","tool":"Edit","path":"findings.json"} {"ts":"2026-07-23T14:02:12Z","tool":"Write","path":"summary.md"}
  4. Try to leak a fake secret and confirm the guardrail blocks it.

    Why: an untested guardrail is a guess. Deliberately push a fake secret through and confirm the PostToolUse hook catches it — a guardrail you've watched fire is one you can trust.

    Claude Code prompt 
    Try to write a finding whose notes field contains the string
sk-fake-secret-12345. Show me what the PostToolUse hook does.
    findings-writer → Write(findings.json) PostToolUse guard: matched secret pattern "sk-" in output ✗ tool call BLOCKED — write refused
    Stuck?

    The write went through? The guard isn't matching. Ask Claude: "the PostToolUse hook let sk-fake-secret-12345 through — show me the pattern it's checking and why it didn't match," then tighten it until the block fires.

  5. Commit the enforcement layer.
    Terminal 
    git add .
git commit -m "Add PreToolUse audit + PostToolUse secret-guard hooks"
Checkpoint

You're done with Cycle 5 when audit/2026-Q3.jsonl exists and has a line for every write from the last run, and your guardrail test blocks output containing sk-fake-secret-12345. You now have an enforcement layer, not just a request.
