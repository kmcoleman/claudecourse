Cycle 1

What are tools?

≈ 45 min
Concept

Before you split work across subagents, understand the thing each agent actually works with: its tools. An agent's tools are its senses and hands — reading a file, writing one, running a shell command, searching the code. Claude Code can only do what its tools let it do, and every tool call is a decision the agent makes on its own.

What is a tool?

A tool is one specific action an agent is allowed to take — Read a file, Write or Edit one, run a shell command with Bash, Grep for text, Glob for filenames. Give the agent a tool and it can reach for it whenever it judges the moment is right. Take a tool away and that whole class of action becomes impossible — not discouraged, impossible.

Blast radius. The set of tools an agent holds is its blast radius — the full range of what it could do if it misjudged a single call. A read-only agent can be wrong but not harmful. An agent with unrestricted Bash and Write could overwrite ledger.csv, rewrite a finding, or leak a secret with one decision. This is the compliance instinct applied to agents: you shrink the blast radius by granting fewer tools. Hold that thought — in Cycle 3 you'll hand each specialist only the tools its one job needs.

What is MCP?

MCP (Model Context Protocol) is a standard way for Claude to talk to an outside tool or data source — a shared language between the model and, say, a data server. The Meridian kit ships an MCP server called meridian-systems that exposes its access data through clean, read-only, per-entity tools: ask it about one account or one person and it answers, rather than handing back the whole export. It's already registered in .mcp.json, so Claude Code launches it for you — there's no server to start by hand.

Two ways to reach the data, and they're not interchangeable. The bulk Ledger you built in Day 2 comes from files read in one pass — that's the right tool for the deterministic join over all 15,158 grants. The MCP server is the opposite: targeted, judgment-time lookups about a single account or person, the kind a reviewer makes while deciding one case. Reconciliation is files; judgment is MCP. You'll use both today.

Cycle 2

Subagents & the first specialist

≈ 90 min
Concept

A subagent is a second Claude handed one narrowly-scoped job and its own slice of context — its own system prompt, its own small set of tools, and nothing else. The orchestrator is the Claude that holds the overall plan: it breaks the work into pieces, delegates each piece to the right specialist, and assembles the results. Same idea as a review lead who doesn't do every task personally but knows who should.

What is a subagent?

A project subagent is a Markdown file at .claude/agents/<name>.md with a short YAML frontmatter block. name and description are required — and the description is the important one, because Claude reads it to decide when to delegate. Optional tools restricts what the subagent may touch (omit it and it inherits everything — usually not what you want); optional model can route a simple specialist to a cheaper model. Everything below the frontmatter becomes the subagent's system prompt.

Why decompose? A single context asked to reason about 15,158 grants at once runs out of room — it loses track, mixes cases, and slows down. Split the work and each specialist keeps a small, clean context: the ledger-reader thinks only about fetching facts, the policy-applier thinks only about the Skills, the findings-writer thinks only about output shape. Small scopes stay sharp. Here's the team you'll build:

Delegation map 
                 orchestrator
                /      |       \
   ledger-reader   policy-applier   findings-writer
   (MCP + Read)    (Read + Skills)  (Write findings.json)
   read-only       read-only        the only writer

Start with one specialist and prove it works before building the whole team. The ledger-reader is the natural first pick: its only job is to fetch the facts about one account from the meridian-systems server and hand them back. If it can round-trip — ask about an account, get its record — the hardest wiring of the day is behind you.

A quirk worth knowing now

Just like .claude/skills/ yesterday, Claude Code only watches an agents directory that existed when the session started. Create .claude/agents/ for the first time mid-session and you must restart before your first subagent is discovered. Hit this now, on an empty directory, rather than while debugging a specialist you think is broken.

The full specialist team

≈ 90 min
Concept

With the reader proven, add the other two specialists and let the orchestrator run all three in sequence. Each keeps a narrow scope and a narrow toolset — the tool list is where Cycle 1's blast-radius lesson becomes concrete:

  • ledger-reader — gathers an account's facts from MCP. Tools: the meridian-systems lookups + Read. Cannot write. (Cycle 2.)

Cycle 5

Hooks: the enforcement layer

≈ 90 min
Concept

Everything so far has asked the system to behave — a rule in CLAUDE.md, a narrow toolset on a subagent. Hooks are how you guarantee behavior instead of requesting it. A hook is a command Claude Code runs automatically around a tool call, whether the agent wants it to or not. For compliance, that makes hooks your audit and enforcement primitive: the layer that records what happened and stops what mustn't.

Hooks are configured in .claude/settings.json under a hooks block, keyed by event. Each entry has a matcher (which tools it fires on, e.g. Write|Edit) and a command to run. The command receives the tool call as JSON on standard input — tool_name, tool_input, session_id, and more — and communicates its decision back through its output.

What is a PreToolUse hook?

A PreToolUse hook runs before a tool call executes. Because it goes first, it can deny the call outright — return a permissionDecision of "deny" and the tool never runs. That's your enforcement point: catch a write before it touches disk. This is the only place a write can actually be prevented.

What is a PostToolUse hook?

A PostToolUse hook runs after a tool call has already succeeded. It can't un-write what just landed — the tool is done — but it can react: record what happened, add context, or halt the run before Claude continues. That makes it the honest place for an audit trail, which by nature records writes that actually occurred.

Two hooks, matched to what each event can truthfully do — one guards, one records:

The enforcement layer 
PreToolUse   (Write|Edit) → scan pending content, DENY on a secret   [ GUARD ]
PostToolUse  (Write|Edit) → append the write to audit/2026-Q3.jsonl  [ AUDIT ]

You won't write these from scratch. The kit ships working, commented stubs at .claude/hooks/examples/ — secret_guard.py, audit_write.py, and a settings.hooks.json showing the wiring. Your job is to copy them into .claude/hooks/, wire them into settings.json, and understand what each line does — not to invent the plumbing.

Task
  1. Copy the audit stub and wire the PostToolUse hook.

    Why: start with the recorder. Before you block anything, get every write onto the record — that alone changes an unwitnessed run into an auditable one.

    What you're building. The audit hook, live. Copy .claude/hooks/examples/audit_write.py into .claude/hooks/ and add a PostToolUse entry matching Write|Edit to .claude/settings.json (the shape is in examples/settings.hooks.json). After each successful write it appends one JSON line — timestamp, tool, path, session — to audit/2026-Q3.jsonl.

    .claude/settings.json — the PostToolUse entry 
    "PostToolUse": [
  { "matcher": "Write|Edit",
    "hooks": [
      { "type": "command",
        "command": "python3 \"$CLAUDE_PROJECT_DIR/.claude/hooks/audit_write.py\"" }
    ] }
]

    How you'll know you got it right. settings.json stays valid JSON, and a single test write produces one line in audit/2026-Q3.jsonl with all four fields present.

    Stuck? — the audit stub, line by line

    event = json.load(sys.stdin) — Claude Code hands the completed tool call to the hook as JSON on standard input; this reads it.

    entry = {...} — builds the audit record: a UTC timestamp, the tool_name ("Write"/"Edit"), the file_path from tool_input, and the session_id so a line traces to a run.

    audit_dir = .../CLAUDE_PROJECT_DIR/audit and os.makedirs(..., exist_ok=True) — resolves the log location from the project dir Claude Code sets, and creates the folder on first use.

    log.write(json.dumps(entry) + "\n") — appends one line. Open mode "a" makes it append-only: every write adds a line, none overwrites another. sys.exit(0) — records only; it never blocks.

    Nothing appears? Confirm the hook is under PostToolUse (not Pre) and that the command path resolves — $CLAUDE_PROJECT_DIR is set by Claude Code at run time.

  2. Copy the guard stub and wire the PreToolUse hook.

    Why: now the enforcement. The guard has to run before the write, which is why it's a PreToolUse hook — a post-hoc scan would be reading a secret that's already on disk.

    What you're building. The secret guard, live. Copy .claude/hooks/examples/secret_guard.py into .claude/hooks/ and add a PreToolUse entry matching Write|Edit. It reads the content about to be written and, if it matches a secret pattern (sk-, ANTHROPIC_API_KEY, password:, Bearer ), returns a deny — so the write never happens.

    How you'll know you got it right. settings.json now carries both a PreToolUse and a PostToolUse entry, still valid JSON, and an ordinary write (a real finding) passes untouched. You'll fire the guard deliberately in Step 4.

    Stuck? — the guard stub, line by line

    SECRET_PATTERNS = [...] — the regexes that must never be written: sk--style tokens, a named key env var, a password: field, a Bearer header. Extend this list per engagement.

    event = json.load(sys.stdin) then pending_text = " ".join(...content, new_string...) — reads the pending call and joins the text about to be written. Write carries the body in content; Edit carries it in new_string, so one guard covers both.

    for pattern in SECRET_PATTERNS: if re.search(...) — on a match it prints a permissionDecision: "deny" with a reason naming the pattern, then exit(0). Exit 0 with a deny decision blocks the tool; the reason is shown so you know exactly what tripped it.

    Final sys.exit(0) with no output — no match, so the guard stays silent and the normal permission flow proceeds. Silence means allow.

    Why not PostToolUse? A PostToolUse hook fires after the write lands — the secret would already be on disk. Prevention has to be Pre.

  3. Re-run the Q3 review and watch the audit log fill.

    Why: with the hooks live, a normal run should record itself. Confirm the recorder before you trust the guard.

    What you're building. Evidence the audit trail works on a real run. Regenerate findings.json through the pipeline, then look at the tail of the log.

  4. Fire the guardrail with a fake secret.

    Why: an untested guardrail is a guess. Push a fake secret through deliberately and watch the PreToolUse hook refuse it — a guard you've seen fire is one you can trust.

    What you're building. Proof the guard blocks. Have the pipeline attempt to write a finding whose text contains the string sk-fake-secret-12345, and confirm the write is denied before it reaches disk.

    findings-writer → Write(findings.json) [contains sk-fake-secret-12345] PreToolUse guard: matched /sk-[A-Za-z0-9]/ in the pending write ✗ write DENIED — secret never reached disk

    How you'll know you got it right. The write is refused, the reason names the pattern that matched, and findings.json does not contain the fake secret afterward. The guarantee is structural now, not a request.

    Stuck?

    The write went through? The guard isn't firing. Check three things: the hook is under PreToolUse (a PostToolUse hook can't prevent the write); the matcher includes Write; and the pattern actually matches — the stub keys on content and new_string, which is where Write and Edit put the text.

    Blocked, but you want to see why? The deny reason is fed back to Claude and shown in the run. It should name the matched pattern — if it doesn't, you're looking at a different block (a permission prompt, say), not the guard.

Only a PreToolUse hook can stop a write before it lands; a PostToolUse hook can only record one that already did.
