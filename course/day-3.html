Cycle 1

What a Skill is, and why prose

≈ 60 min
Concept

A Skill is a file that tells Claude how to think about one specific domain. It isn't code and it isn't a settings table — it's written guidance, in plain language, that Claude reads before it reasons about a problem. Give Claude a "Segregation of Duties" Skill and it evaluates access grants the way someone who wrote that policy would.

What is Markdown?

Markdown is a lightweight way to write formatted text in a plain file — you mark a heading with #, a bold word with **stars**, a list with dashes. It stays readable as plain text and needs no special program. Skills are written in Markdown, in files that end in .md.

Why prose, not a config file? Compliance rules aren't clean if-then switches. Rules have exceptions; exceptions have their own exceptions; and the policy language carries intent that decides the edge cases. A table can hold "Admin + not-a-manager = flag." It can't hold "unless the grant is a documented break-glass account reviewed quarterly, in which case note it but don't escalate." Prose can. That nuance is exactly what you're paid to apply — and exactly what a Skill lets Claude apply too.

The kit ships an example Skill so you can see the shape before writing your own.

Cycle 2

Your first policy Skill — Segregation of Duties

≈ 90 min
Concept

Segregation of Duties (SoD) is the principle that no single person should control a whole risky process end to end — the person who enters an invoice shouldn't also be able to approve it. Meridian's SoD policy, and the conflicting role pairs it points to in the SoD matrix, run to a few pages of prose. You'll turn the relevant part into a Skill.

Remember the Finance & Accounting employee from Day 2 with two linked accounts — a standard login and an old _adm account. Look at what those accounts can do in Atlas ERP: one carries the AP Clerk role (enter an invoice), the other carries AP Manager (approve it). One human, both halves of the payment — and this person is a clerk, not the Controller, so no exemption covers it. That's a textbook SoD violation, and it's the case you'll test your Skill against.

.claude/skills/sod.md (target shape) 
# Segregation of Duties

## Rule
Flag any person who holds a conflicting pair of roles from the SoD
matrix — for example **AP Clerk + AP Manager** in Atlas ERP (enter an
invoice, then approve it) — whether through one account or several
linked accounts.

## Exceptions
- ACP-4.2 documented exemption: the Controller in Finance & Accounting
  may hold AP Manager + Vendor Admin under a CFO-signed compensating
  control (quarterly payment review). Access held under ACP-4.2 is not a finding.

## Citation format
When flagging, cite: "SoD Skill, §".

Cycle 3

Two more policies

≈ 90 min
Concept

You know the pattern now: read the policy, draft the Skill, refine the exceptions, test on a known case, save. Two more policies, same rhythm — and you should move noticeably faster the second and third time.

Privileged Access Standard: a privileged role requires an approved access request (a ticket) before it's granted, and it must show activity within 180 days or be reviewed for removal — a dormancy check that lives inside this standard. Registered, documented break-glass accounts are exempt from that dormancy rule. Contractor Access Standard: a contractor's access ends on their statement-of-work (SOW) end date; any extension needs a new approved ticket referencing the renewed SOW before the old one lapses. Both are prose policies with their own exceptions, and both become Skills.

Task
  1. Draft and save the Privileged Access Review Skill.

    Why: same flow as SoD. Point Claude at the policy, refine, and save to the Skills folder.

    Claude Code prompt 
    Read policies/privileged-access-standard.md. Draft a Skill that
flags privileged roles granted without an approved ticket, and
privileged access dormant beyond 180 days (registered break-glass
accounts exempt). Number the clauses. Save it to
.claude/skills/privileged-access.md.
  2. Test the Privileged Access Skill on one known account.

    Why: same discipline — confirm on a case you understand before you trust it on the whole dataset. emergency.admin is a good one: it looks dormant, but it's a registered break-glass account, so the Skill should not flag it.

    Claude Code prompt 
    Using the Privileged Access Skill, evaluate emergency.admin — a
break-glass Domain Admin account in Active Directory with no login
in ~300 days. Should the 180-day dormancy rule flag it? Cite the
clause.
  3. Draft, save, and spot-test the Contractor Access Standard Skill.

    Why: the third time should feel routine. Draft from the policy, save to .claude/skills/contractor-access.md, and test it on one contractor whose SOW has already lapsed.

    Claude Code prompt 
    Read policies/contractor-access-standard.md. Draft a Skill that
flags contractor access still active past its SOW end date, unless
a new approved ticket references a renewed SOW. Number the clauses.
Save to .claude/skills/contractor-access.md, then test it on the
contractor whose term_date is about three weeks past.
    Stuck?

    Not sure the Skill is being applied? Ask Claude to quote the exact clause it used and the dates it read — the SOW end date and any vouching ticket. A manager's after-the-fact vouch in a ticket does not satisfy the standard; only a new ticket referencing a renewed SOW does. If the call looks wrong, the Skill's wording — not the data — is usually the fix.

  4. Commit all three Skills.
    Terminal 
    git add .
git commit -m "Add privileged-access and contractor-access policy Skills"
Checkpoint

You're done with Cycle 3 when three Skills live in .claude/skills/ — sod.md, privileged-access.md, and contractor-access.md — and each has passed a spot-test on a known account.

Cycle 4

Wire Skills into triage

≈ 90 min
Concept

Yesterday's triage produced findings from one hard-coded rule. Today you rewire it so it applies your three Skills and — crucially — makes every finding cite the clause it came from. A finding an auditor can trace back to a specific policy clause is worth ten a reviewer has to take on faith.

The change is one new field on every finding: policy_reference. Here's the shape you're aiming for:

findings.json (with citation) 
{
  "finding_id": "F-0007",
  "canonical_id": "MRE-00317",
  "person": "<name assigned at seed time>",
  "app": "Atlas ERP",
  "role": "AP Clerk + AP Manager",
  "reason": "Holds AP Clerk and AP Manager — can enter an invoice and approve it",
  "policy_reference": "SoD Skill, §2.3",
  "severity": "high",
  "status": "open"
}
Task
  1. Update the triage step to apply all three Skills.

    Why: triage should now run each grant past every relevant policy Skill, not a single rule.

    Claude Code prompt 
    Update triage.py so that for each ledger entry it evaluates the
grant against the SoD, privileged-access, and contractor-access
Skills, and emits a finding for each violation.
  2. Add the policy_reference field to every finding.

    Why: this is the day's whole point — traceability. Each finding must carry the exact Skill and clause that produced it.

    Claude Code prompt 
    Add a policy_reference field to every finding, formatted like
"SoD Skill, §2.3", holding the specific Skill and clause the
finding came from.
  3. Run the pipeline and read the cited findings.

    Why: this is your proof. Every finding should now name its policy source.

    Terminal

  4. Commit your cited findings.
    Terminal

git commit -m "Wire Skills into triage; findings now cite policy clauses"
