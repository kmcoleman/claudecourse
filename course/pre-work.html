Pre-Work: Get Ready for the Bootcamp

The bootcamp moves fast, and Day 1 assumes your laptop is already set up. This pre-work gets you there — every tool installed, your access working, and the course kit running green — so day one is about building, not troubleshooting.

You don't need any coding experience. Each step below explains what a tool is the first time you meet it, gives you the exact thing to do, and tells you how to prove it worked. Work through it in order; later cycles build on earlier ones.

Timeline

Complete this in the three weeks before class starts. Budget 4–6 hours over the three weeks — a couple of sittings, not one marathon. Office hours are available if you get stuck — [office hours schedule].

What you'll accomplish

  • Install your development environment — a terminal, VS Code, git, and Python
  • Get your GitHub Enterprise access working, and authenticated from both the terminal and VS Code
  • Install and test Claude Code, your coding partner for the week
  • Clone the course kit and run its smoke test — the "green light" that proves everything works
  • Be fully ready for Day 1, with nothing left to install or configure
The one rule of pre-work

If you get stuck for more than 15 minutes on ANY step, do not struggle alone. Bring it to office hours ([office hours schedule]). Setup snags are normal, they're usually a one-line fix, and sorting them out early is exactly what this window is for. Being stuck is not a sign you're behind — waiting until Day 1 to ask is.

Cycle 2

Terminal, git, VS Code, and GitHub Enterprise

≈ 2 hours
Concept

This is the longest cycle — the workhorse of pre-work. By the end you'll have the three tools every engineer lives in, and you'll be able to reach your company's GitHub Enterprise from both the terminal and VS Code. Take it a step at a time, and remember the 15-minute rule.

What is a terminal (command prompt)?

The terminal is a window where you type commands as text instead of clicking buttons. It looks intimidating and isn't — it's just a different door into your computer. On Windows it's called PowerShell or Terminal; on Mac it's Terminal. You'll run everything this week from here.

What is VS Code?

Visual Studio Code is a free editor built for code, and the primary editor for this course. It's where you'll read files, open a terminal, and see your whole project in one window.

What is git — and what is GitHub Enterprise?

git tracks the history of your files: every save point is a labeled snapshot called a commit that you can always return to. GitHub is a website where git projects live online so they can be shared and copied. GitHub Enterprise is your company's private, self-hosted version of GitHub — same idea, behind your company's login. The course kit and your team's work both live there.

Watch ≈ 20 min
GitHub Tutorial for Beginners (2025) — CodeWithChris

A friendly, no-coding-required walkthrough of what GitHub is and how the basic workflow feels. Watch it before the hands-on steps below so the vocabulary isn't brand new.

Task
  1. Install VS Code, then open it.

    Why: it's your workspace for the week. Download from the official site and run the installer for your operating system.

    Browser 
    https://code.visualstudio.com/download
    Stuck?

    Windows: choose the "User Installer" for your architecture (almost always x64). Mac: unzip and drag VS Code into Applications; if it won't open, right-click the app and choose "Open" once to clear the security prompt.

  2. Install git, then verify it in a terminal.

    Why: --version is the universal "are you installed and reachable?" check. Open VS Code's terminal (Terminal → New Terminal) and run the check there.

    Browser 
    https://git-scm.com/downloads
    Terminal 
    git --version
    git --version git version 2.45.1
    Stuck?

    "command not found"? Close the terminal completely and open a fresh one — newly installed tools often aren't visible until you do. On Windows, if it still fails, reboot; the installer updates a system setting that needs a restart.

  3. Do the 15-minute GitHub "Hello World" tutorial.

    Why: this is the fastest way to feel the whole GitHub loop end to end — create a repository, make a branch, commit a change, and open a pull request — on a throwaway repo where nothing matters. Follow GitHub's official walkthrough start to finish.

    Browser 
    https://docs.github.com/en/get-started/start-your-journey/hello-world
  4. Verify your GitHub Enterprise access in the browser.

    Why: this is the one thing most likely to need IT's help, so prove it early. Browse to your company's GitHub Enterprise, sign in with SSO or your company credentials, and confirm you can see your team's organization.

    Browser — your company's GitHub Enterprise 
    https://[GH Enterprise URL]

    Replace [GH Enterprise URL] with the address your instructor gives you. Once signed in, confirm you can see your team's org.

    Stuck?

    SSO won't let you in, or you can't see your org? This is almost always an access-provisioning issue on your company's side, not something you can fix alone. Note exactly what you see and bring it to office hours ([office hours schedule]) so it can be sorted with IT well before Day 1.

  5. Set up authentication to GitHub Enterprise — SSH key or Personal Access Token.

    Why: signing in through the browser isn't enough — the terminal needs its own way to prove it's you. There are two common methods; you only need one. An SSH key is a pair of cryptographic files your machine uses to identify itself. A Personal Access Token (PAT) is a long password-like string with specific permissions ("scopes"). If you're unsure, a PAT is the quicker path to start.

    Option A — SSH key

    In your GitHub Enterprise Settings → SSH and GPG keys, follow the "generate a new SSH key" steps, then add the resulting public key to your account. GitHub's docs walk through it for Mac and Windows.

    Option B — Personal Access Token (PAT)

    In Settings → Developer settings → Personal access tokens, generate a token with repo scope (enough to clone and pull). Copy it when it appears — you won't see it again — and paste it as the password when git prompts you.

    Test that it works by listing a repo's refs without downloading anything:

    Terminal — test your auth (no files downloaded) 
    git ls-remote https://[GH Enterprise URL]/[placeholder repo path]

    Swap in your [GH Enterprise URL] and a real repo at [placeholder repo path] (your instructor will name one you can reach). A list of refs printing back means your terminal is authenticated. For an SSH key, use the git@…:… form of the address instead of https://….

    Stuck? — common auth failures

    SSH: "Permission denied (publickey)." Your public key isn't on your GitHub Enterprise account, or you added the private half by mistake. Re-add the public key (the .pub file) under Settings → SSH and GPG keys.

    PAT: "Authentication failed" or "403." The token is missing the repo scope, has expired, or wasn't SSO-authorized for your org — some Enterprise setups require you to click "Configure SSO / Authorize" next to the token. Regenerate with the right scope and authorize it.

    Either way, if it doesn't clear in 15 minutes, bring it to office hours ([office hours schedule]).

  6. Configure VS Code for GitHub Enterprise.

    Why: you'll want to browse and open repos from inside your editor, not just the terminal. Install the "GitHub Pull Requests and Issues" extension, sign in, and confirm you can see a GitHub Enterprise repo in the VS Code sidebar.

    VS Code — Extensions (Ctrl/Cmd+Shift+X), search & install 
    GitHub Pull Requests and Issues

    After installing, open the Command Palette (Ctrl/Cmd+Shift+P) and run "GitHub: Sign in". For a self-hosted Enterprise server you may also need to set the github-enterprise.uri setting to your [GH Enterprise URL]. Then open a repo and confirm it appears in the sidebar.

    Stuck? — extension won't connect

    Sign-in only offers github.com, not your Enterprise server? Set the github-enterprise.uri setting (Settings → search "github enterprise") to your company's [GH Enterprise URL], reload VS Code, and sign in again. If it still won't connect, that's an office-hours item.

  7. Prove the whole chain: clone a repo from GitHub Enterprise two ways.

    Why: the real test is downloading a full copy of a repo — once from the terminal, once from the VS Code UI. If both work, your access and authentication are solid and Day 5's clone of the kit will be painless.

    Terminal — clone via git 
    git clone https://[GH Enterprise URL]/[placeholder repo path]

    Then do the same from the editor: VS Code Command Palette → "Git: Clone" → pick a GitHub Enterprise repo → choose a folder. Both should land a copy on your machine.

Checkpoint

You're done with Cycle 2 when git --version and code --version both print a number, you can sign in to [GH Enterprise URL] and see your org, and you've successfully cloned a repo from GitHub Enterprise both from the terminal and from the VS Code UI. This is the big one — if it's green, the rest is easier.

Cycle 3

Python and a clean sandbox

≈ 90 min
Concept

The access-review code you'll build runs on Python. You won't need to master the language — Claude Code writes most of it — but it has to be installed, and it should run in a clean, isolated space so this project's tools never collide with anything else on your machine.

What is Python?

Python is a readable, beginner-friendly programming language and the standard for data work, which is why the course uses it. When you run python something.py, you're asking Python to execute the instructions in that file.

What is a virtual environment (venv)?

A venv is a private sandbox for one project's packages. Without it, everything you install piles into one shared space and projects start breaking each other. With it, this project's tools live in their own folder. When the venv is active, your prompt usually shows (venv) at the start of the line. pip is the installer that puts a package into that sandbox with pip install <name>.

Watch ≈ 9 min
Python Virtual Environments — Full Tutorial for Beginners — Tech With Tim

A short, clear walkthrough of creating, activating, and using a venv. It maps directly onto the steps below.

Task
  1. Install Python 3.11 or newer, then verify it.

    Why: same --version check as git. On the Windows installer, tick "Add Python to PATH" — it saves a real headache later.

    Browser 
    https://www.python.org/downloads
    Terminal 
    python --version
    python --version Python 3.12.4
    Stuck?

    "command not found" or wrong version? On Mac, try python3 --version — many Macs use python3 for the version you installed. On Windows, if the command opens the Microsoft Store, you skipped "Add to PATH" — re-run the installer and tick that box.

  2. Create a virtual environment and activate it.

    Why: creating the sandbox isn't enough — you have to step inside. Look for (venv) to appear at the front of your prompt.

    Terminal — create it 
    python -m venv venv
    Terminal · Mac — activate 
    source venv/bin/activate
    Terminal · Windows — activate 
    venv\Scripts\activate
    Stuck?

    Windows blocks the activate script? If you see "running scripts is disabled," you need to allow local scripts once. Search that message, or ask at office hours for the exact one-line command — it's a known, safe fix.

    Mac: python -m venv fails? Try python3 -m venv venv instead.

  3. Install pandas to confirm the sandbox works.

    Why: pandas is the table-handling library you'll lean on from Day 2 onward, so installing it now both proves your sandbox works and gives you a head start. It pulls in a few helpers of its own — that's normal.

    Terminal 
    pip install pandas
    pip install pandas Successfully installed numpy-2.1.1 pandas-2.2.3 python-dateutil-2.9.0 pytz-2024.2 ...
  4. Confirm you can import pandas in a Python session.

    Why: installing and using are different checks. Open Python's interactive prompt (the REPL), import pandas, and — if no error appears — your Python bench is sound. Type exit() to leave.

    Terminal — start Python, then type the import 
    python
>>> import pandas
>>> exit()
    Stuck?

    "ModuleNotFoundError: No module named 'pandas'"? Your venv probably isn't active, so python is a different interpreter than the one pip installed into. Re-activate the venv (you should see (venv)), then try again. On Mac, make sure the python and pip you use are the same one — inside an active venv they are.

Checkpoint

You're done with Cycle 3 when python --version prints 3.11 or higher, pip --version works, your prompt shows (venv), and import pandas succeeds with no error. Your Python sandbox is clean and isolated.

Cycle 4

Anthropic account, API key, and Claude Code

≈ 60 min
Concept

Now the star of the week. Claude Code turns Claude into a working coding partner living right in your terminal — it reads your files, writes and edits code, runs commands, and explains what it did, all from plain-English instructions. To use it, it needs a key that proves the requests are yours — and that key must be handled carefully.

What is an API key?

An API key is a long secret string — like a password for programs. It tells Anthropic's servers "these requests belong to this account." Anyone who has your key can spend against your account, so treat it like a password: never shared, never posted, never committed to git.

What is a .env file (and .gitignore)?

A .env file is a plain-text file that holds secrets like API keys, kept out of your code. The golden rule: a .env must never enter git. You keep it out by listing it in a .gitignore file, which tells git "pretend these files don't exist."

Task
  1. Create an Anthropic account and generate an API key.

    Why: this is the credential Claude Code uses. Create the account yourself, then open API Keys and create one. Copy it the moment it appears — you won't be able to see it again.

    Browser — console 
    https://console.anthropic.com
    Browser — API keys 
    https://console.anthropic.com/settings/keys
    Stuck?

    Creating accounts and entering passwords is something you do yourself — never Claude. If the course provides billing or a shared workspace, your instructor will tell you how to join before you generate a key; check at office hours if you're unsure.

  2. Save the key in a .env file — and make sure git ignores it.

    Why: this is the single most important security habit of the week. The key goes in .env; .env goes in .gitignore; neither the key nor the file ever reaches git. Practice it now on a scratch folder so it's a reflex by Day 1.

    .env (create this file — use your real key) 
    ANTHROPIC_API_KEY=sk-ant-xxxxxxxxxxxxxxxxxxxx
    .gitignore (add this line) 
    .env
    Stuck?

    How do I know it's really ignored? Run git status in that folder. If .env does not appear in the list, git is correctly ignoring it. If it does appear, your .gitignore line is misspelled or in the wrong folder.

    Never commit a key. If you ever do by accident, tell your instructor and rotate (regenerate) the key immediately — the old one must be treated as leaked.

  3. Install the Claude Code CLI, then verify it.

    Why: this puts the claude command on your machine. Open the official docs and use the Native Install for your operating system — a single command that needs nothing else installed first. Then confirm with --version.

    Browser 
    https://code.claude.com/docs/en/overview
    Terminal 
    claude --version
    Stuck?

    "command not found" after installing? Close the terminal and open a fresh one so it picks up the new command. If the docs offer several install methods, the Native Install (a curl or irm one-liner) is the simplest and doesn't require Node.js.

  4. Start Claude Code, sign in, and ask it one question.

    Why: this is the moment it becomes real. Launch claude; the first time, it walks you through signing in — use the Anthropic account you made the key with. Then, in your own words, ask it something simple to feel the back-and-forth — for example, ask it to explain what it can help you do this week, as if you've never written code. Read the answer: you're now working with your coding partner.

    Terminal 
    claude
    Stuck?

    It won't sign in, or asks for a key? Follow the on-screen sign-in prompt with the account you created the key under. If it instead reads a key from your environment, make sure your .env line is exactly ANTHROPIC_API_KEY=… with no spaces around the equals sign, and that you launched claude from the folder that holds it.

Checkpoint

You're done with Cycle 4 when claude --version prints a number, your key lives in a .env that git ignores, and Claude Code has answered your first prompt. Your coding partner is online.

Cycle 5

Clone the kit and run the smoke test

≈ 30 min
Concept

Time to bring it all together. You'll pull the course kit onto your machine, run its one-shot setup script, and confirm the green light — the automated checks that prove your whole bench works together. If this passes, you are ready for Day 1.

What is a smoke test / the "green light"?

A smoke test is the simplest "does it turn on?" check — it doesn't test everything, it confirms the basics work before you build on top of them. In this kit the smoke test runs with pytest. Green means every tool you set up is talking to the others.

Task
  1. Clone the course kit repository, then move into it.

    Why: this downloads the kit you'll build on all week. Use the repository address your instructor gives you in place of the placeholder below — it lives on your company's GitHub Enterprise, the same one you authenticated to in Cycle 2.

    Terminal 
    git clone https://[course repo URL]
cd claudecourse

    Replace [course repo URL] with the real address. The folder name after cd may differ slightly — use whatever the clone creates.

  2. Run the kit's bootstrap (setup) script.

    Why: one script does the whole Cycle 3 dance for you — it creates the kit's own virtual environment (a .venv folder), installs its packages, creates a .env, and runs the checks. On Windows it will even install any missing tools. Run the line for your system from inside the kit folder.

    Terminal · Mac 
    bash scripts/bootstrap.sh
    Terminal · Windows (PowerShell) 
    powershell -ExecutionPolicy Bypass -File scripts\bootstrap.ps1

    The first run creates an empty .env and stops to ask for your key. Open that .env, paste the ANTHROPIC_API_KEY from Cycle 4 (same habit — this is the kit's own .env, already git-ignored), then run the script again to finish the checks.

  3. Run the smoke test yourself and confirm it passes.

    Why: this is your finish line, and pytest is the command you'll run all week to check your work. Step into the kit's venv, then run the free, offline subset.

    Terminal · Mac 
    source .venv/bin/activate
pytest -m "not api"
    Terminal · Windows (PowerShell) 
    .venv\Scripts\activate
pytest -m "not api"
    pytest -m "not api" .............s..................sssssss. [100%] 32 passed, 11 skipped, 1 deselected in 0.51s

    Expect a line like 33 passed, 11 skipped. The offline command above deselects the one live-API test, so it reads 32 passed, 11 skipped, 1 deselected; the full green light (plain pytest) adds that one live call to Claude and shows 33 passed, 11 skipped. The skipped lines are the parts of the system you'll build during the week — on a fresh clone they're meant to skip.

    Stuck? — common smoke-test issues

    "command not found: pytest"? Your venv isn't active — you should see (.venv) at the front of your prompt. Re-run the activate line above.

    A "[warn] Node/npm not found" message during bootstrap? That's fine — Node is only used to install the Claude Code CLI, which you already have from Cycle 4. The Python checks don't need it.

    "permission denied" running the script? Running it with bash in front (as shown) sidesteps that. If errors remain, have Claude Code read the message with you, or bring it to office hours.

Checkpoint

You're done with Cycle 5 when the kit is cloned, bootstrap has run, and pytest -m "not api" comes back green — all passes and skips, no failures. That green light is the whole point of pre-work.
