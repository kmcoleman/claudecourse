Module 1 · The Ledger

Who has access to what?

It's Monday at Meridian Regional Energy. A regulator has asked a question that should be simple: show us everyone who can approve a vendor payment. Nobody can answer it — not because the access doesn't exist, but because it's scattered across several systems that have never spoken to each other.

That's your job this week. Today you lay the foundation: a single, trustworthy record of who holds what access across Meridian. Everything you build the rest of the week sits on top of it.

What you'll build today

A Ledger — one unified table that reconciles Meridian's HR roster against the entitlements export — every account and the app-roles it holds — into a single view of every person and the access they hold, plus a first automated finding that flags a risky access pattern.

What you'll learn

  • Why access data is fragmented across systems, and what identity reconciliation means
  • How to load and inspect raw data with pandas — no prior coding required
  • How to direct Claude Code to write a reconciliation function for you
  • The difference between rule-based and agent-based triage
  • How to produce a structured findings.json that later modules consume

Before you start

Cycle 1

Load the raw data

≈ 30–45 min
Concept

Meridian's access story for the quarter lives in data/2026-Q3/. Before you can answer the regulator — who can approve a vendor payment? — you have to get that story into a place you can actually query. Today's first move is the humblest one all week: load two files and look hard at what's really inside them.

Two exports carry the identity picture, each from a system that was never designed to talk to the other:

  • hr_roster.csv knows people. One row per employee: an employee_id, legal full_name, work email, department, title, hire_date, term_date, employment_type (FTE or Contractor), and status (active, terminated, on leave).
  • entitlements.csv knows access. One row per grant: which account_id / account_name holds which role inside which app (Atlas ERP, Active Directory, Gateway, and nineteen others), when it was granted_date, by whom (granted_by), and when the account last_login.
What is pandas — and a DataFrame?

pandas is a Python library for working with tables of data — think of it as a spreadsheet you drive with code instead of a mouse. It loads a CSV (comma-separated values — a plain-text table, one line per row, commas between columns) into a DataFrame: a table with named columns you can inspect, count, filter, and join. You won't write much pandas by hand; Claude Code will, and your job is to read its work and check the numbers it reports.

Why these two files don't simply line up. HR keys every person on employee_id. The entitlements export has never heard of that ID — it identifies accounts by an account_id like A000544 and an account_name like jeanette.petty, with no column pointing back to HR. To get from "a pile of grants" to "this human holds these roles," you'll eventually have to match accounts to people using the only thing the two files share — a name, buried in an email on one side and a firstname.lastname handle on the other. That job is called identity reconciliation, and it's Cycle 2's work. Cycle 1's job is to earn the right to attempt it: know exactly what each file contains, and find where the data is dirty.

And the data is dirty — on purpose, the way real exports always are. Three messes matter, and you'll measure all three yourself today:

  • Two date formats in one column. Roughly half of granted_date is ISO (2026-08-08); the other half is US (05/31/2026). Same column, two formats — because two upstream systems fed the export and nobody normalized it. Sort or compare those dates naïvely and you'll get nonsense.
  • Department names that drift. hr_roster.csv spells the same department several ways: Customer Care, CUSTOMER CARE, customer care, and  Customer Care  (with stray leading/trailing spaces) are all one department. Group by the raw string and you'll invent departments that don't exist.
  • Duplicate grant rows. A few entitlement rows are exact copies. Worse, some duplicates hide: the same grant appears twice with its date written in each format, so an exact-match check won't catch them.

None of this is exotic — it is what every real access export looks like. Spotting and counting it now is what keeps every number you report later in the week honest.

    Why: every finding you produce this week inherits the quality of this data. Before you trust a single row, you confirm both files loaded, learn their exact shape, and measure the three messes with your own eyes.

    What you're building. A short exploration — a script, or a live Python session — that loads hr_roster.csv and entitlements.csv into DataFrames and answers a handful of questions about each: how many rows and columns, what the columns are called, and how bad the three messes really are. You are not cleaning anything yet — just looking, and writing down what you see.

    What the data looks like. The columns are listed in the Concept above. What you can't see until you load it are the messes — here is exactly what each one looks like in the file, so you know what you're counting:

    granted_date one column, two date formats 2026-08-08 <- ISO, YYYY-MM-DD 05/31/2026 <- US, MM/DD/YYYY department one department, four spellings 'Customer Care' ' Customer Care ' 'CUSTOMER CARE' 'customer care' entitlements a duplicate hiding behind the format split A000025 kara.morgan Box Member 07/21/2026 <- same grant, A000025 kara.morgan Box Member 2026-07-21 <- recorded twice

    How you'll know you got it right. Both files load without error and their shape matches exactly (the shipped kit is seed-locked, so your numbers are not "approximately" these — they are these):

    python explore.py hr_roster (1190, 9) employee_id, full_name, email, department, title, hire_date, term_date, employment_type, status entitlements (15111, 7) account_id, account_name, app, role, granted_date, granted_by, last_login

    Then the three messes, and a couple of distributions, should measure out to these — verify each one against your own output:

    • 22 distinct apps in entitlements — from Active Directory (1,210 grants) down to Procure (15). Atlas ERP, the accounting system, has just 63.
    • granted_date splits into two formats: about 7,486 rows ISO (YYYY-MM-DD) and 7,625 rows US (MM/DD/YYYY) — 15,111 in total, roughly half and half.
    • department shows 31 distinct spellings that collapse to 12 real departments once you strip surrounding spaces and lowercase. (Customer Care alone accounts for four of those spellings.)
    • entitlements has 7 exact-duplicate rows (df.duplicated().sum()) — plus more that hide behind the date-format split and won't show up in an exact-match count.

    Suggested workflow. Work with Claude Code by describing what you want to know, not the code to get it. A reasonable path: ask it to load both CSVs from data/2026-Q3/ and report each file's shape and column names; then ask it to count the distinct apps, break granted_date down by format, count the distinct department spellings (and how many survive stripping and lowercasing), and count exact-duplicate entitlement rows. Read every number it reports against the targets above. When one doesn't match, that is the next thing to dig into with Claude Code — not a reason to move on.

    Stuck?

    FileNotFoundError? You're probably not in the repository root, or the path is off. Confirm data/2026-Q3/hr_roster.csv exists from where you're running, and that you typed the quarter folder exactly.

    ModuleNotFoundError: No module named 'pandas'? The venv isn't active, or pandas landed in a different Python. Re-run Step 1, then check that which python points inside this project's venv/ before you install again.

    The whole file reads as a single column, or the header looks wrong? Something upstream of pandas is off — an unexpected delimiter or a stray first line. Show Claude Code the first few raw lines of the file and ask why the parse produced one column instead of the expected columns.

    Your counts are off by a little? The kit is seed-locked, so exact matches are expected. A mismatch usually means the mess itself — e.g. counting department spellings after stripping spaces gives 12, but before stripping gives 31. Make sure you're measuring the raw column when the target says "spellings."

    Dates won't sort or compare? That's the two-format mess, working as intended. Don't fix it here — just measure how many rows are in each format. Turning those strings into real dates comes later.

Cycle 2

Reconcile identities

≈ 60–75 min
Concept

Now you connect the three tables into one. This is a join: matching rows from different tables that describe the same thing. The trouble is deciding what "the same" means when the systems disagree.

Usernames feel like the obvious key — but they aren't unique or stable. People get renamed after marriage, hold a second admin account, or inherit a username a former employee once used. If you join on username alone, you'll merge two people or split one person in two.

The fix is a canonical identity: one durable ID per real human that every system's record points back to. Building that mapping — and being honest about the rows you can't confidently match — is the heart of reconciliation.

Task
  1. Ask Claude Code to write a reconciliation function.

    Why: you describe the matching logic in plain English; Claude Code turns it into code you can run and inspect.

    Claude Code prompt 
    Write a function reconcile_identities() that merges the
entitlements accounts onto the HR roster to build one ledger.
The entitlements rows have no employee_id, so match each account
to a person by name (account_name is firstname.lastname; HR has
the full name and email). Assign each matched person a
canonical_id. Keep accounts you can't confidently match in a
separate list so we can review them — don't silently drop them.
    Stuck?

    If Claude Code's first attempt drops unmatched rows or crashes on missing values, tell it exactly what you saw: "some entitlement accounts don't match any HR name and the function errored — handle those as unmatched instead of failing."

  2. Run the reconciliation and look at the summary.

    Why: you need to know how many identities matched cleanly and how many need a human eye before you trust the ledger.

    Terminal 
    python reconcile.py
    python reconcile.py Canonical identities: 1198 Matched account records: 1451 Unmatched (needs review): 36 Ledger written to: ledger.csv
  3. Spot-check the results.

    Why: reconciliation is a judgment call, not a guarantee. Pick a few people and confirm the merge looks right — and look at what landed in the unmatched list.

    Claude Code prompt 
    Pick a person in the ledger and show me all their entitlement
rows — is every app-role they hold linked to the same
canonical_id? Then show me three accounts that didn't match any
HR person, and tell me why each one failed to match.
  4. Commit your progress.
    Terminal 
    git add .
git commit -m "Reconcile identities into a unified ledger"
Checkpoint

You're done with Cycle 2 when ledger.csv exists, every matched account carries a canonical_id, unmatched rows are set aside for review rather than dropped, and your spot-check confirms one person's app-roles all rolled up under a single canonical identity.

Cycle 3

Triage entitlements

≈ 60–90 min
Concept

A ledger tells you who has what. Triage is the next question: which of those access grants deserve a closer look? You can't hand a reviewer 15,000 rows and say "check these" — you surface the ones that break a rule.

Start with rule-based triage: precise, explainable conditions like "an Admin role held by someone who isn't a manager." Rules are fast, cheap, and easy to defend to an auditor. Later this week you'll layer on agent-based triage, where Claude reasons about context a fixed rule can't capture. Rules first, judgment second — that order keeps your findings trustworthy.

Every finding you generate lands in a structured file, findings.json, that later modules read. A preview of one finding:

What is JSON?

JSON is a plain-text format for structured data — labeled fields inside curly braces. It's how programs pass records to each other. You'll read it easily; each finding is just a set of named fields describing one flagged access grant.

findings.json (preview) 
{
  "finding_id": "F-0001",
  "rule": "admin-role-non-manager",
  "canonical_id": "MRE-00317",
  "person": "marcus.pipeline",
  "app": "Atlas ERP",
  "role": "ERP Admin",
  "reason": "Holds ERP Admin but is not a people manager in HR",
  "severity": "high",
  "status": "open"
}
Task
  1. Ask Claude Code to write the triage rule.

    Why: this is your first automated control — it encodes a policy ("admins should be managers") as a check that runs against every row.

    Claude Code prompt 
    Write a rule that flags every ledger entry where a person holds
an "Admin" role but is not a manager in the HR data. For each
flagged entry, produce a finding with: finding_id, rule,
canonical_id, person, app, role, reason, severity, status.
  2. Run the rule against your reconciled ledger.

    Why: this turns the rule into actual findings you can count and read.

    Terminal 
    python triage.py
    python triage.py Scanned ledger rows: 15234 Rule: admin-role-non-manager Findings generated: 9 Wrote findings.json
    Stuck?

    Zero findings? Either the data genuinely has none, or the rule isn't reading the manager field correctly. Ask Claude Code to print a few Admin-role rows and show whether it thinks each person is a manager — that reveals which side is wrong.

  3. Open findings.json and confirm it's well-formed.

    Why: later modules depend on this exact structure, so it's worth a 30-second look now.

    Claude Code prompt 
    Show me findings.json and confirm every finding has all nine
required fields. Flag any that are missing something.
  4. Commit your progress.
    Terminal 
    git add .
git commit -m "Add admin-role-non-manager triage rule and findings"
Checkpoint

You're done with Cycle 3 when findings.json exists, contains at least one finding from the admin-role-non-manager rule, and every finding carries all nine fields shown in the preview above.
