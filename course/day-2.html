Module 1 · The Ledger

Who has access to what?

It's Monday at Meridian Regional Energy. A regulator has asked a question that should be simple: show us everyone who can approve a vendor payment. Nobody can answer it — not because the access doesn't exist, but because it's scattered across three systems that have never spoken to each other.

That's your job this week. Today you lay the foundation: a single, trustworthy record of who holds what access across Meridian. Everything you build the rest of the week sits on top of it.

What you'll build today

A Ledger — one unified table that reconciles Meridian's HR roster, Active Directory accounts, and application entitlements into a single view of every person and the access they hold, plus a first automated finding that flags a risky access pattern.

What you'll learn

  • Why access data is fragmented across systems, and what identity reconciliation means
  • How to load and inspect raw data with pandas — no prior coding required
  • How to direct Claude Code to write a reconciliation function for you
  • The difference between rule-based and agent-based triage
  • How to produce a structured findings.json that later modules consume

Before you start

  • Day 1 complete — your environment is set up and Claude Code runs
  • The meridian-capstone repository is cloned to your machine
  • Your virtual environment (venv) is activated (you'll confirm this in Step 1)

Cycle 1

Load the raw data

≈ 30–45 min
Concept

Meridian's access story lives in three files, each exported from a different system that was never designed to talk to the others:

HR roster knows people — legal names, job titles, managers, departments. Active Directory knows accounts — usernames, groups, when someone last logged in. Application entitlements knows permissions — which account can do what inside each business app.

They don't line up. HR lists a Finance & Accounting employee by her full legal name and title. Active Directory knows that same person under two usernames — an everyday login and a second _adm admin account left over from an old project. Atlas ERP just sees a user ID. Pulling these into one view is called identity reconciliation — deciding, with evidence, that these fragments are all the same human being.

What is pandas?

pandas is a Python library for working with tables of data — think of it as a spreadsheet you drive with code instead of a mouse. It loads a CSV into a DataFrame (a table with named columns) so you can inspect, filter, and join data. You won't write much of it by hand; Claude Code will, and you'll read and check its work.

Task

    Why: the venv keeps this project's tools separate from the rest of your computer, so nothing you install here breaks anything else.

    What is a venv?

    A "virtual environment" is a private sandbox for one project's Python packages. When it's active, your terminal prompt usually shows (venv) at the start of the line.

    Terminal

    A CSV ("comma-separated values") is a plain-text table — the simplest way to export data from almost any system. Each line is a row; commas separate the columns.

Cycle 2

Reconcile identities

≈ 60–75 min
Concept

Now you connect the three tables into one. This is a join: matching rows from different tables that describe the same thing. The trouble is deciding what "the same" means when the systems disagree.

Usernames feel like the obvious key — but they aren't unique or stable. People get renamed after marriage, hold a second admin account, or inherit a username a former employee once used. If you join on username alone, you'll merge two people or split one person in two.

The fix is a canonical identity: one durable ID per real human that every system's record points back to. Building that mapping — and being honest about the rows you can't confidently match — is the heart of reconciliation.

Task
  1. Ask Claude Code to write a reconciliation function.

    Why: you describe the matching logic in plain English; Claude Code turns it into code you can run and inspect.

    Claude Code prompt 
    Write a function reconcile_identities() that merges the three
DataFrames into one ledger. Match on employee_id where available;
fall back to name matching for AD and app records that lack it.
Assign each matched person a canonical_id. Keep unmatched rows in
a separate list so we can review them — don't silently drop them.
    Stuck?

    If Claude Code's first attempt drops unmatched rows or crashes on missing values, tell it exactly what you saw: "some AD accounts have no employee_id and the function errored — handle those as unmatched instead of failing."

  2. Run the reconciliation and look at the summary.

    Why: you need to know how many identities matched cleanly and how many need a human eye before you trust the ledger.

    Terminal 
    python reconcile.py
    python reconcile.py Canonical identities: 1198 Matched account records: 1451 Unmatched (needs review): 36 Ledger written to: ledger.csv
  3. Spot-check the results.

    Why: reconciliation is a judgment call, not a guarantee. Pick a few people and confirm the merge looks right — especially anyone with a second _adm account.

    Claude Code prompt 
    Pick a person in the ledger who has a second _adm admin account.
Show me their ledger rows — are both accounts (their standard
login and their _adm account) linked to the same canonical_id?
  4. Commit your progress.
    Terminal 
    git add .
git commit -m "Reconcile identities into a unified ledger"
Checkpoint

You're done with Cycle 2 when ledger.csv exists, every matched account carries a canonical_id, unmatched rows are set aside for review rather than dropped, and your spot-check confirms a known dual-account person merged correctly.

Cycle 3

Triage entitlements

≈ 60–90 min
Concept

A ledger tells you who has what. Triage is the next question: which of those access grants deserve a closer look? You can't hand a reviewer 15,000 rows and say "check these" — you surface the ones that break a rule.

Start with rule-based triage: precise, explainable conditions like "an Admin role held by someone who isn't a manager." Rules are fast, cheap, and easy to defend to an auditor. Later this week you'll layer on agent-based triage, where Claude reasons about context a fixed rule can't capture. Rules first, judgment second — that order keeps your findings trustworthy.

Every finding you generate lands in a structured file, findings.json, that later modules read. A preview of one finding:

What is JSON?

JSON is a plain-text format for structured data — labeled fields inside curly braces. It's how programs pass records to each other. You'll read it easily; each finding is just a set of named fields describing one flagged access grant.

findings.json (preview) 
{
  "finding_id": "F-0001",
  "rule": "admin-role-non-manager",
  "canonical_id": "MRE-00317",
  "person": "marcus.pipeline",
  "app": "Atlas ERP",
  "role": "ERP Admin",
  "reason": "Holds ERP Admin but is not a people manager in HR",
  "severity": "high",
  "status": "open"
}
Task
  1. Ask Claude Code to write the triage rule.

    Why: this is your first automated control — it encodes a policy ("admins should be managers") as a check that runs against every row.

    Claude Code prompt 
    Write a rule that flags every ledger entry where a person holds
an "Admin" role but is not a manager in the HR data. For each
flagged entry, produce a finding with: finding_id, rule,
canonical_id, person, app, role, reason, severity, status.
  2. Run the rule against your reconciled ledger.

    Why: this turns the rule into actual findings you can count and read.

    Terminal 
    python triage.py
    python triage.py Scanned ledger rows: 15234 Rule: admin-role-non-manager Findings generated: 9 Wrote findings.json
    Stuck?

    Zero findings? Either the data genuinely has none, or the rule isn't reading the manager field correctly. Ask Claude Code to print a few Admin-role rows and show whether it thinks each person is a manager — that reveals which side is wrong.

  3. Open findings.json and confirm it's well-formed.

    Why: later modules depend on this exact structure, so it's worth a 30-second look now.

    Claude Code prompt 
    Show me findings.json and confirm every finding has all nine
required fields. Flag any that are missing something.
  4. Commit your progress.
    Terminal 
    git add .
git commit -m "Add admin-role-non-manager triage rule and findings"
Checkpoint

You're done with Cycle 3 when findings.json exists, contains at least one finding from the admin-role-non-manager rule, and every finding carries all nine fields shown in the preview above.
