Module 1 · The Ledger

Who has access to what?

It's Monday at Meridian Regional Energy. A regulator has asked a question that should be simple: show us everyone who can approve a vendor payment. Nobody can answer it — not because the access doesn't exist, but because it's scattered across several systems that have never spoken to each other.

That's your job this week. Today you lay the foundation: a single, trustworthy record of who holds what access across Meridian. Everything you build the rest of the week sits on top of it.

What you'll build today

A Ledger — one unified table that reconciles Meridian's HR roster against the entitlements export — every account and the app-roles it holds — into a single view of every person and the access they hold, plus a first automated finding that flags a risky access pattern.

What you'll learn

  • Why access data is fragmented across systems, and what identity reconciliation means
  • How to load and inspect raw data with pandas — no prior coding required
  • How to direct Claude Code to write a reconciliation function for you
  • The difference between rule-based and agent-based triage
  • How to produce a structured findings.json that later modules consume

Cycle 1

Load the raw data

≈ 30–45 min
Concept

Meridian's access story for the quarter lives in data/2026-Q3/. Before you can answer the regulator — who can approve a vendor payment? — you have to get that story into a place you can actually query. Today's first move is the humblest one all week: load two files and look hard at what's really inside them.

Two exports carry the identity picture, each from a system that was never designed to talk to the other:

  • hr_roster.csv knows people. One row per employee: an employee_id, legal full_name, work email, department, title, hire_date, term_date, employment_type (FTE or Contractor), and status (active, terminated, on leave).
  • entitlements.csv knows access. One row per grant: which account_id / account_name holds which role inside which app (Atlas ERP, Active Directory, Gateway, and nineteen others), when it was granted_date, by whom (granted_by), and when the account last_login.
What is pandas — and a DataFrame?

pandas is a Python library for working with tables of data — think of it as a spreadsheet you drive with code instead of a mouse. It loads a CSV (comma-separated values — a plain-text table, one line per row, commas between columns) into a DataFrame: a table with named columns you can inspect, count, filter, and join. You won't write much pandas by hand; Claude Code will, and your job is to read its work and check the numbers it reports.

Why these two files don't simply line up. HR keys every person on employee_id. The entitlements export has never heard of that ID — it identifies accounts by an account_id like A000544 and an account_name like jeanette.petty, with no column pointing back to HR. To get from "a pile of grants" to "this human holds these roles," you'll eventually have to match accounts to people using the only thing the two files share — a name, buried in an email on one side and a firstname.lastname handle on the other. That job is called identity reconciliation, and it's Cycle 2's work. Cycle 1's job is to earn the right to attempt it: know exactly what each file contains, and find where the data is dirty.

And the data is dirty — on purpose, the way real exports always are. Three messes matter, and you'll measure all three yourself today:

  • Two date formats in one column. Roughly half of granted_date is ISO (2026-08-08); the other half is US (05/31/2026). Same column, two formats — because two upstream systems fed the export and nobody normalized it. Sort or compare those dates naïvely and you'll get nonsense.
  • Department names that drift. hr_roster.csv spells the same department several ways: Customer Care, CUSTOMER CARE, customer care, and  Customer Care  (with stray leading/trailing spaces) are all one department. Group by the raw string and you'll invent departments that don't exist.
  • Duplicate grant rows. A few entitlement rows are exact copies. Worse, some duplicates hide: the same grant appears twice with its date written in each format, so an exact-match check won't catch them.

None of this is exotic — it is what every real access export looks like. Spotting and counting it now is what keeps every number you report later in the week honest.

Cycle 2

Reconcile identities

≈ 60–75 min
Concept

Cycle 1 left you with two files that describe the same organisation and share no key. Reconciliation is the work of building the missing link: deciding, row by row, which account belongs to which human — and being honest about the ones you can't decide.

There is no shared key, only a name. HR identifies people by employee_id (E00251). Entitlements identifies accounts by account_id (A000251) and account_name (michelle.mercado). Nothing in either file points at the other. The only bridge is a human name — spelled Michelle Mercado on the HR side and michelle.mercado on the access side. So your matching key has to be derived: lowercase the HR name, drop punctuation, join the parts with a dot, and compare. That derivation is where all the trouble lives.

What is a join — and a canonical identity?

A join matches rows from two tables that describe the same thing. A canonical identity is the answer the join produces: one durable ID per real human that every system's record points back to. Here the canonical ID is HR's employee_id — HR is the system of record for "who is a person at Meridian," so every account you can confidently place gets stamped with one.

Why a name is a bad key. Meridian has 1,200 accounts but only 1,188 distinct account_names, and 1,190 HR people with only 1,180 distinct names. Both sides collide. Eleven account_names are shared by more than one account, and they are not all the same problem — they fall into three kinds, and each wants a different answer:

  • Two humans, one name. jacob.miller is two accounts and two different employees. A name-based join cannot tell you which is which. Guessing merges two people; picking the first match silently assigns one person's access to another. The correct output is ambiguous.
  • One human, two accounts. james.hernandez is two accounts and exactly one employee — a second account nobody cleaned up. Both should resolve to the same person. (Hold onto this one; it comes back in Cycle 3.)
  • Not a human at all. marcus.pipeline (three accounts) and emergency.admin (two) are service accounts — automation and break-glass logins with no employee behind them. The kit ships the known list in data/2026-Q3/service_accounts.json. Forcing these onto a person is worse than leaving them unresolved.

So a reconciliation that reports one number — "matched" — is hiding the interesting part. Yours should report at least four outcomes: matched, ambiguous, unmatched, and service. An auditor can work with an honest "we could not determine this." They cannot work with a confident wrong answer.

And the order of operations matters more than the code. Cycle 1 found 7 exact-duplicate rows in entitlements.csv. That number is a lie of omission. There are really 30 duplicated grants — but 23 of them were recorded twice with the date written in a different format each time, so the rows aren't byte-identical and an exact-match check walks straight past them. Normalise granted_date first and all 30 become visible. De-duplicate first and 23 survive into your ledger forever, quietly inflating every count you report for the rest of the week. Same two operations, opposite results:

de-duplicate, then normalise dates -> 15,104 rows (23 twins survived) normalise dates, then de-duplicate -> 15,081 rows (correct)

This is the single easiest thing to get wrong today, and nothing downstream will warn you. Get the order right and the rest of Cycle 2 is bookkeeping.

Task
  1. Build the canonical identity table.

    Why: this is the bridge the two exports never had. Every count, every finding, every report for the rest of the week resolves through this one table.

    What you're building. A reconciliation function, and the file it writes: identities.csv at the repository root, one row per account_id — all 1,200 of them, including the ones you can't place. Each row records the account, the name it was recorded under, the employee_id you resolved it to (blank when you couldn't), how you resolved it, and a match_status of matched, ambiguous, unmatched, or service. The rule that matters: no account may be dropped. An account you can't place is a row with an empty employee_id, never a row that vanished.

    What the data looks like. The join key has to be derived from HR's full_name, and the three collision archetypes from the Concept are the cases that decide whether your function is honest:

    deriving the key HR full_name -> matching key 'Michelle Mercado' -> michelle.mercado matches A000251 the three collisions jacob.miller 2 accounts, 2 different employees -> ambiguous james.hernandez 2 accounts, 1 employee -> both -> E00023 marcus.pipeline 3 accounts, no employee -> service names that never match on the dot pattern jwilliams philiph sstokes <- initials, not firstname.lastname jill.smith jacob.hall <- nickname or a name HR spells differently

    How you'll know you got it right. Every one of these is exact — the export is seed-locked. Check each against your own output:

    • identities.csv has exactly 1,200 rows, one per account_id, and the set of IDs equals the set in entitlements.csv. If you have fewer, you dropped accounts.
    • Matching on the derived firstname.lastname key alone resolves 1,055 accounts, leaves 18 ambiguous (10 shared names), 122 unmatched, and 5 service accounts — 1,200 in total. 1,055 is your floor, not your ceiling: a smarter matcher may resolve more, but never by guessing at an ambiguous name.
    • Every non-blank employee_id you write actually exists in hr_roster.csv. A resolved ID that HR has never heard of means your key derivation is producing garbage.
    • Exactly one employee ends up holding two accounts — E00023, both named james.hernandez. If dozens of employees hold multiple accounts, you're matching too loosely.
    • The 5 service accounts (marcus.pipeline ×3, emergency.admin ×2) carry no employee_id.
    • A000409 and A000648 are both jacob.miller and must not end up with the same employee_id.

    Suggested workflow. Describe the outcome to Claude Code, not the algorithm: the two files, the fact that they share no key, the four statuses you want, and the hard rule that all 1,200 accounts survive to the output. Then read the summary it prints against the numbers above. When a count is off, hand it the specific discrepancy — that's the conversation that teaches you what your matcher is actually doing. One caution: you may notice that A000251 and E00251 share their digits. That is an accident of how this export was generated, not a property of Meridian's systems — real exports have no such gift. Matching on it will make these tests pass and teach you nothing, so derive the key from the name.

    Stuck?

    Your row count is under 1,200? An inner join is silently deleting the accounts that don't match. Reconciliation keeps every account and records the failure; it never resolves the problem by discarding it.

    Your row count is over 1,200? The opposite failure: a join on a non-unique key fans out. Ten HR names are shared by two people each, so a plain join emits two rows for those accounts. Detect the multiple-candidate case before you join and mark it ambiguous instead.

    Matched count far above 1,055? Something is matching that shouldn't — usually a fuzzy or partial-string match that maps jill.smith onto any Smith. Ask Claude Code to print twenty matches with the HR name beside the account name and read them yourself; wrong matches are obvious to a human and invisible to a count.

    Matched count far below 1,055? Your key derivation is off. Compare a handful of derived keys against the raw account_name — case, punctuation, and stray whitespace are the usual culprits, and HR names carry the same drift you measured in Cycle 1.

    Not sure whether a name is a person or a robot? Don't guess — data/2026-Q3/service_accounts.json is the shipped list.

  2. Normalise the dates, then de-duplicate, then build the ledger.

    Why: this is the order-of-operations trap from the Concept. Do these three steps in the wrong order and 23 phantom grants live in your ledger for the rest of the week without a single error message.

    What you're building. ledger.csv at the repository root — the file the rest of the course reads. One row per distinct grant: take entitlements.csv, convert every granted_date to ISO YYYY-MM-DD, collapse rows that repeat the same (account_id, app, role), and attach the employee_id and match_status from identities.csv.

    What the data looks like. The pair you met in Cycle 1 is the whole lesson. These are one grant recorded twice, and only the date column disagrees:

    A000025 kara.morgan Box Member 07/21/2026 helpdesk 2026-07-04 A000025 kara.morgan Box Member 2026-07-21 helpdesk 2026-07-04 exact-duplicate rows before normalising granted_date: 7 exact-duplicate rows after normalising granted_date: 30

    How you'll know you got it right.

    • ledger.csv has exactly 15,081 rows. Two wrong answers are worth recognising on sight: 15,111 means you de-duplicated nothing, and 15,104 means you de-duplicated before normalising and 23 format-twins survived.
    • No two rows share an (account_id, app, role).
    • Every granted_date matches YYYY-MM-DD — no slashes left anywhere in the column.
    • A000025 (kara.morgan) holds 14 rows, down from 15, with exactly one Box / Member grant.
    • Every account_id in the ledger appears in identities.csv.
    • Grouped by match_status, the ledger splits 13,307 matched, 1,548 unmatched, 221 ambiguous, 5 service. Those 1,769 unresolved rows are roughly one grant in nine — worth sitting with before you report any number as complete.

    Suggested workflow. Ask for the three steps as three named steps in one function so the order is visible in the code you're reviewing, and ask it to print the row count after each. Watching 15,111 become 15,081 — and seeing exactly where — is the point of the exercise.

    Stuck?

    15,104 rows? The classic. You de-duplicated first. Move the date normalisation above it and re-run.

    Dates came out wrong — some in 2026, some in the future? 05/31/2026 is unambiguous, but 07/21/2026 parsed as day-first becomes an invalid date and parsed inconsistently produces silent nonsense. Convert explicitly with the known format rather than letting a parser guess, and sanity-check the min and max date afterwards.

    Row count grew past 15,111 after attaching identities? The identity join fanned out. identities.csv has one row per account_id by construction — if it doesn't, fix Step 1 before continuing.

    Unsure which duplicate to keep? For this data it doesn't matter — the twins are identical apart from date formatting. Keep the first and move on; note the choice so it's defensible later.

  3. Spot-check the reconciliation by hand.

    Why: the counts can all be right while the matching is wrong. Counts tell you how many; only looking at rows tells you whether the right person got the right access.

    What you're building. Nothing new on disk — a few minutes of reading. Pull up four specific cases and satisfy yourself that each landed the way the Concept says it should.

    How you'll know you got it right.

    • One person, one identity. A000025 resolves to a single employee_id, and all 14 of its grants carry it.
    • Two people, not merged. A000409 and A000648 are both jacob.miller. Neither is confidently assigned to the other's employee, and your table says so out loud.
    • Two accounts, one person. Both james.hernandez accounts resolve to E00023 — and look at that HR row while you're there. It will matter in Cycle 3.
    • The unmatched are explainable. Read ten of the 122. You should be able to say which pattern broke each one — an initials-style handle like jwilliams, or a first name HR spells differently. "I don't know why this failed" on a large share of them means your matcher has a bug, not the data.

    Suggested workflow. Ask Claude Code to print each case as rows you can read, not as a verdict — you are the one checking, and a summary that says "looks correct" is not evidence. When something looks wrong, the useful next question is which side is wrong: the HR row, the account, or your matching rule.

    Stuck?

    Everything looks fine and you're suspicious? Good instinct. Sort the unmatched list alphabetically and skim it. Clusters of similar-looking names usually mean one systematic gap rather than 122 unrelated ones.

Cycle 3

Triage entitlements

≈ 60–90 min
Concept

A ledger tells you who has what. Triage is the next question: which of those 15,081 grants deserve a reviewer's attention? You can't hand someone the whole ledger and say "check this." Triage is the act of narrowing it — applying a stated rule to surface the access that is likely to be a problem, and leaving a trail that explains why.

Rules first, judgment second. You'll start with a rule-based check: a precise, mechanical condition you can write down and an auditor can re-run. Rules are cheap, deterministic, and defensible — asked "why was this flagged," you point at the clause. Later this week you'll add agent-based triage, where Claude weighs context a fixed condition can't express. That order is deliberate. A rule you understand is the thing you'll use to judge whether the agent is right; build the muscle before you add the judgment.

Your first rule: segregation of duties. Meridian's SoD matrix (data/2026-Q3/sod_matrix.json) lists role pairs that no single person should hold. The sharpest one is in Atlas ERP, the accounting system: Vendor Admin creates and edits vendor records; AP Manager approves payments to them. One person holding both can invent a vendor and pay it. The matrix rates that critical, and ACP-4.1 is the clause it violates.

But a rule that fires is not yet a finding. ACP-4.2 grants a standing written exemption: the Controller in Finance & Accounting may hold both roles, because the job requires it and the CFO performs a quarterly manual payment review as a compensating control. The policy is explicit — access held under ACP-4.2 is not a finding. Report a Controller and you've handed your reviewer a false positive, and spent some of the credibility you'll need when a real one lands.

That gap between "the rule fired" and "this is a finding" is the whole reason triage output needs a reviewer judgment layer rather than just a rule. And a suppressed conflict can't simply disappear: a reviewer has to be able to see what you suppressed and on what authority. So today's triage writes two files — the findings, and the exemptions you applied to get there.

What is JSON — and why a fixed schema?

JSON is a plain-text format for structured data — labelled fields inside curly braces, the way programs pass records to each other. Your findings go into findings.json in a shape that is already fixed: the kit ships the contract at src/meridian_capstone/contract/findings.schema.json, and every later module — the reviewer report, the agent, the MCP server — reads that shape. It is strict on purpose. Extra fields are rejected, so if a field you want isn't in the contract, the answer is to express it with the fields that are there.

One finding, in the shape the contract requires:

findings.json (one entry) 
{
  "scope": "account",
  "account_id": "A000251",
  "employee_id": "E00251",
  "app": "Atlas ERP",
  "entitlement": "AP Manager + Vendor Admin",
  "category": "sod_conflict",
  "severity": "critical",
  "recommendation": "revoke",
  "rationale": "Holds both AP Manager and Vendor Admin in Atlas ERP - can
                create a vendor and approve its payment. Senior Accountant,
                not the Controller, so the ACP-4.2 exemption does not apply.",
  "evidence": [
    {"source": "entitlements",
     "detail": "A000251 holds Atlas ERP/AP Manager and Atlas ERP/Vendor Admin"},
    {"source": "hr_roster",
     "detail": "title=Senior Accountant, department=Finance & Accounting"}
  ],
  "policy_citations": ["ACP-4.1"],
  "confidence": 0.95
}

Note what's carrying the weight there. evidence is not decoration — it's the pointer back to the rows that triggered the rule, and a finding a reviewer can't trace is a finding they'll ignore. rationale has to say why the exemption doesn't apply, because that's the first question anyone will ask.

Task
  1. Find the SoD conflicts in the ledger.

    Why: this is your first automated control. Before you worry about output shape or exemptions, get the raw list of accounts the rule fires on — and see how few of 15,081 rows it takes to answer the regulator's question.

    What you're building. A check that reads ledger.csv, groups the Atlas ERP grants by account_id, and reports every account holding both AP Manager and Vendor Admin. No JSON yet, no exemption logic yet — just the accounts, printed, so you can look at them.

    What the data looks like. Atlas ERP is small and that's the point: 63 grants in the whole quarter, across five roles. The conflicting pair is rare on one side and common on the other:

    Atlas ERP 63 grants AP Manager 22 GL Accountant 21 AP Clerk 12 Vendor Admin 5 <- the entire population of the scarce half ERP Admin 3

    How you'll know you got it right.

    • The rule fires on exactly 5 accounts: A000042, A000089, A000168, A000251, A000615.
    • Look at the role counts again once you have that list. There are only 5 Vendor Admin grants in Meridian, and every single one is held by someone who also holds AP Manager. The overlap isn't a handful of stragglers — it's the entire role. Worth noticing before you decide how severe this is.
    • Run it against the raw entitlements.csv instead of your ledger and you get the same 5 — the duplicates don't change this answer. That's luck, not design; a rule that counted grants rather than checking membership would have been wrong. Use the ledger.

    Suggested workflow. Describe the conflict in business terms — create a vendor, approve its payment — and let the code follow. Read the SoD matrix yourself first: it's a small JSON file listing six conflicts, and knowing what else is in there tells you how much of this week's work is already specified.

    Stuck?

    Zero results? Almost always a string mismatch — check the role values in your ledger against the matrix exactly, including capitalisation and spacing. Print the distinct Atlas ERP roles and compare them side by side.

    More than 5? You're probably matching a role by substring, so AP Manager also catches AP Clerk-adjacent text, or you're grouping by account_name rather than account_id — and you know from Cycle 2 that names aren't unique.

    Grouping by employee instead of account? Reasonable instinct, but it changes the answer: one of the five belongs to an employee who also owns a second account. Group by account_id for now — the conflict lives in an account's role set.

  2. Apply the ACP-4.2 exemption and write both output files.

    Why: five hits, but not five findings. This step is where a rule becomes triage — you decide which conflicts a reviewer should see, and you record what you removed so the decision is auditable rather than invisible.

    What you're building. Two files at the repository root. findings.json — an array in the contract shape, holding only the conflicts that survive the exemption. exemptions.json — the ones you suppressed, each naming the account, the clause, and why it applies. The second file is not optional bookkeeping; it's the difference between "we found two problems" and "we found five and cleared three, here's the reasoning."

    What the data looks like. Join each of the five accounts back to its HR row through identities.csv and the picture separates itself:

    A000042 Patrick Ramos Controller Finance & Accounting active A000089 Amanda Garrison Controller Finance & Accounting active A000168 April Tyler Controller Finance & Accounting active A000251 Michelle Mercado Senior Accountant Finance & Accounting active A000615 James Hernandez Ranger/warden FIELD SERVICES terminated

    Three Controllers — exactly the role ACP-4.2 names. Then a Senior Accountant who is close to the exemption but is not it. Then something else entirely: a terminated field-services employee holding payment-approval rights in the accounting system. Two of these are findings, and they are not equally interesting.

    How you'll know you got it right.

    • findings.json exists at the repository root and contains exactly 2 findings — A000251 and A000615.
    • exemptions.json contains exactly 3 — A000042, A000089, A000168 — each citing ACP-4.2.
    • No Controller appears in findings.json. That's the false-positive check, and it's the one this cycle is really about.
    • Both findings use category: "sod_conflict", app: "Atlas ERP", and severity: "critical" — the matrix sets the severity, not your judgment of the individual.
    • Each finding carries at least one evidence entry that names the actual rows behind it, and a rationale that says why ACP-4.2 doesn't apply to this person.
    • Match the exemption on both title and department, and normalise before comparing. A000615's department is recorded as FIELD SERVICES — the same casing drift you measured in Cycle 1, still live, still able to break a comparison.

    Suggested workflow. Write the exemption as a lookup against the matrix's exemptions block rather than as a hardcoded "if Controller" — the clause, the title, and the department are all in the file, and next week's rules will want the same mechanism. Then read both output files yourself before you trust them. And read A000615's HR row properly: this account belongs to the same james.hernandez collision you untangled in Cycle 2, it is a second account for an employee who left, and it holds payment approval in a system their job never touched. It is the most serious thing in today's data, and you only see it because the reconciliation was honest about which account belonged to whom.

    Stuck?

    All five landed in findings.json? The exemption never matched. Print the title and department your code is comparing against the clause's values — nine times in ten it's whitespace or casing on one side.

    Four findings, or one? The exemption is matching too broadly or too narrowly. It requires both title = Controller and department = Finance & Accounting; department alone would clear Michelle Mercado, who is not exempt.

    An account has no HR row to check? Then it can't be exempt — the exemption is defined on a title and a department, and you have neither. Report it and say so in the rationale. Unknown is not the same as cleared.

    Tempted to add a field the contract doesn't have? That's the right instinct meeting a strict schema. The exemption belongs in exemptions.json; inside a finding, use policy_citations and rationale to carry the reasoning.

  3. Validate findings.json against the contract.

    Why: everything downstream this week reads this file. A shape error caught now costs a minute; caught on Day 4 it costs an afternoon of debugging something that isn't actually broken.

    What you're building. A validation run — your findings.json checked against src/meridian_capstone/contract/findings.schema.json, either as a couple of lines with the jsonschema package (already a kit dependency) or as a check you fold into your triage script.

    How you'll know you got it right.

    • Validation passes with no errors.
    • Every finding carries all twelve required fields — none of them empty placeholders. evidence must have at least one entry.
    • The enum fields hold legal values: category is sod_conflict, severity is critical, recommendation is one of revoke / review / retain, scope is account.
    • No extra fields. The schema sets additionalProperties: false, so a stray finding_id or exemption_flag is a hard failure — deliberately, so that every consumer this week can rely on the shape.
    • Because scope is account, account_id must be a real string, not null.

    Suggested workflow. Read the schema file before you validate against it — it's short, and reading it tells you more about what the rest of the course expects than any error message will. examples/sample_findings.json in the kit is a known-valid reference if you want to compare a working entry against yours.

    Stuck?

    ValidationError mentioning additional properties? You've added a field the contract doesn't define. Remove it and move the information into rationale, evidence, or policy_citations.

    Complaining about the top level? The contract describes an array of findings. A single object, or an object wrapping the list under a key, will fail — even with two findings, the file starts with [.

    ModuleNotFoundError: jsonschema? It's declared in the kit's dependencies, so this usually means the venv isn't active or the kit was never installed. Re-activate and re-run the install from the repository root.
