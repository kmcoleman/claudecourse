Concept

To test transfer honestly, you need a client that's genuinely different from Meridian — not Meridian with the names changed. The kit's seed generator builds one: Northwind Biotech, with its own app names, its own role vocabulary, and policy language written differently from Meridian's.

Meet two people at Northwind. And Dana Osei, a Research Analyst whose privileged lab-inventory access hasn't been touched in months — a dormancy case your Day 3 Skill should still catch, if it truly generalized.

Hardcoded vs. parameterized

Something is hardcoded when a specific value is baked directly into your code — "the payments app is called trial-payments." It's parameterized when the value lives in config and the code reads it — "the payments app is whatever config.payments_app says." Hardcoded works for one client; parameterized travels to the next.

Cycle 2

Point the pipeline at Northwind

≈ 90 min
Concept

Now run yesterday's pipeline — unchanged — against Northwind and watch what happens. Two kinds of failure show up here, and the second is more dangerous than the first.

A crash is honest: the code errors because it looked for trial-payments and there isn't one. A wrong answer is quiet: the code runs clean but produces findings that are subtly incorrect, because a Meridian assumption held somewhere you didn't notice. Today you learn to distrust a green run until you've checked that it's actually right.

Task
  1. Run the pipeline against Northwind, unchanged.

    Why: this is the honest transfer test — same code, new client, no edits yet.

    Claude Code prompt 
    Run run_review(export_dir='data/northwind-Q1') with no code
changes. Show me exactly what happens — errors, or findings.
    run_review(export_dir='data/northwind-Q1') KeyError: 'trial-payments' (policy-applier, sod Skill) ... pipeline halted
  2. Diagnose the crash.

    Why: the first error names one hardcoded assumption. Find out which value was baked in and where.

    Claude Code prompt 
    Trace this KeyError. Which Meridian-specific value is hardcoded,
in which file, and why does Northwind not have it?
  3. Hunt for the quiet wrong answers, not just the crash.

    Why: fixing the crash won't be enough if other assumptions produce wrong findings silently. Get ahead of them now.

    Claude Code prompt 
    Beyond this crash, scan the pipeline for other Meridian-specific
assumptions — app names, role labels, column names, thresholds —
that would produce wrong findings for Northwind without erroring.
    Stuck?

    Not sure a finding is wrong? Check it against a case you seeded — Marcus Webb should surface as an SoD violation and Dana Osei as dormancy. If either is missing or mislabeled, an assumption is still baked in.

  4. Commit your diagnosis notes.

    Why: commit the list of assumptions before you start changing code, so you have a clean record of what needed fixing.

    Terminal 
    git add .
git commit -m "Diagnose Meridian-specific assumptions blocking transfer"
Checkpoint

You're done with Cycle 2 when you've run the pipeline against Northwind, found the first crash, and produced a written list of every Meridian assumption — loud and quiet — that needs to come out.

Cycle 3

Fix the assumptions

≈ 90 min
Concept

Now do the actual generalizing. Each assumption on your list comes out of the code and moves into a small config file — one place that says "for this client, the payments app is X, the privileged roles are Y, the dormancy window is Z." The code stops naming Meridian and starts reading the config it's pointed at.

config/northwind.yaml (target shape) 
company: Northwind Biotech
payments_app: supplier-payments
privileged_roles: [lab-admin, grant-approver]
dormancy_days: 120
id_columns: {roster: employee_no, ad: sam_account}
Task
  1. Extract the hardcoded values into a config file.

    Why: this is the core move of the day — every Meridian-specific value becomes a config entry the code reads instead of a literal it assumes.

    Claude Code prompt 
    Pull every hardcoded Meridian value we found into a config file.
Create config/meridian.yaml and config/northwind.yaml, and change
the code to read from a config instead of naming values directly.
  2. Make the Skills read client vocabulary from config too.

    Why: a Skill that hardcodes "trial-payments" won't transfer. The policy logic should stay; only the client-specific nouns should come from config.

    Claude Code prompt 
    Update the SoD, privileged-access, and dormancy Skills so they
refer to the payments app, privileged roles, and dormancy window
by config, not by Meridian's specific names.
  3. Re-run against Northwind with its config.

    Why: point the same code at Northwind's config and see whether the fixes hold — no crash, and the seeded cases surfacing correctly.

    Claude Code prompt 
    Run run_review(export_dir='data/northwind-Q1') using
config/northwind.yaml. Confirm Marcus Webb shows as an SoD
violation and Dana Osei as dormancy.
    run_review(export_dir='data/northwind-Q1') findings: 173 high: 28 medium: 97 low: 48 Marcus Webb → SoD Skill, §2.3 (high) Dana Osei → Dormancy Skill, §1.2 (medium) pipeline OK
    Stuck?

    Still one assumption left? If a seeded case is still missing, one value didn't make it into config. Ask Claude: "which remaining literal is stopping Marcus Webb from being flagged?" and move that one too.

  4. Commit the generalized pipeline.
    Terminal 
    git add .
git commit -m "Extract client specifics into config; pipeline runs on Northwind"
Checkpoint

You're done with Cycle 3 when the Meridian-specific values live in config, the pipeline runs against Northwind without code edits, and your two seeded cases — Marcus Webb and Dana Osei — are correctly flagged.
