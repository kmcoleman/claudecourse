Module 6 · Generalization

Prove it transfers.

Your Q3 review at Meridian went well. But a good review isn't one that worked once — it's one that works next quarter, on data you've never seen. Today you point your pipeline at a fresh Q4 quarter — the same Meridian, a brand-new cast — and find out what your pipeline actually learned.

This is the difference between a demo and a product. The company is the same — same 22 apps, same roles, same five policies, same SoD matrix. What's different is the cast: every employee has a new name and ID, and which specific people are risky this quarter has completely changed. The question the whole week has been building toward: did your pipeline learn the pattern, or did it quietly memorize Q3?

What you'll build today

A pipeline you trust on unseen data: your fully-built-up Day 4 system — rules, skills, tools, subagents, and hooks — run against a fresh, pre-shipped Q4 quarter, producing a valid Q4 findings.json with no logic changes, its audit log filling and its secret-guardrail still firing on the new seed, and every place it secretly leaned on Q3's specifics found and removed. Then, because Q4 ships with no answer key at all, your own: a hand-labeled micro-key and a rationale check on every finding, so you can judge whether Q4 is actually right — not just present.

What you'll learn

  • The difference between learning a pattern and memorizing one quarter's specifics
  • How the same company under a new seed becomes a genuinely unseen quarter to test transfer against
  • How to catch a pipeline that silently special-cases Q3 people, IDs, paths, or exact counts
  • How to build your own hand-labeled micro-key when there's no answer key to check against — and score your pipeline honestly against it
  • How to judge a finding's rationale on its own terms — evidence and policy citation, not just a plausible-looking verdict
  • How to prove a review system transfers — and reason about the quarters you haven't run yet

Before you start

  • Day 4 complete — the full pipeline (tools, subagents, and hooks) produces Meridian Q3 findings, with an audit log and a secret-guardrail in place
  • pytest tests/test_pipeline.py tests/test_hooks.py still passes

Cycle 1

A fresh quarter, same company

≈ 90 min
Concept

To test transfer honestly, you need data your pipeline has never seen — but from the same company, so any failure is about your code, not a different world. That's exactly what Q4 is. It was built the same way Q3 was — the kit's generator run with one different seed — which rebuilds Meridian from scratch: same 22 apps, same roles, same policies, same SoD matrix, but a completely new cast of people and a new set of specific findings.

You won't run that command today. In a real engagement you'd point your pipeline at next quarter's export as it actually arrives; for the bootcamp we've pre-generated Q4 and shipped it in the kit at data/2026-Q4/, so today is spent on the transfer lesson rather than on plumbing. You read Q4 exactly as you'd read a client's real next-quarter data.

What stays fixed seed to seed: the apps (Atlas ERP, MeridianPay, Gateway, Active Directory, Vault, and the rest), the role vocabulary, the five policies, the SoD matrix, and the service-account registry — marcus.pipeline and emergency.admin are constants because they're names, not IDs. What changes: every person's name, email, and employee ID; which employee is the Senior Accountant who also holds Vendor Admin; which one is the Controller covered by the ACP-4.2 exemption; which contractor's SOW has lapsed; and the exact finding counts. A new seed is a new exam sat by the same company.

This is the classic train / test split from machine learning, applied to a consulting engagement. Q3 is the quarter you built and tuned against — your training set. Q4 is held out — data the pipeline has never touched. A system that scores well on the quarter it was built on but poorly on an unseen one has overfit: it memorized rather than learned.

Pattern vs. memorization

Your pipeline learned the pattern if it flags whoever holds Vendor Admin + AP Manager this quarter, exempts whoever the current Controller is, and catches whichever contractor is now past SOW. It memorized Q3 if it leans on a specific Q3 name, account ID, path, or exact count — if account_id in {"A000674", "A001125", "A000387"}, or assert len(findings) == 9. Memorization passes Q3 and fails silently on Q4.

Cycle 2

Run your pipeline against Q4

≈ 90 min
Concept

Now run yesterday's pipeline — logic unchanged — against Q4 and watch what happens. Two kinds of failure show up here, and the second is more dangerous than the first.

A crash is honest: the code errors because it expected a specific Q3 value that Q4 doesn't have, and it stops. A wrong answer is quiet: the run finishes clean, writes a findings.json, and every number looks plausible — but it's subtly wrong. The worst version of this is a run that reports Q3's answer for Q4: nine findings naming Michelle Mercado and James Hernandez, on a quarter where those people don't exist. It's green, and it's completely wrong. Today you learn to distrust a green run until you've checked it's actually right.

The split-brain failure

Your Day 4 ledger-reader fetches per-entity facts through the meridian-systems MCP server, and that server is configured in .mcp.json with MERIDIAN_DATA_DIR=data/2026-Q3 — a path baked in on Day 4, when Q3 was the only quarter. Point run_review at data/2026-Q4 and the orchestrator reads Q4 files while the ledger-reader keeps answering from Q3. Half the pipeline is in one quarter, half in another. The run doesn't crash — it produces a coherent, wrong answer.

Task
  1. Run the pipeline against Q4, logic unchanged.

    Why: this is the honest transfer test — the same code, a quarter it's never seen, no edits to the logic yet. Write the result to a quarter-stamped file so Q3's findings.json stays intact for the regression check later.

    What you're building. A first Q4 run and a captured result. Point the frozen contract at the Q4 export and save its output as findings.2026-Q4.json, keeping it separate from the Q3 findings.json you built in Day 4.

    python -m meridian_capstone.contract.run_review data/2026-Q4 > findings.2026-Q4.json grep -o 'A00[0-9]*' findings.2026-Q4.json | sort -u | head A001115 ← Michelle Mercado — a Q3 account, in a Q4 run A000384 ← James Hernandez — Q3 again ... the pipeline answered from data/2026-Q3
  2. Diagnose the split-brain.

    Why: a Q4 run returning Q3 people is the loudest signal that one part of the pipeline is pinned to a Q3 path. Find exactly where the quarter is hardcoded.

    What you're building. A precise root cause, in your notes. Have Claude Code trace where each specialist gets its data: the orchestrator and its file reads follow export_dir, but the ledger-reader reaches the data through the MCP server, whose MERIDIAN_DATA_DIR is fixed to data/2026-Q3 in .mcp.json. That's the seam where the two halves diverge.

    How you'll know you got it right. You can state it in one sentence: the file side of the pipeline moved to Q4, the MCP side stayed on Q3, and that's why Q4 findings carry Q3 accounts. You don't have to fix it yet — Cycle 3 does — but you know the literal that needs to change.

    Stuck?

    Your run crashed instead of going quiet? Fine — a crash is a cleaner signal. Read what it choked on. If it's a lookup that failed (a Q3 account ID that Q4 doesn't contain, a missing key), you've found a place that hardcoded a specific Q3 value rather than deriving it. Note the file and the literal.

    Run looks completely correct? Then either you never pinned the MCP path, or your findings don't actually flow through the ledger-reader. Confirm by checking the account IDs against Q4's cast — a genuinely correct Q4 run names Q4 people, not Q3's.

  3. Hunt for the quiet wrong answers, not just the first one.

    Why: fixing the data path won't be enough if other Q3 specifics produce wrong findings silently. Get ahead of them now, while you're looking.

    What you're building. A written list of every place the pipeline leans on a Q3 specific. Have Claude Code scan the whole pipeline — the specialists, the policy logic, any verification — for: hardcoded account IDs (an exemption list keyed to the Q3 Controllers; a break-glass allowlist keyed to Q3 service-account IDs), exact counts (== 9), fixed dates (a dormancy cutoff or review as-of date pinned to Q3's quarter end), and quarter-specific paths beyond the one you just found.

    How you'll know you got it right. You can predict the effect of each on Q4. An exemption list keyed to Q3 Controller IDs means Q4's three Controllers get flagged instead of exempted. A break-glass list keyed to Q3 IDs means Q4's two emergency.admin accounts turn into false dormant findings. A hardcoded == 9 means Q4 (which has eight findings) fails a check it shouldn't. Name each predicted effect — that's your Cycle 3 to-do list.

    Stuck?

    Not sure a finding is wrong? Check it against the cases you know must appear on Q4: two Senior Accountants holding Vendor Admin + AP Manager should be flagged, this quarter's three Controllers should not be (ACP-4.2), three contractors past SOW should be flagged, and the two emergency.admin break-glass accounts should stay unflagged. If any of those is wrong, a Q3 assumption is still baked in.

  4. Commit your diagnosis notes.

    Why: commit the list of memorized specifics before you start changing code, so you have a clean record of what needed fixing.

Cycle 3

Fix the memorization

≈ 90 min
Concept

Now do the actual generalizing. Memorization in code has a shape you can learn to spot: a literal where a rule belongs. A quarter baked into a path. An account ID in a set. An exact count in an assertion. A date typed in rather than computed. Each one is a place the pipeline answered "because it was true in Q3" instead of "because the policy says so." Removing them — replacing each literal with the rule that produced it — is the generalization work.

The cleanest example is the ACP-4.2 exemption. The wrong version recognizes the Q3 Controllers by ID; the right version recognizes a Controller by the rule the policy actually states — a Finance & Accounting Controller holding the Vendor Admin + AP Manager pair under a documented compensating control. Rules travel across quarters; identifiers don't.

policy-applier (memorized → pattern) 
# WRONG — memorized Q3 (these are the Q3 Controllers' account IDs)
if account_id in {"A000674", "A001125", "A000387"}:
    exempt = True

# RIGHT — the rule, works every quarter
if (title == "Controller"
        and department == "Finance & Accounting"
        and holds_pair(account, "Vendor Admin", "AP Manager")
        and has_documented_exemption(account, "ACP-4.2")):
    exempt = True

The same move applies to the data path (derive it from the quarter you're reviewing, don't pin it), the break-glass list (recognize emergency.admin by name through the service-account registry, not by a Q3 ID), the finding count (never assert a literal total — assert the structure), and any date (compute the window from the quarter, don't type Q3's in).

    What you're building. A pipeline where the ledger-reader's MCP server reads the quarter under review rather than a pinned data/2026-Q3. Point MERIDIAN_DATA_DIR at data/2026-Q4 for the Q4 run (and, better, drive it from the quarter rather than a literal), so the orchestrator's files and the ledger-reader's MCP lookups agree.

    Why: this is the core move of the day — every memorized Q3 detail becomes the general rule that produced it.

    What you're building. A pipeline with no Q3 literals left in its judgment. Working from your Cycle 2 list, have Claude Code replace each one: the ACP-4.2 exemption keys off title = Controller + Finance & Accounting + documented compensating control, not a set of IDs; the break-glass carve-out recognizes emergency.admin through the service-account registry by name; any dormancy or review date is computed from the quarter; and any == 9 assertion becomes a check on structure (categories present, citations attached, Controllers exempt) rather than an exact total.

Cycle 4

Build your own answer key

≈ 75 min
Concept

Cycle 3 proved the pipeline runs on Q4 without special-casing it. That's still a check on form — did the run complete, do the counts look plausible. It doesn't tell you whether the individual verdicts are actually right, and this time you can't just diff against a number you memorized on Day 3, because Q4 shipped with no answer key at all — same as it will at a real client. So today you build the one you're allowed to have: your own.

Two checks, for two different failure modes

A hand-labeled micro-key catches a wrong verdict — you read a handful of accounts yourself and see whether the pipeline agrees with a human who actually looked. A rationale rubric catches a right verdict for the wrong (or missing) reason — a finding can name the correct account and still be indefensible if its rationale doesn't actually cite the evidence and the policy clause behind it. You need both, because a system can pass one and fail the other: a lucky guess with a hollow rationale, or a well-argued finding pointing at the wrong account.

This is exactly the situation Day 4's /cost-and-self-consistency check couldn't cover — self-consistency tells you a prompt is stable, not that it's correct. Today's techniques are slower and more expensive on purpose: they're for the one quarter where you have no shortcut.

Task
  1. Hand-label 10–12 Q4 accounts yourself, before looking at your pipeline's answer.

    Why: the order matters. Read the evidence and decide first — checking your own findings.json before you've formed an opinion means you're just confirming the pipeline instead of testing it.

    What you're building. A small, honest micro-key. Pick 10–12 Q4 accounts — a mix: a few you'd expect to be clean, a few you suspect are findings, one or two you're genuinely unsure about. For each, use the same tools your specialists use (the meridian-systems MCP lookups, the five policies) to decide for yourself: revoke, review, or retain — and write down why, in one sentence, citing the clause or fact that drove the call.

    micro-key.md — one row per account 
    | account   | your call | one-sentence why                              |
|-----------|-----------|------------------------------------------------|
| A000523   | revoke    | SoD conflict — Vendor Admin + AP Manager (ACP-4.2, no exemption on file) |
| A000690   | revoke    | Dormant privileged — Vault role, no login 210+ days |
| A000518   | retain    | Controller, ACP-4.2 exemption applies, compensating control documented |
| ...       |           |                                                  |

    How you'll know you got it right. Twelve rows, each with a verdict and a one-sentence rationale you could defend to an auditor — written before you opened findings.2026-Q4.json.

  2. Score your pipeline against your own micro-key.

    Why: this is the one piece of ground truth you're allowed — you built it, so it's not cheating to check against it, and it's the closest you can get to the number only the grader will ever see.

    What you're building. A short scorecard. For each of your 12 accounts, look up the pipeline's verdict in findings.2026-Q4.json (or its absence, if the pipeline retained it) and compare to your own call. Count agreements and disagreements.

    How you'll know you got it right. You can state a number — "11 of 12 agree" — and for every disagreement, you can say which of you is wrong and why. A disagreement isn't automatically the pipeline's fault: sometimes your own read was too quick, or missed a compensating control the pipeline's specialist caught. Either way, name the reason before moving on.

    Stuck? — you disagree with your own pipeline

    Pipeline flagged something you called clean? Re-check the account against the policy clause the finding cites. If the citation is real and you missed it, the pipeline was right and your first read was the miss — that's useful to know too.

    Pipeline missed something you flagged? That's the more concerning case — a false negative your micro-key caught that the case-study grading wouldn't surface until Q5. Trace which specialist should have caught it and why it didn't.

  3. Run a rationale check across every Q4 finding, not just your 12.

    Why: your micro-key only covers a dozen accounts. A rationale check scales to every finding the pipeline actually produced, and it catches a different defect — a right verdict with a rationale that doesn't hold up.

    What you're building. A pass over all eight Q4 findings asking one question per finding: does the rationale field actually name the evidence (which fact, from which source) and the policy clause behind the verdict — or does it just restate the category name in prose? Have Claude Code read each finding cold, without the context of having produced it, and judge the rationale on those terms alone.

    How you'll know you got it right. For every finding, you can point to the specific evidence field and the specific clause its rationale cites — and where one is thin or missing, you've named it rather than let it pass because the verdict itself looked right.

  4. Commit your micro-key and rationale notes.
    Terminal 
    git add .
git commit -m "Add hand-labeled Q4 micro-key and rationale check"
Checkpoint

You're done with Cycle 4 when you have a 10–12 account micro-key you labeled before looking at the pipeline's output, a scored comparison against it with every disagreement explained, and a rationale check across all eight Q4 findings that names real evidence and real citations rather than just restating the verdict. You now have a way to judge whether Q4's findings are actually right — without ever seeing the answer key that decides your grade.

Cycle 5

Prove transfer & capstone reflection

≈ 90 min
Concept

A clean run is necessary but not sufficient — you want the Q4 findings to be as good as Q3's, not just present. So you'll do a final clean run, then compare the quality across the two quarters: same rigor, same traceability, same shape? You'll also confirm the enforcement layer you built on Day 4 travels — that the audit log fills for Q4 and the secret-guardrail still fires on a seed it has never seen. Then you close the week with a short written reflection — the single most useful artifact you'll take back to your real clients.

Task

    Why: one uninterrupted run start to finish, producing a complete findings.2026-Q4.json and its exemptions.2026-Q4.json sidecar.

    How you'll know you got it right. Eight findings across the three categories with full citation coverage, five exemptions recorded, and not a single Q3 account anywhere in the output.

  2. Diff the quality of Q4 findings against Q3's.

    Why: transfer means comparable quality across quarters, not just a file that exists. Check that Q4 findings are as traceable and well-formed as Q3's.

    What you're building. A short quality comparison.   3. Confirm the enforcement layer traveled — check the Q4 audit log.

    Why: hooks are only worth anything if they fire on data they've never seen. After the Q4 run, audit/2026-Q4.jsonl should exist and carry a line for every write — the same audit hook working on the new seed.

    What you're building. A Q4 audit trail. The audit hook writes to audit/<quarter>.jsonl, keyed off the MERIDIAN_QUARTER environment variable — which defaults to 2026-Q3. Set it to 2026-Q4 for the Q4 run so the log lands in the right file, then read the tail.

    Terminal

    How you'll know you got it right. There's a line for every write the Q4 run made, each a valid JSON object with the four fields — the same PostToolUse hook, unchanged, recording a quarter it was never built for.

    Stuck?

    Writes landed in audit/2026-Q3.jsonl instead? MERIDIAN_QUARTER wasn't set, so the hook used its Q3 default. Set it to 2026-Q4 before the run — that's the one small piece of config the enforcement layer needs to follow you to a new quarter.

  4. Confirm the secret-guardrail still blocks on Q4.

    Why: an enforcement layer that only works on Q3 isn't enforcement. Push a fake secret through the Q4 pipeline and confirm the PreToolUse guardrail still catches it.

    What you're building. Proof the guard is seed-independent. The guard matches on a pattern, not on any quarter's data, so it should behave identically on Q4. Have the pipeline attempt to write a Q4 finding whose text contains sk-fake-secret-12345, and confirm the write is denied before it reaches disk.

    How you'll know you got it right. The write is refused, the reason names the pattern that matched, and findings.2026-Q4.json does not contain the fake secret afterward. The guarantee held on a quarter it had never seen — because it never depended on the quarter in the first place.

  5. Write your capstone reflection — 3 to 5 sentences.

    Why: naming what your pipeline learned versus memorized is how you'll trust it at the next real client. Save it in the repo as REFLECTION.md.

    What you're building. A short, honest REFLECTION.md in the repo root, answering the questions that matter for your real work:
