Failure mode two from sub-task 6, at full scale. Every check passes and every answer is wrong.

Everything you have built has been tuned against one quarter of one fictional company. Every number in every worksheet came from 2026-Q3. Every Skill was written while looking at accounts you now know by name.

The question Theme I answers is whether you built a system or memorized an answer. There is only one way to find out, and it is to point it at data it has never seen.

The run will succeed. Every test will pass. The findings will name people who do not exist in the quarter you asked about.

What you'll understand and do

Concept

The one idea

The most dangerous failure is the one that looks like success.

In sub-task 6 you broke a script three ways. Mode one crashed and told you where. Mode three hallucinated a rationale you could catch by asking for a citation. Mode two was the one worth fearing: the silent wrong answer. Nothing errors. The output is well-formed. You have no signal at all.

That was a toy. This is the same failure across an entire pipeline, and it is much harder to spot because everything you built to detect problems will report that there aren't any.

What is a split-brain configuration?

Two parts of the same system pointed at two different data sources, each internally consistent, neither aware of the other.

run_review(export_dir) takes its path as a parameter, so pointing it at Q4 is a one-line change. Your MCP server does not — it reads MERIDIAN_DATA_DIR from .mcp.json, which says data/2026-Q3.

So run_review reads Q4 and ledger-reader reads Q3. Both work perfectly. The findings describe Q3 and are labelled Q4.

You have already seen this configuration once, in passing. Sub-task 21 asked you to note what MERIDIAN_DATA_DIR could do to you, and sub-task 28 mentioned it again when you pointed the pipeline at a poisoned copy. This is the sub-task where noting it pays off — or where not noting it costs you an hour.

Why every check you built will pass

Schema validation — Q3 findings are valid findings.

Coverage checks — the distribution is exactly the healthy one you calibrated against, because it is that distribution.

Self-consistency — two runs agree perfectly. Both read Q3.

The micro-key — scores perfectly. It was built from Q3.

The judge — every rationale is well-evidenced and correctly cited, because the reasoning is sound. It's sound about the wrong quarter.

Six evaluations, all green, all wrong. The only thing that catches this is a human noticing that gabriel.villa does not appear in the Q4 roster.

Open the quarter you have never seen

  1. Confirm data/2026-Q4 is already in your kit.

    Why: there is nothing to generate. The kit ships a second quarter alongside Q3 — same company, same world design, a completely different cast. It has been sitting in your repo since sub-task 1, deliberately unmentioned. The kit's transfer tests carry Q4 ground truth that matches this exact export, so use the shipped one rather than a substitute.

    terminal

  2. Confirm it's the same company and a different cast.

    Why: the world design is unchanged — same 22 applications, same five policies, same SoD matrix, same service accounts, 1,200 accounts and 1,190 HR rows. What changed is every person, every ID, and every specific finding.

Stuck?

data/2026-Q4 isn't there. It ships with the kit, so it was most likely deleted or never checked out. Restore it from the repo (git checkout -- data/2026-Q4); the transfer tests only line up with that export.

My row counts don't match. Then your copy has been edited or replaced. Restore the shipped one, or the transfer tests will check ground truth that doesn't describe your data.

Where did Q4 come from? The same generator that produced Q3, run once by the instructor under a different seed. You don't run it — both quarters are committed course data. What matters here is only that you've never looked at this one.

Task 2

Run it, and believe the result for a moment

  1. Point run_review() at Q4 and run the full quarter.

    Why: write to a quarter-stamped file. Keep findings.json as your Q3 answer — the pipeline test still checks it, and losing your Q3 result to overwrite it would be an unforced error.

    terminal 
    python -m meridian_capstone.contract.run_review data/2026-Q4 > findings.2026-Q4.json
  2. Run every evaluation you built, and note that they all pass.

    Why: this is the point of the sub-task and it deserves a moment. Schema, coverage, self-consistency, micro-key, judge. Six green results. Write down that they were green, because it is the most instructive fact in Theme I and it will be tempting to forget once you know what's wrong.

  3. Now read the findings.

    Why: take each account_id and each name in the findings and look for them in data/2026-Q4/hr_roster.csv. If you see gabriel.villa, michelle.mercado or james.hernandez, you are reading Q3's answers in a file named Q4.

    terminal 
    python3 -c "
import json,csv
f=json.load(open('findings.2026-Q4.json'))
ids={r['account_id'] for r in csv.DictReader(open('data/2026-Q4/entitlements.csv'))}
for x in f:
    print(x['account_id'], 'IN Q4' if x['account_id'] in ids else 'NOT IN Q4')
"
  4. Diagnose it properly — find the two data paths.

    Why: don't guess. Trace where each component gets its data. run_review() takes export_dir, so that half followed you. ledger-reader calls MCP tools; the MCP server reads MERIDIAN_DATA_DIR from .mcp.json; that file says data/2026-Q3.

    terminal 
    grep -n MERIDIAN_DATA_DIR .mcp.json
grep -rn "2026-Q3" .mcp.json .claude/ src/ *.py 2>/dev/null

    That second command is worth running in full. It will find more than the one you're looking for, and everything it finds is sub-task 38's work list.

  5. Fix the split brain and re-run.

    Why: point MERIDIAN_DATA_DIR at Q4, or better, parameterize it so the pipeline can't disagree with itself. Restart — .mcp.json is read at startup. Then run again and confirm the findings now name people who exist in Q4.

    Expect the answers to be different, not necessarily right. Sub-task 38 is the rest of the fix.

  6. Write up the failure while it's fresh.
    The silent wrong answer

    This is the story you tell a client about why "all tests pass" is not the same as "it works". Write it so it lands.

  7. Add that check to your validator, and commit.

    Why: the last worksheet box names a check that would have caught this in a second — every account_id in the findings must exist in the export under review. It is one line, it is quarter-independent, and it closes the exact hole that just made every other eval useless. Add it now.

Stuck?

The findings already named Q4 accounts. Either you parameterized the data directory earlier — well done, note that you avoided the trap — or your pipeline doesn't route through MCP at all. Check which. If your agents read files directly the split-brain never happens, and that's a legitimate architecture with its own trade-offs worth writing down.

The Q4 run crashed. Different and easier failure. Something is hardcoded to a Q3 path or a Q3 identifier. Fix it and note it — it's the first entry on sub-task 38's list.

It found zero findings on Q4. Also a memorization symptom, and a revealing one. Something keyed to Q3 specifics — account IDs in an exemption list, a hardcoded as-of date — is now matching nothing. That's sub-task 38's subject.

If you're curious

  • Overfitting — the same idea from machine learning. A model that memorizes its training set scores perfectly on it and fails on anything else, which is precisely what your pipeline just did to 2026-Q3.
  • Diff the two exports structurally — row counts, application list, policy files, the SoD matrix. What stays identical is the world; what changes is the population. A system should depend only on the first.
