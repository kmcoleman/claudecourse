Make a hook deny a write that would leak a secret

Depends on: Sub-task 25 — you need the three-agent pipeline running Time: ≈ 60 min Type: building block #5
First appearance
Hooks PreToolUse deny decision settings.json

Building block five of six. The deliverable is a denial message written by you, not by the model.

Every safety property you have rests on agent files being written correctly. ledger-reader can't write because you left Write off its list. findings-writer writes to the right paths because its system prompt says so.

The first of those is a real constraint. The second is a hope. Nothing checks the path a write actually targets, or what's in the bytes going to disk. You found that gap yourself in sub-task 20 — tool restriction controls capabilities, never arguments.

Hooks are the layer that inspects the arguments. And the ordering property that makes them useful is blunt: PreToolUse runs before the tool, so it is the only place a write can be prevented rather than regretted.

What you'll understand and do

  • Explain the hook lifecycle and why PreToolUse is the only preventive point
  • Wire secret_guard.py into settings.json
  • Attempt a write carrying an API key and get denied by your own hook
  • State what a pattern-based guard catches and what it can't

Concept

The one idea

Prevention has to happen before the thing you're preventing.

Obvious written down, and routinely got wrong in practice, because the natural place to put a check is where you notice you need one — which is usually after something went wrong.

What is a hook?

A command Claude Code runs at a defined point in the tool lifecycle. It receives JSON on stdin describing the event and can respond on stdout.

PreToolUse fires after the model requests a tool call and before the call executes. It can deny. The tool never runs, and nothing lands on disk.

PostToolUse fires after the call has completed successfully. It cannot prevent anything — the file is already written. It can record, and it can halt what happens next. That's sub-task 27.

Configuration lives in .claude/settings.json (committed) or .claude/settings.local.json (gitignored). A matcher selects which tools the hook applies to.

The stdin payload is the whole interface. Your hook gets tool_name, tool_input, session_id, cwd and hook_event_name. For a Write, the body is in tool_input.content. For an Edit, it's in tool_input.new_string. A guard that checks only one of those has a hole in it the size of the other tool.

How to deny

Two mechanisms. Exit with status 2 and write to stderr — the stderr text goes back to Claude as feedback. Or exit 0 having printed a decision object:

{"hookSpecificOutput": {"hookEventName": "PreToolUse",
 "permissionDecision": "deny", "permissionDecisionReason": "…"}}

The second is better here because the reason is a field rather than a side effect of an error channel, and Claude sees it as an explanation rather than a crash.

A note on the design, because the kit deviates from the obvious layout. The intuitive assignment is Pre = audit, Post = secret guard — log what's about to happen, then scan what happened. It doesn't work. A post-hoc secret scan reads a secret that is already on disk, already in the file, and possibly already committed. The scan correctly reports a breach it was powerless to stop.

So the kit inverts it. Pre = guard, because prevention has to be preventive. Post = audit, because an audit trail should record what actually happened rather than what was attempted. Every claim in that arrangement is literally true, which is not something you can say about the alternative.

Do this

Task 1

Read the shipped guard before you wire it

  1. Read .claude/hooks/examples/secret_guard.py.

    Why: it's short and the whole mechanism is visible. It loads JSON from stdin, joins tool_input.content and tool_input.new_string so one guard covers both Write and Edit, and tests the result against a list of patterns.

    the patterns it ships with 
    sk-[A-Za-z0-9]      API-key style tokens
ANTHROPIC_API_KEY   a named credential variable
password:           a password field in YAML/JSON/text
Bearer              an Authorization header value

    Four patterns, and they are pattern-based rather than keyed to any Meridian specifics. That matters for a reason you'll appreciate in Theme I: this guard works unchanged on a quarter that doesn't exist yet.

  2. Copy it up one level into .claude/hooks/.

    Why: examples/ is reference material. The live hook lives at .claude/hooks/secret_guard.py so the settings path is stable and the example stays intact for comparison.

    terminal 
    cp .claude/hooks/examples/secret_guard.py .claude/hooks/
Task 2

Wire it and watch it fire

  1. Add a PreToolUse hook to .claude/settings.json, matching Write|Edit.

    Why: .claude/hooks/examples/settings.hooks.json is the reference shape — read it rather than guessing the nesting, which is fiddlier than it looks. Use $CLAUDE_PROJECT_DIR in the command so the hook resolves regardless of the working directory.

    Settings are read at startup. Restart after editing, or you'll spend twenty minutes concluding your hook doesn't work.

  2. Try to write a file containing an API key.

    Why: the deliverable is the denial. Ask Claude Code to write a config file containing something like sk-fake-secret-12345, or to add ANTHROPIC_API_KEY=sk-… to a file. Use an obviously fake value — the exercise is the guard firing, and there is no reason to have a real key anywhere near this.

    expected 
    secret-guard: matched /sk-[A-Za-z0-9]/ in the pending write to
<path>; refused before it reached disk.

    That message is yours. It came from a file you copied and wired, not from the model deciding to be careful. Read it and then check the filesystem — nothing should exist.

  3. Check the Edit path separately.

    Why: Write and Edit carry their payload in different fields, and a guard that only reads content lets every Edit straight through. Create an innocent file, then edit a secret into it. The guard should deny that too.

  4. Confirm it doesn't fire on ordinary work.

    Why: a guard that denies everything is not a guard, it's an outage. Run your limit=20 pipeline and confirm findings.json writes normally. A false positive rate you haven't measured is a false positive rate that will find you at the worst moment.

    Worth a moment on the shipped patterns while you're here. password: is broad — a rationale mentioning "the password policy requires…" would trip it. That is a genuine tension between a guard that catches things and a guard that lets you work, and it's the tension you'd be tuning in a real engagement.

Stuck?

The hook doesn't fire. Restart first. Then check the JSON parses, the matcher is Write|Edit, and the command path is right — a hook whose command can't be found fails quietly rather than blocking.

It fires but the write still happens. The decision output isn't being read. Check the JSON shape exactly, including hookEventName, and that the script exits 0 after printing it. Exit 2 with a stderr message is the fallback if the object form is misbehaving.

Everything is blocked. Test the script standalone: pipe a JSON payload into it and read what it prints. Debugging a hook through the agent adds a layer you don't need.

terminal 
echo '{"tool_name":"Write","tool_input":{"file_path":"x.txt","content":"hello"}}' \
  | python3 .claude/hooks/secret_guard.py
Task 3

Be honest about what this catches

  1. Find something it misses, deliberately.

    Why: four regexes are four regexes. A base64-encoded key, a key split across two writes, a credential in a format none of the patterns describe — all pass. Find one and confirm it. Knowing your control's coverage is the difference between a control and a comfort.

  2. Write down what layer this is and what it isn't.

    Why: hooks are the last line, not the only one. Tool restriction already removed the capability from two of your three agents. The guard checks the arguments of the one that has it. Neither is sufficient alone, and saying so precisely is what sub-task 28 builds on.

    My guard, and its limits

    Sub-task 28 attacks this layer along with tool restriction. Know its edges before then.

  3. Commit.

    .claude/hooks/secret_guard.py and .claude/settings.json. Both are the control; both belong in review.

You're done when

Building block five exists. Specifically:

  • secret_guard.py live at .claude/hooks/ and wired as a PreToolUse hook on Write|Edit
  • A denial message from your own hook, with nothing on disk to show for the attempt
  • Both the Write and Edit paths confirmed
  • A normal pipeline run unaffected
  • One bypass found on purpose, and the layer's limits written down

You can now prevent a class of write. What you cannot do is say what your pipeline actually wrote last Tuesday.
