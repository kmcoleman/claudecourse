Close the loop — and see why you wouldn't ship it

Depends on: Module 4 · 3 — you need a working export Time: ≈ 60 min Type: elective — not a building block
First appearance
local control plane append-only decision record trust boundary

The most useful thing in this sub-task is the list of reasons not to deploy what you build in it.

A browser cannot run your pipeline. It has no shell, no Python, and that is a deliberate property of the platform rather than a gap to work around. If a page could start processes on the machine that opened it, the web would be unusable.

So closing the loop means putting something between them: a small local process that owns the dangerous capabilities and exposes exactly two of them. Building it takes forty lines. Understanding why those forty lines must never leave 127.0.0.1 is the actual lesson.

This one is genuinely optional. If you stop after sub-task 3 you have a complete, defensible deliverable: findings in, decisions out, CSV and PDF. Nothing below improves the artifact.

What it does is show you the shape of the production version — and the shape of the trust boundary you'd be taking on. If you'd rather read this one and not build it, read the concept section and the last task, and skip the middle.

What you'll understand and do

  • Put a stdlib-only local server between the page and the pipeline
  • Run a review from the UI and reload findings without touching a terminal
  • Append reviewer decisions to the audit trail your hooks maintain — as their own record type
  • Name every reason this design stays on localhost

Concept

The one idea

The moment your UI can start a process, you own a trust boundary you didn't have before.

Everything through sub-task 3 was inert. A static page that reads a file it was handed cannot do damage: worst case it renders something wrong. Add one endpoint that runs subprocess and the page is now a control plane for a program that reads client data and spends API budget.

That's a fine thing to have on your own laptop while iterating. It is not a fine thing to leave running, and the difference between the two is one string in one call.

Bind to 127.0.0.1, never 0.0.0.0

("", 8000) and ("0.0.0.0", 8000) both listen on every interface. On café wifi, on a client's guest network, on a VPN, that is an unauthenticated endpoint that runs your pipeline and appends to your audit log, offered to everyone on the segment.

("127.0.0.1", 8000) is reachable only from the machine itself. Type it explicitly. It's the same instinct as sub-task 23's specialist that can't write — capability granted deliberately, at the smallest scope that works.

Why the decision record is not shaped like the hook's

Your PostToolUse hook writes ts, tool, path, session_id — a record of a tool call, written by machinery, about machinery.

A reviewer decision is a different kind of fact. It has a human author, a verdict, and a reason. Forcing it into the hook's four fields would mean lying in the tool field, and an audit log where one record type lies about its shape is one nobody can parse confidently later.

Same file, same append-only discipline, explicit kind field so a reader can tell them apart. That's the honest design, and it's why sub-task 27 had you notice the four-field minimum in the first place.

What the real version looks like. At a client this is a small web service with SSO, a database instead of localStorage, reviewers assigned to applications they own, a sign-off step that freezes the quarter, and decisions flowing into whatever actually revokes access. None of that changes the architecture you've built — findings in, decisions out, both recorded. It changes who is allowed to do it and where the state lives.

Worth being blunt about: that service is a normal enterprise application, not an agentic system. The agentic part finished at sub-task 39. Knowing where that line falls is part of the job — a lot of AI project budget gets spent building conventional software with an unconventional label on it.

Task 1

The local control plane

  1. Write reviewer/serve.py — stdlib only, localhost only.

    Why: it subclasses the same SimpleHTTPRequestHandler you've been using since sub-task 1, so static files keep working exactly as they did and you're only adding two POST routes. Run it from the repo root; the handler serves the current working directory.

    reviewer/serve.py 
    #!/usr/bin/env python3
"""Local-only reviewer control plane. A development convenience — NOT a deliverable.

Run from the repo root:  python reviewer/serve.py
Then open:               http://127.0.0.1:8000/reviewer/
"""
import json
import subprocess
import sys
import time
from http.server import SimpleHTTPRequestHandler, ThreadingHTTPServer
from pathlib import Path

ROOT = Path(__file__).resolve().parent.parent
QUARTER = "2026-Q3"


class Reviewer(SimpleHTTPRequestHandler):
    def do_POST(self):
        if self.path == "/api/run":
            return self._json(self._run_review())
        if self.path == "/api/decision":
            return self._json(self._append(self._body()))
        self.send_error(404)

    # ---- helpers ------------------------------------------------------
    def _body(self):
        n = int(self.headers.get("Content-Length", 0))
        return json.loads(self.rfile.read(n) or b"{}")

    def _json(self, payload, status=200):
        blob = json.dumps(payload).encode("utf-8")
        self.send_response(status)
        self.send_header("Content-Type", "application/json")
        self.send_header("Content-Length", str(len(blob)))
        self.end_headers()
        self.wfile.write(blob)

    # ---- the two capabilities ----------------------------------------
    def _run_review(self):
        proc = subprocess.run(
            [sys.executable, "-m", "meridian_capstone.contract.run_review",
             f"data/{QUARTER}"],
            cwd=ROOT, capture_output=True, text=True,
        )
        if proc.returncode != 0:
            return {"ok": False, "stderr": proc.stderr[-2000:]}
        (ROOT / "findings.json").write_text(proc.stdout, encoding="utf-8")
        return {"ok": True, "count": len(json.loads(proc.stdout))}

    def _append(self, d):
        log = ROOT / "audit" / f"{QUARTER}.jsonl"
        log.parent.mkdir(parents=True, exist_ok=True)
        record = {
            "ts": time.strftime("%Y-%m-%dT%H:%M:%SZ", time.gmtime()),
            "kind": "reviewer_decision",          # not a tool call — say so
            "finding_key": d["key"],
            "model_recommendation": d["model_recommendation"],
            "human_verdict": d["verdict"],
            "reason": d.get("note", ""),
            "reviewer": d.get("reviewer", "unattributed"),
        }
        with log.open("a", encoding="utf-8") as fh:   # append-only, one line
            fh.write(json.dumps(record) + "\n")
        return {"ok": True, "appended": record}


if __name__ == "__main__":
    # 127.0.0.1 — not "" and not "0.0.0.0". See the concept section.
    ThreadingHTTPServer(("127.0.0.1", 8000), Reviewer).serve_forever()

Task 2

Decisions into the audit trail

  1. Post each decision to /api/decision as it's made, keeping the localStorage write.

    Why: localStorage stays the source of truth for the UI so the page still works with the server down. The audit append is additive — if it fails, warn and carry on rather than losing the reviewer's decision to a network error.

    reviewer/index.html — script 
    function decide(f, verdict, note) {
  var entry = {
    key: keyOf(f),
    verdict: verdict,
    model_recommendation: f.recommendation,
    note: note || "",
    reviewer: document.getElementById("reviewer").value || "unattributed",
    decided_at: new Date().toISOString()
  };

  decisions[entry.key] = entry;
  saveDecisions(decisions);            // local first — always succeeds, always the UI's truth

  fetch("/api/decision", {             // audit append — best effort, never blocking
    method: "POST",
    headers: { "Content-Type": "application/json" },
    body: JSON.stringify(entry)
  }).catch(function () {
    status("Decision saved locally but not appended to the audit log.");
  });
}
  2. Read the audit log and separate the two record types.

    Why: this is the payoff for the kind field. One append-only file now holds what the machinery did and what the humans concluded, and a reader can tell them apart without guessing.

Stuck?

404 on /api/run. You're on the plain python -m http.server from sub-task 1, which knows nothing about POST. Stop it and start python reviewer/serve.py instead — and check nothing else is holding port 8000.

The subprocess can't find the module. cwd=ROOT sets the working directory but not the environment. Run the server from the same virtualenv you run the pipeline in; sys.executable then points at the right interpreter and the package resolves.

The run succeeds but the page shows stale findings. The browser cached findings.json. Re-fetch with a cache-buster ("../findings.json?t=" + Date.now()) or send a no-store header.

Decisions are duplicated in the log. Correct, and intended. Append-only means a changed mind is a second record, not an edit. Reduce to latest-per-key when you read, and keep the history — a reviewer who reversed a decision is exactly what an auditor wants to see.

Is a browser posting to a local Python server safe? On your own machine for your own review, yes. Understand that any page open in that browser can also post to 127.0.0.1:8000 — which is the honest answer to why this never ships as it stands, and why the production version starts with authentication.

You're done when
  • reviewer/serve.py runs on 127.0.0.1 only, using nothing outside the standard library
  • A Run review button produces fresh findings and reloads them in place
  • Decisions survive a live re-run, still attached to the right accounts
  • Decisions append to audit/2026-Q3.jsonl as kind: "reviewer_decision", distinguishable from the hook's tool records
  • The log is still append-only and the sub-task 26 guard still denies
  • A written account of what would change before this touches a client machine

End to end. The pipeline runs, findings appear, a named human decides, and both the machine's judgment and the human's are recorded in one append-only log.

The elective is done, and so is everything else. What you built here isn't part of the six blocks and shouldn't be — but it's the part your client sees, and the part that decides whether the other six ever get used.
