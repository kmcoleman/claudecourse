You are about to build the artifact everything else in this course reads from, and then throw away 87% of it before any agent ever sees it. Both halves matter, and the second half is the one worth remembering.

Everything you've done in Theme B has been code. No agent, no judgment, no prompt. That was not an accident of ordering — it's the design principle, and this sub-task is where you name it.

What you'll understand and do

  • Build the Ledger — one de-duplicated, identity-attached row per grant
  • State the context-economics principle and apply it as a triage rule
  • Defend a candidate count with the claim that everything else is provably clean

Concept

The one idea

Context is expensive. Move bulk to code; move judgment to the model.

This is the design principle of the whole course, and it's worth stating in a form you could use on a system that has nothing to do with access reviews:

Context economics

A model's context window is the scarcest resource in any agentic system — scarce in tokens, in money, in latency, and above all in attention. Every row you put in front of a model competes with every other row for the model's care.

So the design question for every step is not "can the model do this?" It is: does this step require judgment? If it doesn't, it belongs in code — where it is cheaper, faster, deterministic, and testable. If it does, it belongs with the model — and the model should arrive at it with the irrelevant 87% already gone.

Put concrete numbers on it. entitlements.csv is 1.16 MB, on the order of 320,000 tokens. You could feed the whole thing to a model. It would be slow, it would cost real money every run, and — the part people miss — it would be worse, because the twelve genuinely difficult accounts would be buried under fifteen thousand rows of Zoom memberships that no reviewer would look at twice.

The test for which side a decision belongs on is whether two competent reviewers with the same data would give the same answer:

≡
Code — determined by the data

Is this employee terminated? Was this grant dated before their hire date? Does this account hold two roles the SoD matrix names as conflicting? Is this role on the application's privileged list?

Same answer every time. No model needed, and a model would only add variance.

?
Judgment — requires reading, weighing, deciding

Is this contractor's access still justified given the ticket they filed? Does the compensating control in the policy actually cover this case? Is this orphan a leaver nobody offboarded, or a rename nobody recorded?

Reasonable reviewers can disagree. This is what the model is for.

Mechanical triage is how you get from one to the other: a set of deterministic rules, each cheap and each testable, that partition the ledger into needs a human-or-model look and provably clean. The second pile is the valuable one, because you can say something precise about it: not "we didn't check those", but "we checked every one of those with a rule, and here is the rule."

Why this generalizes

Log triage, document review, alert handling, code review, claims processing — the shape is identical every time. Deterministic filter, then judgment on the residue. When you take this back to your own problem, the first question is always: what fraction of my volume can a rule dispose of, and what exactly is the rule?

Task 1

Build the Ledger

  1. Join the normalized entitlements to identities.csv and write ledger.csv at the repository root.

    Why: the Ledger is the one table the rest of the course reads. One row per distinct grant — per (account_id, app, role) — with ISO dates, the resolved employee_id where there is one, and the match status where there isn't.

    Two things it must not do. It must not drop unmatched accounts: an orphan with production access is the finding, and a left join that quietly discards it produces a clean-looking report that is wrong. And it must not fan out: joining 1,200 accounts on name against 1,190 people can produce more than 1,200 rows if a name matches twice. Check your row count after the join, every time.

    expected output 
    ledger.csv
  rows                              15158
  distinct (account_id, app, role)  15158     <- must be equal
  distinct account_id                1200     <- nothing dropped
  granted_date non-ISO values            0
  2. Run the tests. The ledger tests should now pass.

    Why: the failure messages are written to diagnose you. 15,188 means nothing was de-duplicated. 15,178 means you de-duplicated before normalizing and twenty format-twins survived — go back to sub-task 10. Anything else means the join changed your row count.

    terminal 
    pytest -m "not api"
# 4 failed, 42 passed, 10 skipped, 1 deselected

    Four failures left, all in the findings group. Those are sub-task 12.

Stuck?

My ledger has more than 15,158 rows and I did de-duplicate. The join fanned out. Join on account_id against a table with exactly one row per account — which is what identities.csv is for. Never join entitlements to HR on name directly.

My ledger has fewer than 15,158 rows. An inner join dropped the unmatched accounts. Those 1,544 grants on 122 unresolved accounts are among the most interesting rows in the file.

Which columns should the ledger have? Your call, but at minimum enough to answer a finding without re-reading the source: account, name, resolved person, match status, app, role, normalized grant date, granted-by, last login.

Task 2

Write the mechanical triage rules

  1. Implement each rule as a deterministic filter over the ledger, and count what it catches.

    Why: one rule at a time, each independently countable. A rule you can't count is a rule you can't defend. These counts assume the baseline exact-match identity table from sub-task 9; if you widened the matcher, your orphan and ambiguous rows will be lower.

    expected output — baseline matcher 
    rule                     grants   accounts   source of truth
-------------------------------------------------------------------
terminated employee         134         10   hr_roster.status
orphan account             1544        122   identities.csv match_status
ambiguous identity          221         18   identities.csv match_status
granted before hire           2          2   granted_date < hire_date
privileged role             105        105   applications.json
sod conflict                 10          5   sod_matrix.json
privileged, no ticket        23         23   access_tickets.json (85 tickets)
dormant 90+ days           1283        771   last_login
contractor on crown app     219        105   employment_type + app tier
  2. Notice which rules are cheap and which are lethal.

    Why: granted before hire catches 2 rows out of 15,158 — and each one is an account that existed before its owner did. Two rows, essentially free to compute, and among the most serious things in the file. Meanwhile dormant 90+ days catches 1,283 rows and most of them are somebody who hasn't opened Zoom since June.

    Rule volume is uncorrelated with rule value. This is why you count each rule separately instead of jumping straight to a combined filter — a rule you can't see the size of is one you can't reason about.

Stuck?

My privileged count isn't 105. Privileged roles are named per application in applications.json under privileged_roles. It's not a global list of role names — Admin is privileged in one app and not defined in another.

My terminated count is higher. Ten employees have status == "terminated". If you're using a non-empty term_date instead you'll pick up 13 people, three of whom have a future-dated departure and are still employed today. Those are different questions; know which you asked.

My dormant count differs. The window's start point is a choice. The number above uses 90 days before 2026-09-30, the export date, and counts a blank last_login as dormant. Both of those are decisions; state yours.

Task 3

Produce the candidate set and defend the remainder

  1. Union the high-signal rules into one candidate set.

    Why: a grant is a candidate if any high-signal rule fires on it. Which rules count as high-signal is your decision — the reference numbers below take terminated, orphan, ambiguous, granted-before-hire, SoD, privileged-and-dormant, and privileged-without-a-ticket, and deliberately leave out bare dormancy and bare contractor status, which are too broad to be worth a model's attention on their own.

    expected output 
    ledger                     15158 grants   1200 accounts
candidates                  1919 grants    166 accounts
provably clean             13239 grants                  87.3%

model calls made so far: 0
  2. Re-run the triage with your widened matcher from sub-task 9, and watch the number fall.

    Why: this is the payoff for the work you did in sub-task 9, and it is the most quietly important number in Theme B.

    expected output — widened matcher 
    baseline matcher   (1055 resolved)    1919 candidate grants    166 accounts
widened matcher    (1118 resolved)    1125 candidate grants    104 accounts

    Sixty-three better identity matches removed 794 candidate grants — 41% of the judgment workload — because an account you can attribute to a real, currently-employed person stops being suspicious. Better reconciliation is not tidiness. It is directly less work for the expensive part of the system, and it is why reconciliation comes before agents rather than after.

  3. Write the sentence that defends the 87%.

    Why: this is the sentence a client or an auditor will challenge, and it has to be a claim about rules rather than a claim about effort. Not "we reviewed a sample." Something closer to: every grant in the ledger was evaluated against nine deterministic rules; 1,919 matched at least one and went to review; the remaining 13,239 matched none, and the rules are listed in appendix A.

    That claim is falsifiable, reproducible, and re-runnable next quarter. It is also the honest version — it says exactly what was checked, which means it also says exactly what wasn't.

  4. Commit your progress.

    ledger.csv is gitignored as a learner artifact — commit the code that builds it.

Stuck?

My candidate count isn't 1,919. Expected, if you chose a different set of high-signal rules — and that's a legitimate design decision rather than an error. What matters is that you can name every rule in your union and count each one. If you want to reproduce 1,919 exactly, use the seven rules listed above with the baseline matcher.

Isn't 1,919 still too many to hand a model? Yes, and noticing that is the right instinct. Two things fix it, and you'll meet both later: triaging at the account level rather than the grant level (166 accounts, not 1,919 rows), and splitting the work across narrow subagents instead of one generalist. Note the concern now.

Should I just let a model decide which rules to use? Ask what you'd do when it picks differently on the next run. Rule selection is a judgment call and you've just made it; rule application is mechanical and belongs in code. Keeping those separate is the whole principle.

ledger.csv exists with 15,158 rows — and the ledger tests in test_ledger.py pass. Plus:

  • Distinct (account_id, app, role) equals the row count, and all 1,200 accounts survive
  • Every granted_date is ISO
  • Each triage rule is implemented separately and counted separately
  • A candidate set — 1,919 grants on 166 accounts at baseline — produced with zero model calls
  • You ran it with the widened matcher too, and saw candidates fall to 1,125

The principle, in the form worth keeping: context is expensive, so move bulk to code and move judgment to the model. Everything remaining in this course is the judgment half — and it only works because you just made it 87% smaller.
