Your agent has knowledge now. What it doesn't have is reach: it knows only what you decided to put in the dossier, and if the dossier is missing something, the agent has no way to go and get it.

Tools are the fix, and before you hand any out it is worth being precise about what one is. A tool is a capability you grant. Every capability you grant is something that can go wrong, and the set of things that can go wrong is the blast radius.

You have been working alongside a heavily-tooled agent for nineteen sub-tasks. Start by taking its inventory.

What you'll understand and do

  • Define a tool precisely enough to reason about what granting one costs
  • List the tools Claude Code actually has in your install
  • Sort them read-only versus mutating and rank by blast radius
  • Produce the table you'll apply when restricting subagents in Theme F

Concept

The one idea

Every tool you grant is a thing that can go wrong. Grant fewer.

A tool is a function the model may choose to call, described to it in enough detail that it can decide when calling it is appropriate. The model does not execute anything — it emits a request to call a tool with particular arguments, and something on your side runs it and hands back the result.

What is a tool?

A name, a description, and a schema for its inputs. The description is what the model reads when deciding whether this tool is the right one, which makes it the same kind of high-leverage text as a Skill's description.

The model never runs anything. It asks. Your harness decides whether to comply. That gap is where every safety control in Themes F and G lives — tool restriction, hooks, permissions. If the model executed things directly there would be nowhere to stand.

Blast radius is the question you ask about each tool: if the model calls this with the worst plausible arguments, what is the damage, and can I undo it? It is not about the model being adversarial. It is about the model being confidently wrong, which you have already watched it be twice.

The primary split is read-only versus mutating. A read-only tool called wrongly wastes tokens and may mislead the reasoning. A mutating tool called wrongly changes the world. Those are not the same category of problem and should not carry the same level of caution.

Why this matters more here than in most projects

An access review is an observational exercise. You look at what access exists and write down what you think about it. Nothing in the job description involves changing anything in Meridian's systems — not revoking a grant, not closing a ticket, not updating a record.

So the honest tool surface for most of this system is read-only, and the one component that needs to write should write exactly one thing: your findings. Sub-task 24 makes that structural. This sub-task is where you work out what "read-only" actually means in tools.

One more distinction worth having now, because it shapes the whole of Theme F. Omitting the tool list inherits everything. A subagent defined without a tools: field gets the full set, including every mutating tool and every MCP server you have configured. Restriction is opt-in, which means an unrestricted agent is the default and you have to choose otherwise.

Task 1

Take the inventory

  1. Ask Claude Code to list the tools it currently has, and what each one does.

    Why: ask the agent rather than reading a doc, for two reasons. The set changes between versions, so a list in a course page goes stale. And it depends on your configuration — MCP servers you've added appear here too, which is exactly the point you're about to make.

    Intent: "list every tool available to you in this session, with one line on what it does and whether it can change anything on disk or over the network." Have it distinguish built-ins from anything configured.

  2. Sanity-check the list against what you've watched it do.

    Why: you have nineteen sub-tasks of evidence. It has read files, searched them, run shell commands, edited code, and written new files. Every one of those was a tool call. If something in the list surprises you, that's the interesting entry — ask about it.

    the shape of what you'll see 
    reading      Read, Glob, Grep            filesystem, no writes
network      WebFetch, WebSearch          reads the outside world
executing    Bash                         runs arbitrary commands
mutating     Write, Edit                  changes files on disk
delegating   Task / subagents             spawns another agent
configured   any MCP server tools         depends on .mcp.json

    Names and groupings vary by version. The categories don't, and the categories are what you're building.

Task 2

Rank them by blast radius

  1. For each tool, answer three questions: can it change anything, how far does the change reach, and can you undo it?

    Why: those three answers are the ranking. "Can it change anything" separates read-only from mutating. "How far does it reach" separates a single file from the whole filesystem from the public internet. "Can you undo it" is what turns an annoyance into an incident.

    the axes — fill in for your own list 
    tool     mutates?   reach                      reversible?
Read     no         one file                   n/a
Grep     no         many files, read only      n/a
Glob     no         filesystem metadata        n/a
Edit     YES        one existing file          yes, in git
Write    YES        any path, creates files    mostly, if committed
Bash     YES        anything the user can do   NO
WebFetch no*        outbound network           * sends data out

    Two entries deserve argument. Bash is not one tool — it is the ability to run anything you could run, which makes its blast radius the union of every other tool's plus everything you never thought of. And WebFetch is only read-only from the model's side: it reads a remote page, but the request itself carries data out of your environment, which for a client's access data is a real consideration even though nothing local changed.

  2. Pick the minimum set for each job in the system you're about to build.

    Why: this is the deliverable. Three roles are coming in sub-tasks 23 and 24 — something that gathers facts about accounts, something that applies policy, and something that writes findings. Decide now what each genuinely needs, and be strict: the test of a good answer is that removing any one tool breaks the job.

  3. Notice the gap in that last answer.

    Why: "what stops it writing elsewhere" almost certainly has no good answer yet. Granting Write grants writing to any path — the tool list restricts which capabilities, not which arguments. That gap is real and tool restriction cannot close it. Building block five closes it, in sub-task 26. Write down that you noticed.

Stuck?

Doesn't restricting tools just make it worse at the job? Sometimes, and that's the trade you're pricing. The question isn't "fewest tools" but "fewest tools that still do the job" — and the honest way to find the line is to remove one and see what breaks, which is sub-task 23.

Bash could do everything. Why not just grant Bash? It could, and it's a real design position — broad capability, minimal tool surface. The cost is that your harness sees an opaque command string instead of a typed call, so it can't gate, audit, or parallelise anything. Granting Bash to the component that writes findings means every hook you write in Theme G has to parse shell to know what happened.

My list doesn't match the example. Expected. Versions differ and your configuration differs. Your list is the correct one for your system; the categories are what transfer.
