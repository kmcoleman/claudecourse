The schema from sub-task 12 stops being a validator and starts being a constraint on the model.

The verdict you got in sub-task 13 is readable and useless. A human can act on it, once. Nothing else can — you can't count it, sort it, diff it against last quarter, or feed it to the next stage.

You already own the fix. findings.schema.json has been sitting in the repo since sub-task 12, where you used it to validate findings you built by hand. This sub-task hands the same schema to the model as a constraint on what it is allowed to produce. Same file, different job.

What you'll understand and do

  • Recognize structured output as sub-task 12's idea applied one level up
  • Constrain a model call to the findings schema and get back something that validates
  • Read per-call cost and project it across the candidate set

Concept

The one idea

You already learned this. It just moves from the output file to the model call.

Sub-task 12 made an argument about structured output that had nothing to do with compliance: fixing the shape of output makes it composable, testable, and forces the ontology early. That argument was about findings.json — a file you wrote.

The same argument applies to the model's output, and the mechanism is the same schema. That is the reframe. Structured output is not an agent technique you are learning now; it is a general discipline you learned in Theme B, now applied to the one component that can't be trusted to follow instructions perfectly.

What is an output constraint?

A JSON Schema attached to the request. The model's response is forced to conform — not asked politely in the prompt, constrained.

The difference matters. "Please reply in JSON with these fields" works most of the time and fails unpredictably: a stray sentence before the brace, a missing field, an invented enum value. A real output constraint doesn't have a failure mode you have to parse around.

This also changes how the model reasons. A required evidence array with a minimum length means a finding without a citation is not expressible. The schema doesn't ask for rigour — it removes the alternative.

There is a second thing to notice, and it is the reason this sub-task is only 45 minutes: constraining the output shape usually improves the judgment, not just the format. Ten named categories force a decision that prose lets the model dodge with "this may warrant further review." A required severity means it has to commit.

Cost, honestly

usage gives you tokens. Tokens times the model's published rate gives you dollars. Look up the current rate rather than trusting a number from a course page — prices change, and a stale figure in a client deck is worse than no figure.

What you want out of today is the per-account cost of a judgment call, because that number multiplied by 166 is the quarterly bill and you can compute it in your head. Sub-task 34 does it properly, with wall-clock time attached. Today is the estimate.

Task 1

Constrain the call to the contract

  1. Re-issue the sub-task 13 call with the findings schema as an output constraint.

    Why: the schema describes a list of findings; a single call about a single account should produce one finding object, or a signal that there's nothing to report. Take the item schema out of findings.schema.json rather than retyping it — a hand-copied schema drifts, and drift here means the model produces output your own validator rejects.

    the shape — write your own 
    import json, anthropic

schema = json.load(open("src/meridian_capstone/contract/findings.schema.json"))
item = schema["items"]                # the per-finding schema, straight from the contract

response = client.messages.create(
    model="claude-sonnet-5",
    max_tokens=1024,
    system="<same reviewer framing as sub-task 13>",
    output_config={"format": {"type": "json_schema", "schema": item}},
    messages=[{"role": "user", "content": dossier("A000012")}],
)

finding = json.loads(response.content[0].text)
  2. Validate the result against the contract — the same way you validated your hand-built findings.

    Why: constrained output should validate by construction. Check anyway, every time. The schema you passed and the schema you validate against must be the same file, and asserting that is one line.

    terminal 
    python -c "
import json, jsonschema
schema = json.load(open('src/meridian_capstone/contract/findings.schema.json'))
jsonschema.validate([json.load(open('one_finding.json'))], schema)
print('valid')
"
  3. Compare it, field by field, against the prose verdict from sub-task 13.

    Why: this is where the interesting thing shows up. Very often the prose hedged and the structured version commits — and occasionally the commitment is to something the prose never actually said. Check the category against the enum, the severity against what the prose implied, and the confidence against how hedged the prose was. A confidence of 0.95 attached to reasoning that said "it appears possible that" is a real signal, and it's the kind of thing sub-task 33 will grade systematically.

Stuck?

The API rejects my schema. Output constraints don't accept every JSON Schema feature. Numeric bounds, string length limits and recursive references are common casualties. Strip the unsupported keywords from the copy you send and keep validating against the original — the contract stays the contract.

Every object needs additionalProperties: false. The findings contract already sets it, which is convenient. Nested objects inside it may need it too.

It produced a finding for an account that shouldn't have one. A constraint that only expresses "a finding" makes "no finding" inexpressible — so the model invents one. That's a design defect in your schema, not a model failure. The fix belongs in sub-task 17, where "not a finding" becomes a legitimate result. Note it now.

Task 2

Put a number on one judgment

  1. Log input and output tokens for the call, and convert to dollars using the current published rates.

    Why: build the habit of logging usage next to every call now, while there is one. Retrofitting cost tracking onto a pipeline you already built is miserable, and Theme H assumes you didn't have to.

    the log line you want 
    {"account_id": "A000012", "model": "claude-sonnet-5",
 "input_tokens": ..., "output_tokens": ..., "usd": ...}
  2. Multiply out, and write the projection down.

    Why: 166 accounts reach the agent layer in your candidate set. One judgment call each gives you a first quarterly figure. It will be wrong — some accounts need more context, the real pipeline makes more than one call per account, and caching hasn't happened yet — but it's the right order of magnitude, and knowing the order of magnitude on day one is what stops a project going sideways in week six.

You're done when
  • One agent-produced finding for A000012 that validates against findings.schema.json — produced by the model, not by you
  • The schema you constrain with is read from the contract file, not retyped
  • A usage log line carrying input tokens, output tokens, and dollars
  • A written projection for one quarter, with its own caveats stated

You now have both halves of a finding: a machine-readable shape and a cost. What you do not have is any reason to believe the content is true.
