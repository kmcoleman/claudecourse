Get a verdict on one account from one model call

Depends on: Sub-task 12 — you need a candidate set and a working contract Time: ≈ 60 min Type: first agent · the model call
First appearance
model call tokens response.usage dossier

Theme B produced 1,919 grants that a rule can't settle. This is the first one you hand to a model.

Everything you have built so far is deterministic. Given the same files, your code produces the same ledger, the same candidates, the same two SoD findings, forever. That is the right way to build the parts that can be built that way — and it is why the remaining work is hard.

The 1,919 grants in your candidate set are the ones a rule couldn't settle. Not because you wrote bad rules, but because settling them requires reading a policy written in English, looking at a person's job title, and forming a view. That is judgment, and judgment is what the model is for.

This sub-task is the smallest possible version of that: one account, one prompt, one response, one verdict you read with your own eyes and decide whether you agree with.

What you'll understand and do

  • Explain what a model call actually is — text in, text out, tokens billed both ways
  • Assemble a candidate dossier: everything one account looks like, in one string
  • Get a written verdict on a real Meridian account and judge it yourself
  • Read response.usage and know what you just paid for

Concept

The one idea

An agent is a function call that happens to be expensive and non-deterministic.

Strip away the vocabulary and a model call is unremarkable: you send a string, you get a string back. There is no session, no memory, no state on the far end. The model knows exactly what you put in the request and nothing else — not your ledger, not last quarter's review, not the conversation you had with it five minutes ago unless you resent it.

What is a model call?

One HTTP request to the Claude API carrying a model name, a list of messages, and a cap on how long the reply may be. One response carrying content blocks and a usage object.

Stateless. Every call is the first call. If the model needs to know something, it has to be in the request.

Billed both directions. You pay for the tokens you send (input_tokens) and the tokens it generates (output_tokens), at different rates. Output is several times more expensive than input.

Non-deterministic. The same prompt can produce different words. That is not a bug to be engineered away; it is the reason sub-task 30 exists.

Two consequences follow immediately, and they shape the rest of this course.

Context is the whole product. A model that gives a bad verdict is usually a model that wasn't told enough. Before blaming the prompt, ask what a competent human reviewer would need on the desk in front of them to answer this — and check whether you put it in the request. That list is your dossier.

Every call has a price, and you should be able to say what it is. Not approximately, not "it's cheap" — a number. The usage object on every response gives you the raw material. Sub-task 34 turns that into a figure you can put in front of a client's manager. Start counting now, while there is one call to count.

Why one account, and why this one

You are going to run this on A000012, gabriel.villa. It is a good first case because a rule genuinely cannot settle it and a human can.

The account holds Vault / Admin — a privileged role on a crown-tier system. It was granted on 2025-05-18 by gateway.provisioning. The last login on that grant was 2025-11-14. The employee, E00365, is a Futures trader in Procurement, and is active.

Nothing there is a violation on its face. Whether it is a finding depends on how you read a sentence in a policy document — which is exactly the shape of every hard question in this domain.

Do this

Task 1

Get an SDK that can make one call and tell you what it cost

  1. Install the Anthropic SDK into your virtualenv.

    Why: the kit ships claude-agent-sdk, which drives Claude Code sessions. That is the right tool for Themes E–G, where an agent runs a loop and calls tools. It is the wrong tool for this — you want one bare call whose cost you can read off the response. Add anthropic alongside it; this is a deliberate addition, exactly like installing pandas in sub-task 8.

    terminal 
    pip install anthropic
python -c "import anthropic; print(anthropic.__version__)"
  2. Confirm your key is in the environment, not in a file you might commit.

    Why: sub-task 4 put ANTHROPIC_API_KEY in .env and .env in .gitignore. The SDK reads the environment, not the file — export it, or load it with python-dotenv. Never pass a key as a literal in code.

Task 2

Build the dossier before you write a word of prompt

  1. Write a function that takes an account_id and returns everything you know about it as one readable block of text.

    Why: the intent is "assemble the desk a reviewer would need", not "format a prompt". Pull from the artifacts you already built — ledger.csv for grants, identities.csv for the person, the raw exports for tickets and prior review. Keep it plain and labelled; the model reads English better than it reads your column names.

    what a good dossier contains 
    account:      id, name, matched employee (and how confident that match is)
person:       title, department, employment type, status, hire/term dates
grants:       every app/role on this account, with granted_date, granted_by, last_login
tickets:      any access request naming this account
prior review: what a reviewer decided about this account last quarter
as-of date:   the quarter end you are reviewing against

    The last line matters more than it looks. "Has this account been used recently?" is meaningless without a date to be recent relative to. Derive it from the quarter — 2026-Q3 ends 2026-09-30 — rather than typing it in. Sub-task 38 will come back for anyone who typed it in.

  2. Print the dossier for A000012 and read it as if you were the reviewer.

    Why: check it against the numbers below before you spend a token. A dossier missing the last-login date will produce a confident verdict about dormancy based on nothing, and you will not be able to tell.

    expected content — A000012 
    account_id    A000012        account_name  gabriel.villa
employee_id   E00365         title         Futures trader
department    Procurement    status        active
grants        13 total, including Vault / Admin
Vault/Admin   granted 2025-05-18 by gateway.provisioning
              last_login 2025-11-14
tickets       none referencing this account
as-of         2026-09-30 (quarter end, 2026-Q3)
Stuck?

My dossier has 15 grants, not 13. You're reading the raw entitlements.csv rather than your de-duplicated ledger, or you're matching on account_name instead of account_id. Use the ledger.

I can't find a ticket and I think that's a bug. It isn't. There are 85 tickets for 1,200 accounts — most accounts have none. "No ticket" is a fact about this account, and it belongs in the dossier stated explicitly rather than by omission. A silent absence and a stated absence read very differently to a model.

Task 3

Make the call and read what comes back

  1. Send the dossier to Claude and ask for a prose verdict.

    Why: intent, not incantation. You want a short written judgment on whether this access should be revoked, reviewed, or retained — with the reasoning visible, so you can disagree with it. Say who the model is (an access reviewer at a regulated utility), give it the dossier, and ask the question. Don't ask for JSON yet; that's sub-task 14, and reading the prose first is the point.

    the call — shape only, write your own prompt 
    import anthropic

client = anthropic.Anthropic()          # reads ANTHROPIC_API_KEY from the environment

response = client.messages.create(
    model="claude-sonnet-5",
    max_tokens=1024,
    system="<who the model is and what it is being asked to do>",
    messages=[{"role": "user", "content": dossier("A000012")}],
)

print(response.content[0].text)
print(response.usage)

    A note on the model name: claude-sonnet-5 is the judgment workhorse for this course — strong enough for the reasoning, cheap enough to iterate on. Sub-task 35 makes you justify that choice against the alternatives with measurements rather than vibes.

  2. Read the verdict properly — then decide whether you agree.

    Why: this is the actual exercise. Not "did it work" but "is it right". You have the same facts it had. Form your own view of A000012 first, then compare. Agreeing is fine. Disagreeing is more interesting, and both go in the worksheet.

    My first agent verdict

    Write this before you move on. Sub-task 19 re-runs the same account with Skills loaded, and sub-task 31 scores the pipeline against verdicts you wrote yourself. This is the first entry in that record.

    Saved in this browser
  3. Look at response.usage and write the two numbers down.

    Why: input_tokens is what your dossier and system prompt cost to send. output_tokens is what the verdict cost to generate. A dossier for one account is small — a few hundred tokens. Multiply by 166 candidate accounts in your head and notice that the number stops being negligible. That multiplication is the whole of Theme H's cost argument, and you can do it today.

    what usage looks like 
    Usage(input_tokens=..., output_tokens=..., cache_creation_input_tokens=0,
      cache_read_input_tokens=0)

    The two cache fields are zero and will stay zero until sub-task 36. Note that they exist; that's a lever you haven't pulled yet.

  4. Commit the script.

    Commit the dossier builder and the call script. Do not commit the response — it isn't reproducible, and it'll be different next run anyway.

Stuck?

Authentication error. The SDK reads the process environment. echo $ANTHROPIC_API_KEY in the same shell you're running from — if it's empty, .env exists but was never exported.

The verdict is vague and hedging. Usually a thin dossier. Print exactly what you sent and read it as a stranger would: could you reach a verdict from that text alone? If not, the model can't either.

It refused to give a recommendation without more information. That's a defensible answer and worth recording. It's also a preview of sub-task 32, where "I don't know" becomes a first-class output rather than a failure.

The response got cut off mid-sentence. max_tokens is a hard ceiling. Raise it. It caps output length, not quality.

You're done when

You have made a real model call about a real Meridian account, and:

  • A dossier(account_id) function that assembles one account's full picture from your own artifacts, with the as-of date derived from the quarter
  • A written verdict on A000012 that you have read and formed an opinion about
  • Your own independent verdict, written down before you decided whether you agreed
  • The input and output token counts for that one call

That is your first agent. It is one function call, and it is genuinely an agent — a model given context and asked to exercise judgment. Everything else in this course is that, with more structure around it.

Next: the verdict is prose, which means nothing downstream can consume it. Sub-task 14 constrains it to the schema you already own.
