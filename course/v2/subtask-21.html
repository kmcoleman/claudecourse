Call Meridian's systems by hand over MCP

Depends on: Sub-task 20 — you need the blast-radius framing Time: ≈ 60 min Type: tools · MCP
First appearance
MCP .mcp.json stdio server per-entity lookup

Seven read-only tools over Meridian's systems. You call all seven yourself before any agent does.

The kit ships an MCP server. It exposes Meridian's HR, identity and ticketing systems as seven read-only tools, each answering a question about one entity: this employee, this account, this application.

It is deliberately the opposite of the Ledger. The Ledger is bulk — fifteen thousand rows, joined once, in code. These tools are targeted — one account, at the moment a judgment needs a fact. Getting that distinction right is most of what separates a system that works from one that costs a fortune and times out.

This sub-task is entirely by hand. You call all seven on one account and read what comes back.

What you'll understand and do

  • Explain what MCP is and what a stdio server actually is
  • Start meridian-systems and confirm all seven tools are visible
  • Call every tool on one account and read the responses
  • State clearly why bulk reconciliation must not go through these tools

Concept

The one idea

MCP is how an agent reaches a system it doesn't own.

The Model Context Protocol is a standard for exposing tools and data to a model. A server declares what it offers; a client discovers that list and can call it. The value is that neither side needs to know about the other in advance — you can point Claude Code at a server it has never seen and it will discover the tools.

What is a stdio server?

The simplest MCP transport. The client launches your server as a subprocess and talks to it over standard input and output. No port, no network, no auth, nothing to deploy.

Meridian's server is declared in .mcp.json at the repo root:

"meridian-systems": { "type": "stdio",
  "command": "python", "args": ["-m", "meridian_capstone.mcp_server.server"],
  "env": { "MERIDIAN_DATA_DIR": "data/2026-Q3" } }

Read that env line carefully. The server's idea of which quarter it is living in comes from there — not from anything your code passes at call time. Note it. Sub-task 37 is built on it.

A course simplification you should carry into real work

One server, seven tools, all of Meridian. In a real engagement these are separate systems with separate owners, separate credentials and separate refusal modes — a Workday connector, an Okta connector, a ServiceNow connector. Collapsing them into one server keeps the course focused on judgment rather than on integration.

What survives the simplification is the shape: read-only, per-entity, called at judgment time. What doesn't is the assumption that they all work, agree, and are up.

The rule that matters most. These tools answer questions about one thing. They are not how you load data.

You have 1,200 accounts. Reconciling them through get_account would be 1,200 subprocess round-trips to produce something you already built in seconds with a dataframe join — and it would produce it worse, because reconciliation needs to see the whole population at once. The ambiguous-slug analysis in sub-task 9 is impossible one account at a time; you can only know that jacob.miller is ambiguous by looking at every jacob.miller.

Reconciliation is code, over files, in bulk. Judgment is agents, over MCP, one entity at a time. That line is in your CLAUDE.md from sub-task 7, and this is the sub-task where it stops being a slogan.

Do this

Task 1

Start the server and see the tools

  1. Read .mcp.json and src/meridian_capstone/mcp_server/server.py.

    Why: the server is about 120 lines and reading it removes all the mystery. Each tool is a plain Python function with a decorator; the decorator is what turns a function into something a model can discover and call. That is the entire mechanism.

  2. Get Claude Code to connect to meridian-systems and confirm all seven tools are visible.

    Why: a configured-but-not-connected MCP server behaves exactly like a server with no tools, silently. Confirm the connection before you debug anything else.

    the seven tools 
    get_employee(employee_id)                  one HR record
get_account(account_id)                    every grant on one account
search_tickets(account_id, app=None)       access requests for an account
get_prior_review(account_id)               last quarter's decisions
get_application(app_name)                  tier, roles, privileged roles, owner
is_approved_service_account(name)          is this a registered service account
get_sod_matrix()                           the conflict rules and exemptions

    Six of the seven take an entity identifier. The seventh, get_sod_matrix, returns a small shared reference document. That is the natural shape of a judgment-time tool surface — mostly lookups, occasionally a rule book.

Stuck?

The server won't start. The command is bare python, so it resolves against whatever is on PATH when Claude Code launches it — not necessarily your activated virtualenv. If the module isn't found, that's the cause.

It connects but returns nothing. MERIDIAN_DATA_DIR is relative, so it resolves against the working directory the server was launched from. Launch from the repo root.

Do I have to restart to pick up .mcp.json? Yes — same watcher behaviour as Skills and agents. Config read at startup, changes need a restart.

Task 2

Call all seven on one account

  1. Run every tool that applies to A000012 — gabriel.villa, the account you have been judging since sub-task 13.

    Why: you know this account well, which makes it the right one for seeing what the tools add and what they don't. Call them by hand, one at a time, and read each response before moving on.

    expected — A000012 
    get_account("A000012")              13 grants, incl. Vault / Admin
get_employee("E00365")              gabriel.villa, Futures trader,
                                    Procurement, active
search_tickets("A000012")           [] — no access request, ever
get_prior_review("A000012")         5 rows: Badge access, Atlas ERP,
                                    VPN, Zoom, Active Directory
get_application("Vault")            tier crown, privileged_roles [Admin],
                                    owner Information Technology
is_approved_service_account("gabriel.villa")   False
get_sod_matrix()                    6 conflicts, 1 exemption (ACP-4.2)
  2. Notice what get_prior_review just told you.

    Why: five prior-review rows for this account, and Vault is not among them. The one privileged grant on a crown-tier system — the grant that is actually the finding — was never reviewed last quarter. Badge access was. Zoom was.

    Then look at the file as a whole: 5,752 prior-review rows, of which 5,749 are approved and 3 are conditional. Nothing was ever rejected. That is a rubber stamp, and it means "approved last quarter" carries almost no information. Anyone building a rule that trusts prior review has just built a rule that always says yes.

    Neither of those facts was in your dossier. Both change how you read this account. That is what tools are for.

  3. Put the tool responses next to your ledger row for the same account.

    Why: the overlap is the point. get_account returns the same grants your ledger has — the tool is reading the same export. What it adds is reach: prior review and application metadata were never in your ledger at all, and pulling them for all 1,200 accounts up front would have bloated every dossier for the benefit of the few that need them.

  4. Confirm they are read-only by trying to break something.

    Why: read the tool list again and satisfy yourself there is no revoke_access, no close_ticket, no update_account. The blast radius of this entire server is zero writes. For an observational exercise that is the correct design, and it's worth being able to state it plainly to a client who asks what the agent could do to their production identity system.

Stuck?

get_employee needs an employee_id I don't have. Correct, and instructive. The exports share no key — that was Theme B's entire problem. The employee_id comes from your reconciliation, which means these tools depend on work you did earlier, and an unmatched account can't be looked up at all.

I noticed A000012 and E00365 share digits. They do, across almost the whole dataset — an artefact of how the export was generated, not a property of Meridian's systems. Sub-task 9 flagged it. Don't build on it.

search_tickets returns an empty list. That's the answer, not a failure. 85 tickets across 1,200 accounts means most accounts have none, and "no approving ticket" is half the Privileged Access Standard's test.
