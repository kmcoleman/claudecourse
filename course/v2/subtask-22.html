Let your agent look things up mid-judgment

Depends on: Sub-task 21 — you need the MCP server connected Time: ≈ 60 min Type: tools · the tool-use loop
First appearance
tool-use loop judgment-time retrieval tool-call trace

The last sub-task in Theme E, and the first time the agent decides what it needs to know.

Until now you have decided what the agent knows. You built the dossier; whatever you left out, it could not ask for.

That works while you know which facts matter. It stops working the moment a case is unusual — and the unusual cases are the entire reason a human reviews access instead of a script.

This sub-task inverts the flow. Give the agent the account and the tools, and let it decide what to look up. Then read the trace of what it chose.

What you'll understand and do

  • Understand the tool-use loop — the model asks, you execute, it continues
  • Grant your single-account agent the MCP tools
  • Capture a trace of which tools it called, in what order, and why
  • Compare judgment-time retrieval against the fixed dossier

Concept

The one idea

The loop is three lines. Everything agentic follows from it.

Sub-task 13 made a single call: prompt in, text out, done. Add tools and the shape changes.

The tool-use loop

1. You send the prompt, plus the list of available tools.

2. The model replies. Either it's finished, or it asks to call a tool with specific arguments.

3. If it asked, you execute the call, append the result to the conversation, and send the whole thing back. Return to 2.

That's it. An agent is this loop. Everything in Themes F and G is structure around it — who runs the loop, which tools are in the list, what gets checked before a call is allowed.

Two properties of the loop deserve attention before you run one.

The model chooses, and it will surprise you. You do not script the sequence. Given a dossier that mentions a Vault Admin grant, one run may pull the application metadata first to establish that Vault is crown-tier, another may go straight for tickets. Both are reasonable. The variation is real and it is what sub-task 30 measures.

Every iteration costs a full call. The conversation grows each time — every prior tool result is resent with every subsequent request. An agent that makes six tool calls has made seven model calls, each larger than the last. This is the single biggest driver of agent cost, and it is why sub-task 36's caching work matters as much as it does.

Judgment-time retrieval

The pattern this enables: ask for what you need, when you find you need it.

The alternative is loading everything up front, which for 1,200 accounts × seven systems is enormous, mostly irrelevant, and paid for on every call. Judgment-time retrieval pays only for what a specific case turned out to require, and different cases require different things — which is exactly the property a fixed dossier cannot have.

Do this

Task 1

Hand over the tools

  1. Give your single-account agent access to the seven meridian-systems tools.

    Why: the mechanism depends on how you're running the agent. Inside Claude Code the server is already connected, so this is mostly about prompting. Driving it yourself, you register the tools and write the loop. Either is fine — what matters is that the model can call them and you can see what it called.

  2. Thin the dossier down to a stub.

    Why: this is the experiment. Hand it the account ID and the barest context, and let it gather the rest. If you leave the full dossier in place, it has no reason to call anything and you learn nothing.

    the stub 
    account_id  A000012
as-of       2026-09-30 (quarter end, 2026-Q3)

Determine whether this account's access should be revoked, reviewed,
or retained. Look up whatever you need.

    Keep the as-of date. That is genuinely something the agent cannot derive — it's a property of the review, not of the data — and omitting it produces confident dormancy reasoning against an unstated baseline.

  3. Run it and capture the trace.

    Why: you want the sequence of calls with their arguments, not just the final verdict. Record tool name, arguments, and order.

    a plausible trace — yours will differ 
    1  get_account("A000012")                    → 13 grants, Vault/Admin
2  get_application("Vault")                  → crown, Admin is privileged
3  search_tickets("A000012", "Vault")        → []
4  is_approved_service_account("gabriel.villa") → False
5  get_employee("E00365")                    → Futures trader, Procurement
   verdict: revoke

    Read that as reasoning, because it is. It found a privileged grant, checked whether the application is one where that matters, looked for the approving ticket the standard requires, ruled out the break-glass exemption, and checked whether the job title plausibly justifies Vault admin in the first place. A different run may take a different route to the same place.

Stuck?

It called nothing and guessed. Either the tools weren't actually available, or the stub still contained enough to answer from. Check the tool list reached the model, then thin the stub further.

It called the same tool repeatedly. Usually a loop that isn't appending results correctly — the model asks again because it never saw the answer. Check that each tool result is added to the conversation before the next request.

It called eleven tools for one account. Not necessarily wrong, but worth pricing: eleven calls is twelve model requests. If the extra calls aren't changing the verdict, tell it what a sufficient basis looks like. That's a real design decision, not a bug.

Task 2

Compare against the fixed dossier — both directions

  1. Diff this verdict against the sub-task 19 verdict on the same account.

    Why: same account, same Skills, same model. The only change is who decided what facts to gather. Compare the recommendation, the evidence cited, and the rationale — and specifically check whether it found anything your dossier didn't contain. Prior review is the likely candidate, and Vault's absence from it is a genuinely useful observation you never fed it.

  2. Run it on a case your dossier design didn't anticipate.

    Why: A001185 (anita.richardson, contractor overstay) is a good second case, because the relevant facts are different in kind — a term_date, a ticket that looks like a renewal, and the question of what that ticket actually authorises. Watch whether it calls search_tickets and then reasons about what the ticket doesn't say.

    This is the real argument for judgment-time retrieval. A dossier builder tuned for dormant admins gathers the wrong facts for a contractor. An agent with tools gathers what the case needs.

  3. Count the cost of the loop.

    Why: sum usage across every iteration, not just the last. Compare it to the single call from sub-task 14. The multiple is the price of retrieval, and you want to be able to state it before someone asks. Note also that the growth isn't linear — each request carries all previous results, so call six is much more expensive than call one.

  4. Commit.

    The agent changes. Not the traces — they won't reproduce.

Stuck?

The verdict got worse with tools. Genuinely possible and worth investigating rather than reverting. Common cause: it gathered less than your dossier contained and stopped early. The fix is usually to say in the prompt what a sufficient basis looks like — for a privileged grant, the grant itself, the ticket position, and the exemption check.

It trusted prior review. Excellent — you've caught something real. 5,749 approvals out of 5,752 means "approved last quarter" is close to information-free, and an agent treating it as evidence is drawing a conclusion from a rubber stamp. This belongs in a Skill, not in the prompt: whichever policy Skill governs the finding should say what prior review is worth.

Should the dossier go away entirely? No. The pragmatic design is a thin dossier with the facts every case needs, plus tools for what a specific case turns out to require. Pure retrieval pays a loop for facts you knew you'd need anyway.

You're done when
  • Your agent can call the seven meridian-systems tools and chooses which to use
  • A tool-call trace for A000012 with names, arguments and order
  • A second trace on a case of a different shape — a contractor rather than a dormant admin
  • Total loop cost measured against the single-call baseline
  • A stated position on when judgment-time retrieval earns its cost and when it doesn't

Theme E is complete, and building block three with it. Your agent has knowledge from Skills and reach from tools, and you have a blast-radius table saying which capabilities each part of the system should get.

What you have is still one agent doing everything. Theme F splits it into three, gives each the minimum tools from your table, and hands exactly one of them the ability to write.
