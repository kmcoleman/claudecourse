Write Rules that visibly change how Claude behaves

First appearance
Rules CLAUDE.md

The first of the six building blocks. After this sub-task, Theme A is complete.

Everything so far has been preparation. This is the first of the six building blocks you mapped in sub-task 1 — and the simplest: a file of standing instructions that Claude reads at the start of every session.

The reason it goes first is that it's the cheapest possible demonstration of the course's real subject. You'll take a prompt that produced behaviour you didn't want, write down a rule, and run the same prompt again. Same question, different answer — and you changed nothing but a text file.

What you'll understand and do

  • Explain what CLAUDE.md is and when a rule belongs in it
  • Write project rules that are specific enough to actually change behaviour
  • Demonstrate the change with a before-and-after pair of transcripts

Concept

The one idea

A rule is a correction you only have to make once.

You've now had several sessions with Claude Code. You've probably repeated yourself: don't change that file, show me the count, don't paste the data in. Every one of those repetitions is a rule you haven't written down yet.

Rules — building block one — live in a file called CLAUDE.md at the root of your project. Claude reads it at the start of every session, so anything in it applies to every task without you asking. This repository already has one; you'll read it, then extend it.

What is CLAUDE.md?

A plain markdown file of persistent project instructions. No special syntax — headers and bullets. It's shared through git, so a rule you write applies to your whole team.

Rule of thumb for what goes in: anything you've had to say twice. Build commands, conventions, things that must never be touched, how to check work is correct. Keep it short — under about 200 lines. Long files get followed less reliably, not more.

The honest limitation, stated up front. CLAUDE.md is context, not enforcement. Claude reads your rules and tries to follow them, but nothing blocks a violation. Specific, concrete rules are followed far more reliably than vague ones — "don't paste more than 50 rows of CSV into your reply" beats "be careful with data" — but a rule is guidance.

When something must be impossible rather than discouraged, you need a different block: Hooks, number five on your map, which run as actual code and can refuse. Rules are the cheap 80%; hooks are the guarantee. Knowing which you need is a large part of designing these systems well.

Do this

Task 1

Capture the "before"

  1. Read the rules that already exist.

    Why: this repository ships a CLAUDE.md. Open it in VS Code and read it — it names a frozen function signature, says reconciliation is done in code while judgment is done by agents, and points at the test suite as the green light. Every one of those is a correction someone got tired of repeating.

  2. Run a prompt that invites the behaviour you don't want — and save what you get.

    Why: you need a documented "before". Start a fresh session (/clear) and ask:

    prompt · before 
    Show me the entitlements data for Q3 and tell me which accounts look risky.

    That file has 15,188 rows across 22 applications. The prompt quietly invites two bad habits: dumping bulk data into the conversation, and calling accounts "risky" against no stated policy. Watch how much data comes back, and whether it says what "risky" means.

    Copy the reply into your notes as BEFORE.

Stuck?

It behaved well — it didn't dump anything. Quite likely; the existing CLAUDE.md is already doing work, and that's a finding in itself. Note precisely what it did do. You can still improve it: did it define "risky"? Did it cite a policy? Did it show its evidence? Aim your new rules at whatever it left vague.

It dumped hundreds of rows into my terminal. Perfect — you have a vivid BEFORE. That's slow, expensive, and in a real engagement it's client data sprayed into a transcript.

Task 2

Write the rules

  1. Add a rules section to CLAUDE.md.

    Why: three rules, each aimed at something real you've seen. Open CLAUDE.md in VS Code and append:

    claude.md 
    ## My working rules

- **The contract is frozen.** Do not change the signature of
  `run_review(export_dir, limit)` in
  `src/meridian_capstone/contract/run_review.py`. If a task seems to
  need a different signature, stop and tell me instead.
- **Never paste bulk data into a reply.** Read files with tools and
  report aggregates — counts, distinct values, a handful of example
  rows. Never more than 20 rows of any CSV in your response.
- **Tests are the green light.** After changing code, run
  `pytest -m "not api"` and report the exact pass/skip/fail counts.
  Do not describe work as done without that output.
- **Cite evidence for judgments.** Any claim that an account or person
  is risky must name the policy or rule it violates and the file the
  evidence came from. If no policy covers it, say so.

    Notice the shape: each is concrete enough to check. "Never more than 20 rows" can be violated observably; "be careful with data" cannot.

  2. Add one rule of your own, aimed at your sub-task 1 headache.

    Why: this is where the course stops being about Meridian. What would you always want an assistant working on your problem to know or never do? A system it must never write to, a stakeholder whose sign-off is required, a definition your organisation uses differently from everyone else.

Task 3

Capture the "after" and mark the difference

  1. Start a completely new session and run the identical prompt.

    Why: CLAUDE.md is read at session start, so a running session won't have picked up your edit. Exit fully (/exit) and start claude again — don't just /clear.

    prompt · after (identical) 
    Show me the entitlements data for Q3 and tell me which accounts look risky.

    Same words. Different behaviour: aggregates instead of dumps, and either cited reasoning or an honest statement that no policy covers it yet.

  2. Mark the difference explicitly.

    Why: "it seemed better" isn't a result. Name which rule caused which change — that's what makes this a demonstration rather than an impression.

    Before / after

    Be specific. Quote both transcripts where you can.

    Saved in this browser
  3. Confirm you didn't break anything, then commit.
    terminal 
    pytest -m "not api"
git add CLAUDE.md
git commit -m "Add my working rules to CLAUDE.md"

    Still 33 passed, 11 skipped, 1 deselected — editing rules doesn't touch code. But running the check anyway is the habit, and you just wrote a rule demanding exactly that.

Stuck?

Nothing changed between before and after. Check the file is at the repository root and named exactly CLAUDE.md. Inside a session, run /context and look for it under Memory files — if it isn't listed, Claude never saw it. And confirm you fully restarted rather than /clearing.

It followed some rules and ignored others. That's the honest behaviour of a guidance mechanism, and it's worth writing in the last box. Look at the ignored one — is it vaguer than the others? Vague rules lose. If it must be guaranteed, you're looking at a job for Hooks.

My rules contradict the existing ones. Resolve it rather than leaving both. Contradictory rules get resolved arbitrarily, which is the worst of all worlds.

You're done when

You have two transcripts of the same prompt — before and after your rules — with the differences marked and attributed to specific rules. Plus:

  • CLAUDE.md contains your rules, including one aimed at your own headache
  • pytest -m "not api" is still green
  • Your rules are committed
