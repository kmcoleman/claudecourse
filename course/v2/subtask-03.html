Run the kit's green light and read what it tells you

Depends on: Sub-task 2 — you need git and a terminal Time: ≈ 60 min Type: installation + verification
First appearance
Python virtual environment (venv) pytest skipped vs failed

The kit's test suite is the green light you'll return to after every change for the rest of the course. Today you learn to read it.

The course ships with a kit: the Meridian data, some starter code, and — the part that matters — a test suite. That suite is your green light. Every time you change something from here on, it's the thing that tells you whether you broke it.

So the goal today isn't just to get the tests passing. It's to run them and be able to explain every line of what comes back — including the eleven tests that don't run at all. Reading that output correctly is a skill, and most people get it wrong the first time in a way that quietly costs them later.

What you'll understand and do

  • Explain what a virtual environment is and why this project insists on one
  • Install the kit and run its offline test suite
  • Tell the difference between a skipped test and a failed one — and explain why 11 skips is the correct result today

Concept

The one idea

A skip is not a failure. Confusing the two will cost you a day.

When you run the tests today, you'll get something like 33 passed, 11 skipped, 1 deselected — and no failures. Many people see "11 skipped" and assume something is broken. Nothing is broken. Those eleven tests are checking work you haven't done yet, and they're politely standing down until you have.

This is a deliberate design in the kit, and it's the single most useful thing about it: as you complete later sub-tasks, skips turn into passes. The suite is a progress bar. But only if you can read it — which means knowing, for each skip, which future piece of work it's waiting on.

What is Python, and what is a virtual environment?

Python is the programming language this kit is written in. You will not be writing much of it by hand — but you'll read a lot of it, and you need it installed to run anything.

A virtual environment (venv) is a private box of Python packages that belongs to one project. Without one, every project on your machine shares a single set of libraries, and two projects that need different versions of the same library will break each other. With one, this project's dependencies sit in a .venv folder inside the project and touch nothing else. You activate it to step inside, and everything you install goes in that box.

What is pytest?

The tool that finds and runs the kit's tests. Each test is a small function that makes one claim about the code and checks it. Run them all and you get a one-line verdict on whether the project is in a good state.

Its output uses one character per test: . passed, s skipped, F failed. A line of dots with a few ss in it is a healthy run. A single F is the thing you stop and read.

What "deselected" means. One test in the kit makes a real, billable call to Claude. It's tagged so you can exclude it, and -m "not api" is what excludes it — that's the 1 deselected. You'll switch it on in sub-task 4. Until then, every check you run is free and offline.

Do this

Task 1

Get the kit and open it

  1. Clone the course repository.

    Why: git clone copies a repository — with its whole history — onto your machine. Your instructor supplies the URL; paste it in place of the placeholder.

    terminal 
    git clone <repository-url>
cd claudecourse
  2. Look around before you run anything.

    Why: thirty seconds of orientation now saves a lot of confusion later. ls (macOS) or dir (Windows) lists what's here.

    terminal 
    ls

    Four things to notice: data/ holds Meridian's exports, src/ holds the kit's code, tests/ holds the green light, and CLAUDE.md is a rules file you'll meet properly in sub-task 7.

Task 2

Build the box and install the kit into it

  1. Create the virtual environment.
    terminal 
    python3 -m venv .venv

    On Windows use python -m venv .venv. This creates a .venv folder. The leading dot just means most file browsers hide it. Nothing has changed about your machine yet — you've only built an empty box.

  2. Activate it.

    Why: this is the step people forget, and forgetting it is the cause of roughly half of all "it doesn't work" moments in this course.

    terminal · macos 
    source .venv/bin/activate
    powershell · windows 
    .venv\Scripts\Activate.ps1

    Your prompt should now start with (.venv). That prefix is the whole point — it's how you know you're inside the box. It disappears every time you close the terminal, so expect to run this line at the start of every working session.

  3. Install the kit.
    terminal 
    python -m pip install -e ".[dev]"

    This reads the project's dependency list and installs it into your venv. The -e means "editable" — the installed kit points at these files rather than copying them, so your edits take effect immediately. The [dev] adds pytest. Expect a wall of scrolling text ending in Successfully installed.

Stuck?

Windows: "running scripts is disabled on this system". PowerShell blocks scripts by default. Run Set-ExecutionPolicy -Scope CurrentUser -ExecutionPolicy RemoteSigned, answer Y, then activate again. This affects only your own user account.

There's a shortcut, by the way. The kit ships a script that does all of Task 2 in one go: bash scripts/bootstrap.sh on macOS, or powershell -ExecutionPolicy Bypass -File scripts\bootstrap.ps1 on Windows. Use it if you get stuck — but read the steps above first, because when something breaks later you'll need to know what it did.

"pip: command not found". Use python -m pip rather than bare pip — that's why the command above is written that way. If python isn't found either, try python3.

I closed my terminal and everything broke. You left the box. cd back to the project folder and activate again. This will happen more than once; it's normal.

Task 3

Run the green light, then make it explain itself

  1. Run the offline test suite.
    terminal 
    pytest -m "not api"

    The -m "not api" excludes the one test that costs money. Expect roughly this:

    pytest -m "not api"
    .............s...................sssssss. [100%] 33 passed, 11 skipped, 1 deselected in 0.70s

    Your numbers should match. What matters is zero failures.

  2. Now ask pytest why it skipped those eleven.

    Why: this is the actual lesson. The -rs flag means "report the reason for each skip". Well-written tests explain themselves, and these do.

    terminal 
    pytest -m "not api" -rs

    You'll get a block like this:

    SKIPPED [1] tests/test_ledger.py:38: No Day 2 artifacts found at the repository root... SKIPPED [1] tests/test_skills.py:38: No .claude/skills/ directory found... SKIPPED [1] tests/test_pipeline.py:31: No .claude/agents/ directory found... SKIPPED [1] tests/test_hooks.py:163: No hooks configured in .claude/settings.json yet... SKIPPED [7] tests/test_transfer.py: findings.2026-Q4.json not produced yet...

    Read every line. Each one names a thing you haven't built yet — the ledger, the skills, the subagent pipeline, the hooks, the second-quarter run. Those are the six building blocks from sub-task 1, waiting for you.

  3. Write one line in your notes: what has to become true for the skips to become passes?

    Why: this reframes the whole course as a single measurable goal. You now have an objective definition of "finished" that doesn't depend on anyone's opinion — including mine.

Stuck?

"pytest: command not found". Either the venv isn't active (check for (.venv) in your prompt) or the install didn't finish. Reactivate, reinstall, retry.

I get failures, not skips. That's worth stopping for. Read the first failure only — later ones are often knock-on effects. The most common cause is running from the wrong folder: you must be in the repository root, the folder containing pyproject.toml.

My numbers are slightly different. If you have zero failures and around eleven skips, you're fine — the kit evolves. If passed is much lower than 33, something didn't install.

The skip messages mention "Day 2", "Day 4" — but this course has sub-tasks. Correct, and mildly confusing. The kit's test messages use the course's earlier day-based names. Map them by building block: ledger, skills, subagents, hooks, transfer.

You're done when

pytest -m "not api" reports 33 passed, 11 skipped, 1 deselected with no failures — and you can answer these three without looking:

  • Why is a skip not a failure here?
  • What is the 1 deselected test, and why is it excluded?
  • Name two things that must exist before some of those skips become passes.
