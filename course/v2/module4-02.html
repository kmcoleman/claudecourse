Let a human disagree with the model

Depends on: Module 4 · 1 — you need findings rendering in a table Time: ≈ 60 min Type: elective — not a building block
First appearance
recommendation vs decision stable finding key localStorage attestation

The distinction in the first term is the whole sub-task. The other three are how you keep it intact.

Your system says revoke. The reviewer says no — that account belongs to a contractor whose SOW was extended last week and the export predates it. Both of those facts are now true, and a UI that stores one of them has destroyed evidence.

An access review is an attestation. Its output is not a list of what should happen; it's a record of who looked at what and what they concluded. The model's judgment is an input to that record, not the record itself.

What you'll understand and do

  • Keep the model's recommendation and the human's decision as two separate fields, always
  • Give each finding an identity that survives a re-run
  • Persist decisions in localStorage and understand exactly what that promises
  • Require a reason when the human overrides the model

Concept

The one idea

Never let the human's decision overwrite the model's recommendation. Store both.

It's a tempting simplification — one status field, updated in place, obviously cleaner. It also erases the only measurement that tells you whether the system is any good.

With both fields you can answer the question every second engagement opens with: how often does the human disagree, and on what? A 4% override rate concentrated in one category is a policy Skill that needs a clause added. A 40% override rate is a system that isn't ready and a conversation you want to have from data rather than from vibes. Sub-task 31 had you hand-label twelve dossiers to get a number like this. Once the UI exists you get it continuously, for free, from real reviewers on the whole quarter.

Approve, deny, defer — and what each one means

Approve — the reviewer agrees with recommendation, whatever it was. Approving a retain is a decision, not a no-op.

Deny — the reviewer rejects the recommendation. This is the one that needs a reason, and the one your eval pipeline should be reading.

Defer — the reviewer can't decide with what's on screen. Usually it means they need to ask the account owner. Defer is not an unanswered finding; it's an answered one whose answer is "escalate", which is exactly the human-in-the-loop path you specified in sub-task 32.

Why the array index is the wrong key

Store decisions as decisions[3] and everything works until the pipeline runs again. A finding is resolved, the array shortens, and every decision after index 3 now points at a different account — silently, with no error, in a compliance artifact.

Key on what the finding is about: scope + account_id + app + entitlement + category. Stable across runs, distinct between the same account's two conflicting entitlements, and it survives the findings being reordered by severity the moment they load — which sub-task 1 already does.

What localStorage actually promises. Roughly 5 MB of strings, scoped to one origin, on one browser profile, on one machine, cleared by "clear browsing data" without warning. It is the right tool for a single reviewer working through a quarter in one sitting on their own laptop — which is genuinely the common case — and the wrong one for anything two people touch.

The origin gotcha that will bite you

file:///Users/you/repo/reviewer/index.html and http://localhost:8000/reviewer/ are different origins. So are localhost:8000 and localhost:8001.

Decisions saved under one are invisible under another. Not corrupted — invisible, which is worse, because the page loads clean and empty and looks like data loss. Pick one URL and put it in your runbook.

Sub-task 3 makes the decisions exportable, which is the real answer to all of this. localStorage is a working buffer between "the reviewer starts" and "the reviewer exports". Treating it as a database is where this design fails.

Task 1

Identity and storage

  1. Write the key function and prove it's unique across your quarter.

    Why: if two findings collide on a key, one reviewer decision silently covers both. Nine findings is small enough to check exhaustively, and the check is two lines — run it now rather than discovering the collision in Q4.

    reviewer/index.html — script 
    // A finding's identity is what it is about — never where it sits in the array.
function keyOf(f) {
  return [f.scope, f.account_id || "", f.app, f.entitlement || "", f.category].join("|");
}

// Prove it: distinct keys must equal finding count.
var keys = findings.map(keyOf);
console.assert(new Set(keys).size === findings.length, "key collision", keys);
  2. Load and save decisions under a quarter-scoped storage key.

    Why: meridian-decisions-2026-Q3, not decisions. When you point the page at Q4 — and Theme I says you will — the two sets stay separate instead of merging into one bucket where the keys happen not to collide and the provenance is gone.

    reviewer/index.html — script 
    var QUARTER = "2026-Q3";
var STORE = "meridian-decisions-" + QUARTER;

function loadDecisions() {
  try { return JSON.parse(localStorage.getItem(STORE)) || {}; }
  catch (e) { return {}; }        // corrupt value must not blank the page
}
function saveDecisions(d) {
  try { localStorage.setItem(STORE, JSON.stringify(d)); }
  catch (e) { alert("Could not save — storage may be full or disabled."); }
}

var decisions = loadDecisions();
  3. Record both verdicts in every entry.

    Why: model_recommendation is copied in at decision time, not looked up later. A re-run can change what the model says; the record has to preserve what it said when the human decided, or the override rate you compute next quarter is measuring the wrong thing.

    reviewer/index.html — script 
    function decide(f, verdict, note) {
  decisions[keyOf(f)] = {
    verdict: verdict,                          // approve | deny | defer  — the human
    model_recommendation: f.recommendation,    // revoke | review | retain — the model
    note: note || "",
    reviewer: document.getElementById("reviewer").value || "unattributed",
    decided_at: new Date().toISOString()
  };
  saveDecisions(decisions);
}
  4. Add a reviewer-name field at the top of the page.

    Why: an attestation with no attester is not an attestation. One text input, persisted alongside the decisions, stamped into every entry. It takes two minutes and it's the difference between a decisions log and a list of opinions.

Task 2

The controls

  1. Add three buttons and a note field per row.

    Why: build them from the verdict list rather than writing three near-identical handlers — the fourth verdict someone asks for should be a one-word change. Repaint the row from state after every click so what's on screen is what's stored, always.

    reviewer/index.html — script 
    var VERDICTS = ["approve", "deny", "defer"];

function controls(f, tr) {
  var td = document.createElement("td");
  var note = document.createElement("input");
  note.type = "text";
  note.placeholder = "reason (required to deny)";

  VERDICTS.forEach(function (verdict) {
    var b = document.createElement("button");
    b.textContent = verdict;
    b.addEventListener("click", function () {
      if (verdict === "deny" && !note.value.trim()) {
        note.focus();
        return;                                  // a denial with no reason is not a record
      }
      decide(f, verdict, note.value.trim());
      paint(tr, f);
      updateProgress();
    });
    td.appendChild(b);
  });

  td.appendChild(note);
  tr.appendChild(td);
  return note;
}
  2. Paint decided rows so state is visible without clicking.

    Why: a reviewer coming back after lunch needs to see what's left in one glance. Colour the row by verdict, and mark the disagreements specially — deny against a revoke is the row you'll want to find again when someone asks why that account is still open.

    reviewer/index.html — script 
    function paint(tr, f) {
  var d = decisions[keyOf(f)];
  tr.className = d ? "decided " + d.verdict : "";
  // The model said revoke, the human said no. Worth seeing from across the room.
  if (d && d.verdict === "deny" && f.recommendation === "revoke") {
    tr.classList.add("override");
  }
}
  3. Add a progress counter and a filter for what's left.

    Why: "7 of 9 decided" is the number a reviewer is working toward, and a show-undecided-only toggle is what makes a hundred-finding quarter finishable. Both are derived from state you already have.

  4. Re-run the pipeline and confirm your decisions are still attached to the right findings.

    Why: this is the test the whole sub-task is built around. Decide three findings, re-run run_review, reload the page. Same three rows decided, same accounts. If anything shifted, the key isn't stable — and you've just reproduced the bug this design exists to prevent.

    terminal 
    python -m meridian_capstone.contract.run_review data/2026-Q3 > findings.json
# reload the page — the same three rows should still be decided
  5. Walk the whole quarter and write down what you learned doing it.

    Why: you are now the reviewer, which is a different seat from the one you've occupied for thirty-nine sub-tasks. Where did you disagree with your own system? Where did you need something the page didn't show you? That's the sub-task 3 backlog.

Stuck?

My decisions vanished. Check the address bar first. Almost every instance of this is file:// versus http://localhost:8000, or a port that changed because 8000 was busy. Different origin, different storage, no error.

They vanished and the URL is the same. Private browsing, or a browser set to clear site data on close. Open the console and run localStorage.getItem("meridian-decisions-2026-Q3") — that tells you in one line whether the write ever landed.

All my buttons decide the last row. A loop variable captured by reference. The forEach callback in the snippet gives each iteration its own scope; a for (var i…) loop does not.

The key collides on two findings. Same account, same app, same category, different entitlement — and one of the entitlements is null. Include scope in the key, which is what distinguishes the account-scoped from the application-scoped row.

Should defer count as decided? Yes. It's a conclusion with a follow-up attached, and treating it as undecided means your reviewer can never reach zero. Give it its own colour and export it as its own verdict.

You're done when
  • Every row has approve / deny / defer, and denying without a reason is refused
  • Each stored decision carries both the human verdict and the model's recommendation as it stood at decision time
  • The storage key is derived from the finding's content, not its position
  • Decisions survive a reload and a pipeline re-run
  • Every decision carries a reviewer name and a timestamp
  • A counter shows how many findings are left

A reviewer can now walk a quarter and record what they concluded. It's still trapped in one browser on one laptop — that's next.
