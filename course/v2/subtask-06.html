Break the same script three ways and name each failure

Depends on: Sub-task 5 — you need the intent prompt shape Time: ≈ 60 min Type: experiment + reference card
First appearance
traceback silent wrong answer hallucinated rationale

Three failure modes, three different reading methods. This card gets reused for the rest of the course.

Everything you build from here can fail in three distinct ways, and they need three completely different responses. Most people only recognise the first — which is unfortunate, because it's by far the least dangerous.

So you're going to cause all three deliberately, on a script small enough to hold in your head, and write down the tell and the first diagnostic move for each. Inducing failure on purpose, while the stakes are zero, is how you learn to spot it later when they aren't.

What you'll understand and do

  • Name the three ways an agentic system fails and recognise each one's tell
  • Explain why the loud failure is the safe one and the quiet one is not
  • Produce a reference card with a first diagnostic move for each mode

Concept

The one idea

The failure that shouts is the one you can afford. Learn to hear the quiet ones.

A crash is a gift. It stops, it tells you where, and nobody acts on its output because there isn't any. The other two modes produce clean, confident, well-formatted results that are wrong — and those flow straight into a report with your name on it.

1
The crash

The code stops and prints a traceback. Loud, specific, and honest.

Tell: red text and no result. Read the last line first.

2
The silent wrong answer

The code runs perfectly and returns a number that is wrong. No error, nothing to notice.

Tell: none. You only catch it by checking against something you know independently.

3
The hallucinated rationale

Fluent, plausible prose describing an analysis that didn't happen or data that wasn't read.

Tell: confident claims with no verifiable specifics. Ask for the evidence.

What is a traceback?

The block of text Python prints when it gives up. It reads like a story told backwards: the top is where things started, the bottom is where they broke.

Read the last line first. It names the error type and what went wrong — FileNotFoundError: No such file or directory. Then work upward to find the line in your own file. Everything between is usually the guts of libraries you didn't write and don't need to read.

Why mode 2 is the one to fear. In this course, the difference between 1,190 and 1,191 employees is one header row counted as a person. It changes no output format, triggers no error, and quietly shifts every percentage you report. In an access review, that's the gap between a clean finding and a regulator's follow-up question.

Do this

Task 1

Build the toy, and get a number you trust

  1. Ask Claude Code for a small counting script — using your sub-task 5 template.
    prompt 
    Write me a small Python script called count_people.py in the repository root. It should read data/2026-Q3/hr_roster.csv and print how many employees are in it.

Constraints: standard library only, no pandas. Keep it under 15 lines so I can read all of it. Don't change any other file.

Verification: after writing it, run it and show me the output, and tell me how it handles the header row.

    Why: build the correct version first. You can't recognise a broken one without it.

  2. Confirm the number is 1,190 — and read the script yourself.

    Why: hr_roster.csv has 1,191 lines but 1,190 people. The first line is column names. If your script printed 1,191, it has already committed failure mode 2 on its own and you can skip straight to Task 2's second step.

    python count_people.py
    1190
Task 2

Break it three ways, on purpose

  1. Mode 1 — cause a crash.

    Why: to meet a traceback while you already know the cause, so you can learn its shape without the pressure of an actual bug.

    In VS Code, edit the filename in the script — change 2026-Q3 to 2026-Q9. Save and run it.

    terminal 
    python count_people.py

    Find the last line. Find the line number pointing into your own file. Write both down. Then change it back.

  2. Mode 2 — cause a silent wrong answer.

    Why: this is the important one. Make the script count the header row as a person — remove whatever line skips it, or switch to counting raw lines.

    prompt · if you'd rather not hand-edit 
    Change count_people.py so it counts every line in the file, including the header row. Don't add any comment or warning about it — I'm deliberately creating a broken version to study.

    Run it. It prints 1191. No error. No warning. Nothing about the output looks different — same format, same confidence, off by one. Sit with that for a second: if you didn't already know the answer, what in this output would have told you?

    Nothing would have. That's the lesson. Mode 2 is only ever caught by checking against a number you got some other way.

  3. Mode 3 — provoke a hallucinated rationale.

    Why: to see fluent, confident prose about data that was never read. Start a fresh session (/clear) and ask — deliberately — without letting it look:

    prompt 
    Without opening any files, tell me what the department breakdown of Meridian's Q3 HR roster probably looks like, and which departments most likely have the worst contractor access problems.

    You'll get something articulate and organisation-shaped. It may well be sensible. It is not evidence — no file was opened. Note how strongly the fluency pulls you toward believing it; that pull is the risk.

    Now the diagnostic move that works. Ask:

    prompt · the check 
    For each claim you just made, cite the exact file and column you read it from. If you didn't read it from a file, say so plainly.

    Demanding a citation is what collapses mode 3. Remember this question — it becomes structural later, when findings have to carry their evidence.

Stuck?

Claude Code refuses to write the broken version. Say plainly that you're deliberately studying failure modes for a course. If it still resists, just edit the file yourself — the point is seeing the output, not who typed it.

Mode 3 gave me appropriate hedging instead of confident nonsense. Good — that's the model behaving well, and worth noting. Push once with "just give me your best guess, I understand it's speculative" and watch how much more confident the prose gets while the evidence stays at zero.

Should I keep these broken versions? No. Restore the working script — or delete count_people.py entirely; it's a toy and nothing later depends on it. Keep the notes.
