Make every write leave an audit trail

Depends on: Sub-task 26 — you need hooks wired and firing Time: ≈ 45 min Type: hooks · audit
First appearance
PostToolUse audit log append-only

The other half of the lifecycle. It can't stop anything, which is exactly why it's honest.

Your pipeline produced nine findings for 2026-Q3. Which component wrote them, when, to which paths, and in which session?

You don't know. You can infer it from the architecture — only findings-writer has Write, so it must have been that one — but inference is not a record, and an auditor asking "how do you know nothing else touched this file" deserves better than an argument from design.

PostToolUse is the honest place for that record, precisely because it can't do anything else.

What you'll understand and do

  • Explain why PostToolUse cannot prevent and what it can do instead
  • Wire audit_write.py and produce a JSONL trail
  • Read the log and reconstruct what a run actually did
  • Notice the quarter environment variable, before Theme I does

Concept

The one idea

A hook that runs after the fact should record, not pretend to protect.

PostToolUse fires once the tool has already completed. The file exists. The bytes are on disk. Whatever the write was going to do, it did.

What PostToolUse can and cannot do

Cannot: stop the tool call. It's over. There is no mechanism, and any design that assumes otherwise is broken in a way that will only show up when it matters.

Can: observe the completed call, including tool_response, which PreToolUse never sees. And it can return {"decision": "block"} to stop the agent loop from continuing — useful when a completed write reveals a problem worth halting on, though it doesn't undo the write.

Which makes audit its natural job, and a better one than it sounds. An audit trail written pre-execution records attempts — including ones that were denied, failed, or errored. An audit trail written post-execution records what happened. For a compliance artifact, the second is the one you want, and the distinction is exactly the sort of thing an auditor will ask you to be precise about.

Why JSONL, and why append-only

One JSON object per line, appended, never rewritten. Cheap to write during a run, cheap to grep, cheap to stream, and impossible to accidentally truncate by rewriting the file.

Append-only is the property that makes it evidence. A log a process can rewrite is a log that can be made to say anything. A log that only grows is one where the absence of an entry is itself informative.

The shipped hook records four fields: ts, tool, path, session_id. That's a deliberate minimum — enough to answer what changed, when, by which tool, in which run, with no content and therefore no risk of the audit log itself becoming the leak. It's worth noticing that session_id is what lets you separate today's run from last week's in a single file.

Stuck?

The log is empty. Nothing wrote. Either the run produced no writes, or the guard denied them, or the hook isn't wired. Check the guard didn't fire on something innocuous — password: is broad enough to catch a rationale.

There are more lines than I expected. Interesting rather than wrong. Every Write and Edit in the session is logged, including ones you made yourself while editing code. If findings.json appears repeatedly within one run, the writer is doing incremental writes rather than one atomic one, which is worth knowing.

Should the audit log record content? Deliberately not. An audit log containing the findings duplicates the findings and creates a second copy of whatever was sensitive about them. Path, time, tool and session answer the compliance question without becoming a liability.

Can I trust a log written by the thing being audited? Sharp question, and the honest answer is: less than you'd like. The hook runs in the same environment as the agent. In a real engagement the log ships to somewhere the agent can't reach. Worth saying out loud rather than overclaiming.
