The last sub-task in Theme H. Two optimisations with no quality risk — and one that will be zero until you hunt for why.

Every call your pipeline makes resends the same thing: the system prompt, the Skills, the schema, the framing. That prefix is identical across all 166 accounts and you pay full price for it every single time.

Prompt caching charges you once and serves it back at a fraction of the cost. Unlike model tiering, it cannot change the output — the model sees exactly the same tokens either way.

It will also, almost certainly, do nothing the first time you turn it on. The interesting half of this sub-task is finding out why.

What you'll understand and do

  • Explain prefix caching and why one changed byte destroys it
  • Add cache_control and verify with cache_read_input_tokens
  • Hunt down the invalidator when the hit rate is zero
  • Run the full quarter through the Batch API and say why it can't be your debug loop

Concept

The one idea

Caching is a prefix match. One byte anywhere in the prefix and there is no cache.

The cache key is derived from the exact bytes of the request up to your marked breakpoint. Everything after it is uncached. Everything before it must be byte-identical to the previous request, or the whole thing is a miss.

How it works, concretely

Render order is tools, then system, then messages. You put a cache_control marker on the last block of the stable prefix; the request is cached up to that point.

Writing costs more than a normal token — roughly 1.25× for the short TTL. Reading costs about a tenth. So two requests break even and everything after that is nearly free.

There is a minimum cacheable prefix, and it varies by model — on the order of a few hundred to a few thousand tokens. Below it, nothing caches and nothing errors. Your Skills prefix is probably above it; check rather than assume, especially if sub-task 35 moved a component to a cheaper tier with a higher minimum.

The stable/volatile split is the entire design problem. Stable content first, volatile content last. Your system prompt, Skills and schema are stable. The account dossier is volatile. If a timestamp, a run ID, or the account ID has crept into the front of your prompt, everything after it is uncacheable no matter where you put the marker.

The invalidators to hunt for

A timestamp or run ID in the system prompt — the classic. datetime.now() in a prompt builder makes every request unique.

Non-deterministic serialization — json.dumps without sort_keys=True, or anything iterating a set. Same content, different bytes.

A varying tool list — tools render at position zero, so adding, removing or reordering one invalidates everything.

The account ID early in the prompt — the one most likely to be yours. It's the most natural thing in the world to open with "Reviewing account A000012", and it makes every request a unique prefix.

Batching is the other lever, and it's blunter. The Message Batches API takes many requests, processes them asynchronously, and charges roughly half. Most batches complete within an hour; the ceiling is 24. That latency is why it can't be your debug loop — a 45-minute round trip on a change you're not sure about is how iteration dies. It's for the production run, which nobody is waiting on.

Do this

Task 1

Cache, and find out it didn't work

  1. Identify your stable prefix precisely.

    Why: print the full request for two different accounts and diff them. Whatever is identical is your cacheable prefix; whatever differs must come after the marker. Do this before adding any cache_control — the diff tells you where the marker can go, and often reveals the invalidator before you've turned anything on.

  2. Add cache_control at the end of the stable prefix.

    Why: on the last block of the system prompt, if that's where your stable content ends. Not on the dossier — a marker after volatile content caches a prefix that is unique per account, so you pay the write premium 166 times and read nothing back.

    the shape 
    system=[{
    "type": "text",
    "text": stable_prompt_and_skills,
    "cache_control": {"type": "ephemeral"},
}],
messages=[{"role": "user", "content": dossier(account_id)}]
  3. Run several accounts and read the cache fields.

    Why: usage carries cache_creation_input_tokens and cache_read_input_tokens. The first call writes; every subsequent call should read. If cache_read_input_tokens is zero across five accounts, caching is not working and the rest of this task is the point of the sub-task.

  4. Hunt the invalidator.

    Why: if the hit rate is zero, something in the prefix differs between requests. The method is mechanical: dump the exact prefix bytes for two consecutive requests and diff them. Something will differ, and it will be small — a timestamp, a reordered key, an account ID that snuck into the framing.

    terminal 
    diff <(python -c "print(build_prefix('A000012'))") \
     <(python -c "print(build_prefix('A000598'))")

    If they're identical and the hit rate is still zero, check the prefix is above the model's minimum cacheable length. Short prefixes fail silently — no error, just cache_creation_input_tokens: 0.

  5. Measure the hit rate and the saving.

    Why: cache reads as a proportion of total input tokens across the run. On a pipeline where the Skills prefix dominates, this can be a large fraction. Compare the run cost against sub-task 34's baseline.

Stuck?

Still zero after removing the obvious things. Check the tool list is byte-identical between calls — tools render before system, so a tool set that varies per account invalidates everything downstream. Also check nothing rebuilds the Skills content per call in a way that reorders it.

Cost went up. Writes cost more than normal tokens. If your prefix is effectively unique per account you're paying the premium every time and reading nothing back, which is strictly worse than no caching. Fix the prefix or remove the marker.

My subagents each have their own prompts. Then each has its own cacheable prefix, and each caches independently. That's fine — ledger-reader's prefix is stable across accounts, and it's likely your highest call volume, so it's the one worth getting right first.

The cache expires between runs. Expected. The short TTL is minutes. Within a single run over 166 accounts you get the benefit; across runs an hour apart you don't, unless you use the longer TTL — which costs more to write and needs more reads to pay off.

Task 2

Batch the production run

  1. Work out which of your calls can be batched.

    Why: batching needs the request to be knowable up front, which rules out anything inside a tool-use loop — call two depends on call one's result. What batches well is the independent, single-shot work: the judge from sub-task 33 is the cleanest case, and a fixed-dossier adjudication step is another.

    That constraint is worth understanding as a design property rather than a limitation. An architecture with more single-shot calls and fewer loops is cheaper in two ways at once.

  2. Batch one stage and run the full quarter.

    Why: build the request list with a custom_id per item, submit, poll until the batch ends, then collect. Results come back in any order — key them by custom_id, never by position. That is the single most common bug in first batch implementations and it produces findings attached to the wrong accounts, which validates cleanly and is completely wrong.

    the flow 
    batch = client.messages.batches.create(requests=[...])   # custom_id per request
# poll client.messages.batches.retrieve(batch.id) until
# processing_status == "ended"
for result in client.messages.batches.results(batch.id):
    handle(result.custom_id, result.result)              # key by custom_id
  3. Verify the batched output matches.

    Why: batching changes cost and latency, not behaviour. Score against the micro-key and run the coverage checks. If anything differs, suspect the ordering bug first — mismatched results produce plausible findings on the wrong accounts.

  4. Record the final numbers against the sub-task 34 baseline.

Stuck?

The batch is still processing after an hour. Within spec — the ceiling is 24 hours. Poll rather than block, and treat this as the concrete demonstration of why batching is a production lever rather than a development one.

Some batch requests errored. Each result carries its own status. Handle errored, expired and canceled separately from succeeded — a partial batch that you treat as complete gives you a silently short findings file, which your sub-task 29 coverage check should catch.

Can I batch and cache together? Yes — a shared cached prefix across a batch is a natural fit, and the two savings compound. Worth trying once both work separately.

My findings changed after batching. Almost certainly the ordering bug. Check you're keying by custom_id. If they still differ, it's ordinary run-to-run variation — compare against your sub-task 30 baseline before concluding batching caused it.

You're done when
  • A cache_control marker at a genuine prefix boundary, and cache_read_input_tokens above zero
  • The invalidator found by diffing prefix bytes — or the prefix confirmed above the model's minimum
  • At least one stage run through the Batch API, with results keyed by custom_id
  • A before/after cost table across three configurations
  • All five effectiveness evals green on the optimised pipeline

Theme H is complete. Seven evaluations built, a cost figure you can defend, and two optimisations that moved it without moving the answers.
