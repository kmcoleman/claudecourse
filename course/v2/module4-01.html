Put your findings in front of a human

Depends on: Sub-task 39 — you need a course-complete system and a real findings.json Time: ≈ 45 min Type: elective — not a building block
First appearance
static page fetch same-origin textContent vs innerHTML

The first four sub-tasks of the course's only elective. Nothing here is a building block — the system was finished at sub-task 39. This is about what the client receives.

Your system produces a JSON array. That is exactly right as an interface between programs, and exactly wrong as a thing to hand a compliance manager who has forty minutes and no terminal.

Everything in this module sits outside the frozen contract. run_review keeps its signature, keeps emitting schema-valid findings, and never learns that a UI exists. What you build here reads its output and nothing more.

Why this is optional. The six building blocks are the course. A reviewer UI is not a seventh block — it's the thin, boring layer between a correct system and a client who can act on it. It's optional because plenty of engagements deliver a CSV and stop there.

It's here because the ones that don't are usually the ones that get renewed.

What you'll understand and do

  • Render findings.json as a table a non-technical reviewer can read
  • Understand why a browser refuses to read your file over file://
  • Handle the two finding shapes the schema allows — account-scoped and application-scoped
  • Render model-authored text without opening an injection hole

Concept

The one idea

The deliverable is not the artifact your program emits. It's the one your client can act on.

A finding in findings.json carries twelve fields. A reviewer working through a quarter needs about six of them at a glance and the rest on demand. Choosing which six is a judgment call about your client's job, not a formatting problem — and getting it wrong is how a technically correct review becomes one nobody finishes reading.

What a static page is, and why it's enough

One HTML file, no build step, no framework, no npm install. The browser parses it, runs the script inside it, and that's the whole stack.

For a review artifact this is a feature rather than a compromise. It opens on a machine that has never heard of your project, it still opens in three years, and there is no dependency tree for a security team to audit before your client is allowed to look at their own results.

Why fetch fails when you double-click the file

Open reviewer/index.html straight from Finder and its address is file:///Users/…. Browsers treat every file:// document as its own opaque origin, so a fetch for ../findings.json is a cross-origin request and gets blocked. The console says CORS; the cause is that there is no origin to be same as.

The fix is the one the course portal already tells you about: serve the directory. python -m http.server 8000 from the repo root gives every file one origin, and the fetch succeeds.

Two finding shapes, one table. Your schema allows scope: "account" — a specific person holding a specific entitlement — and scope: "application", where account_id, employee_id and entitlement are all null by construction. A coverage gap is a fact about an application, not about anyone in particular. A renderer that assumes every row has an account prints null across a column and quietly teaches your reviewer to distrust the table.

textContent, never innerHTML

The rationale field is model-authored prose derived from client data. Client data is exactly the surface sub-task 28 had you defend: text that arrives from somewhere else and would very much like to be interpreted.

el.innerHTML = f.rationale parses that prose as markup. el.textContent = f.rationale displays it. There is no case in this module where the first is the right call, and the habit is worth more than the specific bug it prevents.

Task 1

Serve the repo and load the file

  1. Produce a fresh findings.json and look at its shape.

    Why: build the UI against the real thing. Nine findings for Q3, and you want to see at least one null account_id before you write the renderer rather than after.

    terminal 
    python -m meridian_capstone.contract.run_review data/2026-Q3 > findings.json
python -c "import json;d=json.load(open('findings.json'));print(len(d));print(sorted({f['scope'] for f in d}))"
  2. Make a reviewer/ directory with an empty index.html, and serve the repo root.

    Why: serving from the root rather than from reviewer/ is what puts the page and findings.json on the same origin. Serve the subdirectory and you're back to a cross-origin fetch for a file one level up.

    terminal 
    mkdir -p reviewer
python -m http.server 8000          # from the repo root
# then open http://localhost:8000/reviewer/
  3. Add reviewer/ to .gitignore, or don't — decide deliberately.

    Why: this is a deliverable, so it probably belongs in the repo. findings.json is a run output and probably doesn't. Whatever you choose, choose it now, because "the reviewer UI works but only on my laptop" is a discovery best made before a client call.

Task 2

Render the table

  1. Fetch the findings and fail loudly if you can't.

    Why: fetch only rejects on network failure — a 404 resolves happily with ok: false, and calling .json() on it throws something unhelpful about unexpected tokens. Check r.ok and put the real reason on the page, where the person who needs it will see it.

    reviewer/index.html — script 
    fetch("../findings.json")
  .then(function (r) {
    if (!r.ok) throw new Error("HTTP " + r.status + " for findings.json");
    return r.json();
  })
  .then(render)
  .catch(function (e) {
    document.getElementById("status").textContent =
      "Could not load findings.json — " + e.message;
  });
  2. Build one row per finding, most severe first.

    Why: seven columns, every cell set with textContent, and null rendered as an em dash rather than the word "null". Severity is an enum, not a sortable string — "critical" < "high" is alphabetically false and exactly backwards, so rank it explicitly.

    reviewer/index.html — script 
    var RANK = { critical: 0, high: 1, medium: 2, low: 3 };

function render(findings) {
  findings.sort(function (a, b) { return RANK[a.severity] - RANK[b.severity]; });

  var body = document.querySelector("#findings tbody");
  findings.forEach(function (f) {
    var tr = document.createElement("tr");
    [
      f.account_id || "—",                          // null on application-scoped rows
      f.app,
      f.entitlement || "—",
      f.category,
      f.severity,
      f.recommendation,
      (f.policy_citations || []).join(", ") || "—"
    ].forEach(function (value) {
      var td = document.createElement("td");
      td.textContent = value;                       // never innerHTML
      tr.appendChild(td);
    });
    body.appendChild(tr);
  });

  document.getElementById("status").textContent =
    findings.length + " findings · 2026-Q3";
}
  3. Put the rationale and evidence behind a disclosure, not in a column.

    Why: rationale is a paragraph and evidence is a list of source/detail pairs. Both are what a reviewer reads to decide, and neither survives being a table cell. A <details> in a full-width row underneath each finding costs you four lines and keeps the table scannable.

    reviewer/index.html — script 
    function detailRow(f, columns) {
  var tr = document.createElement("tr");
  var td = document.createElement("td");
  td.colSpan = columns;

  var d = document.createElement("details");
  var s = document.createElement("summary");
  s.textContent = "Why — confidence " + f.confidence;
  d.appendChild(s);

  var p = document.createElement("p");
  p.textContent = f.rationale;
  d.appendChild(p);

  var ul = document.createElement("ul");
  (f.evidence || []).forEach(function (e) {
    var li = document.createElement("li");
    li.textContent = e.source + " — " + e.detail;
    ul.appendChild(li);
  });
  d.appendChild(ul);

  td.appendChild(d);
  tr.appendChild(td);
  return tr;
}
  4. Style it badly on purpose, then stop.

    Why: a bordered table, a readable font, severity in colour, and nothing else. The next two sub-tasks add behaviour, and behaviour is where the remaining time should go. A reviewer UI that looks polished and can't record a decision is worse than an ugly one that can.

  5. Show it to someone who hasn't taken this course.

    Why: you know what sod_conflict means and what ACC-4.2 refers to. Your client does not. Watch where they hesitate — that hesitation is the copy you have to write, and it's cheaper to find now than in a readout.

Stuck?

The console says CORS and I'm confused, because it's my own file. That's the file:// opaque-origin rule. You're not double-clicking the HTML file — you're opening http://localhost:8000/reviewer/ with python -m http.server 8000 running from the repo root. Check the address bar; it's almost always still showing a path starting with file:///.

404 on ../findings.json. The server is rooted where you started it. Started in reviewer/, the parent directory is outside the served tree and can't be reached at all. Restart it from the repo root.

A column is full of null. Application-scoped findings have no account, employee or entitlement — that's the schema, not a bug in your pipeline. f.account_id || "—" handles it.

Sorting puts critical last. You're comparing the strings. Map the enum to a rank first; there is no ordering in the JSON to lean on.

The page is blank and the console is clean. Your script ran before the table existed. Put the <script> at the end of <body> — the same reason every page in this course does.

You're done when
  • A single reviewer/index.html with no dependencies renders every finding in findings.json
  • Rows are sorted by severity and both scopes render without stray null
  • Rationale and evidence are reachable per finding without leaving the page
  • A bad path produces a readable error rather than a blank screen
  • Every cell is set with textContent

Your findings are visible. Nobody can do anything with them yet — that's next.
