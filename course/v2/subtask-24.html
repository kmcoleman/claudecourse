Stand up the orchestrator and give exactly one agent the pen

Depends on: Sub-task 23 — you need a working restricted subagent Time: ≈ 90 min Type: subagents · orchestrator-workers
First appearance
orchestrator fan-out single writer

Three agent files, one of which holds Write. That asymmetry is the safety property.

You have one specialist. Two more complete the pipeline: something that applies policy to the facts, and something that writes the result.

The interesting decision is not how to split the work — gather, judge, record is fairly obvious once you see it. It is what happens to the tool lists when you do. Two of the three components need no ability to change anything at all, and the third needs it for exactly one file.

That is not a rule you enforce by discipline. It's a property of how the files are written, and it stays true whether or not anyone is watching.

What you'll understand and do

  • Explain the orchestrator-workers pattern and why it fits this problem
  • Author policy-applier (read-only) and findings-writer (the only writer)
  • Orchestrate all three end to end on a handful of accounts
  • Write the decomposition rationale you'd defend in a design review

Concept

The one idea

If only one component can write, only one component can corrupt the output.

Orchestrator-workers is a plain pattern: a coordinator decomposes the task, delegates pieces to specialists, and assembles what comes back. The coordinator holds the plan; the workers hold the context for their own piece and nothing else.

The three roles

ledger-reader — MCP lookups plus Read. Answers "what is true about this account?" Read-only. Built in sub-task 23.

policy-applier — Read, so it can load the Skills. Answers "given these facts, what does policy say?" Read-only.

findings-writer — Write and Edit. Turns adjudications into schema-valid records on disk. The only component in the system that can change anything.

Single-writer is a structural property, not a convention. The distinction matters because conventions decay. A convention says "we agreed the reader shouldn't write"; it holds until someone adds a tool for a good reason on a Tuesday. A structural property says the reader has no write capability, and if you want to break it you have to edit a frontmatter line and commit it, where a reviewer sees it.

Three concrete things you get from it. Auditability: exactly one component's actions need logging to reconstruct what changed — which is what makes sub-task 27's audit trail a small file rather than a firehose. Attribution: a malformed findings.json came from findings-writer, full stop; you don't investigate three components. Injection containment: sub-task 28 puts hostile text into a ticket description, and the component that reads it is the one that cannot write.

Fan-out, and why not yet

Each account is independent. Nothing about A000012's adjudication depends on A001185's, which means they can run concurrently — a fan-out. The orchestrator dispatches many, collects results, writes once.

Get it correct on a handful first. Concurrency turns a deterministic bug into an intermittent one, and debugging an intermittent bug across three agents is a bad way to spend an afternoon. Sub-task 25 scales it.

Do this

Task 1

The two remaining specialists

  1. Author .claude/agents/policy-applier.md, read-only.

    Why: it takes an account picture and returns an adjudication — finding, exemption, or nothing — with the clause cited. It needs Read so the Skills load. It does not need MCP: ledger-reader already gathered the facts, and letting this one go back to the source blurs the split you just made.

    Its body should say which policies apply here, that citations must be real, and — this is the one people forget — that "exempt" and "no finding" are results it must return explicitly. Silence is not an output. That was sub-task 17's lesson, and it belongs in this file.

  2. Author .claude/agents/findings-writer.md — the only writer.

    Why: it takes adjudications and produces findings.json and exemptions.json. It needs Write, plausibly Edit, and Read so it can validate against the schema. It needs nothing else, and it must not have MCP — a writer that can also go and look things up is a writer that can decide things, and then you have two components forming judgments.

    Its body should state the contract: twelve required fields, additionalProperties false, exemptions to the sidecar file, and validation before writing. Say the paths explicitly. It cannot enforce them — that's sub-task 26 — but stating them is what makes a violation detectable.

  3. Verify the tool lists across all three.

    Why: read the three frontmatter blocks side by side and check the asymmetry is real. Exactly one Write in the whole set. No Bash anywhere — Bash in any of them silently grants all three the ability to write. And no tools: field missing, because a missing field inherits everything.

    terminal 
    grep -A1 "^tools:" .claude/agents/*.md
grep -l "Bash" .claude/agents/*.md      # should print nothing
Stuck?

Shouldn't policy-applier get MCP so it can check something? Tempting, and it's the decision most people revisit. If it needs a fact it didn't get, the right fix is usually that ledger-reader should have gathered it — which is a fixable, testable problem. Granting MCP here trades a clean boundary for a convenience, and you'll want the boundary back in sub-task 28.

Why three and not two? Because gathering and judging fail differently. A gathering failure is a missing fact; a judgment failure is a wrong conclusion from complete facts. Splitting them means a bad finding tells you which half to look at. Two components would work; three make failures attributable.

Can the orchestrator write directly? It could, and it would collapse the property you just built. If the orchestrator holds Write then the number of components that can corrupt the output is two, and the audit story gets more complicated for no gain.

Task 2

Orchestrate

  1. Wire the three together and run five accounts end to end.

    Why: the orchestrator's job is to take the candidate set, delegate each account through gather → adjudicate, collect the results, and hand the batch to the writer once. Start with five accounts you know the answer to — A000012, A000384, A001115, A000387 and A001185 give you a dormant admin, two SoD cases, an exempt Controller and a contractor overstay.

  2. Check the handoffs, not just the output.

    Why: the output being right doesn't mean the decomposition is working. Confirm that ledger-reader returned facts and no verdict, that policy-applier reasoned from those facts rather than going back to the source, and that findings-writer wrote what it was handed rather than re-deciding anything. A writer that improves a rationale on the way past is a fourth judgment step you didn't design.

  3. Wire it into run_review() without touching the signature.

    Why: the contract has been frozen since sub-task 12 and this is the moment it earns its keep. The function still takes export_dir and limit and still returns a list of dicts. What changed underneath is the entire architecture, and the grader neither knows nor cares.

    Make limit real now if it isn't — it caps how many candidates reach the agent layer, and sub-task 25 depends on it working.

Stuck?

The orchestrator does the work itself instead of delegating. Usually the descriptions. If they don't clearly signal what each specialist is for, the orchestrator concludes it's faster to do it directly — which it often is, for one account. Make the descriptions concrete about the input and output of each.

The findings are worse than the single agent's. Look at the handoff. The most common cause is ledger-reader summarising instead of reporting, so policy-applier adjudicates from a lossy digest. Have the reader return the facts, not its impression of them.

Where does the orchestrator live? Your call. A Claude Code session delegating via the agent files, or code that drives them explicitly. Code gives you deterministic control flow and easier cost accounting, and sub-task 25 is easier if you have it.

You're done when
  • Three agent files, and grep confirms exactly one holds Write
  • No Bash anywhere, and no agent silently inheriting the full tool set
  • Five known accounts adjudicated correctly end to end — 4 findings, 1 exemption
  • run_review() driving the pipeline with its signature untouched, and limit actually capping
  • A decomposition rationale that states the cost as well as the benefit

The architecture is complete. What remains is to run it at full scale and find out what that costs.
