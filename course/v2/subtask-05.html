Turn a vague ask into an intent that produces the right code

Depends on: Sub-task 4 — you need Claude Code running Time: ≈ 60 min Type: experiment + comparison
First appearance
intent-based development verification-in-the-prompt

The prompt shape you settle on here is the one you'll reuse for the rest of the course. It is worth an hour.

You have Claude Code running and you've asked it one question. Now the real skill: how you ask determines what you get, and the difference is far larger than most people expect.

You're going to run the same small task three ways — vague, step-by-step, and intent-with-verification — and compare the results side by side. The point isn't that one is obviously better. It's that they fail differently, and knowing how lets you pick deliberately.

What you'll understand and do

  • Describe the three prompt shapes and the characteristic failure of each
  • Write a prompt that states the outcome, the constraints, and how you'll check the result
  • Keep a reusable prompt template of your own, in your own words

Concept

The one idea

Say what "right" looks like, and you get a system that can check itself.

Most people's instinct with a capable assistant is one of two extremes. Either they under-specify — "clean up this data" — and get something plausible aimed at a target nobody named. Or they over-specify, dictating each step, which turns a system that could exercise judgment into a slow way of typing.

Intent-based development is the third shape, and it has three parts:

1
The outcome

What must be true when this is done — stated as a result, not a procedure.

2
The constraints

What it must not do, must not change, or must not assume. Usually learned the hard way, which is why they accumulate.

3
The verification

How you'll know it worked — stated in the prompt, so the work and the check arrive together.

The third part is the one people leave out, and it's the one that does the work.

Why verification-in-the-prompt changes the outcome

A prompt that ends "…and show me the row count so I can confirm it" does something a bare instruction can't: it forces the answer into a form you can falsify. Vague prose can't be wrong. A number can.

This matters more with an agentic system than with a person, because an agentic system won't tell you when it's unsure — it'll produce something confident and well-formatted either way. Naming the check up front is how you get a handle on the result.

What you'll be asking for. A deliberately small task against Meridian's HR file: count the contractors. Small enough that all three prompts "work" — which is exactly what makes the comparison interesting.

The answer, so you can grade the results

data/2026-Q3/hr_roster.csv holds 1,190 employee rows (1,191 lines including the header — remember that gap, it matters in sub-task 6). Of those, 117 are Contractor and 1,073 are FTE. By status: 1,176 active, 10 terminated, 4 on leave.

Don't put these numbers in your prompts. They're how you mark the answers.

Do this

Task 1

Run the same task three ways

  1. Start Claude Code in the project folder.

    Why: run each prompt in a fresh session — type /clear between them. Otherwise prompt two inherits everything prompt one worked out, and you'll be comparing nothing.

  2. Prompt A — vague.
    prompt a · vague 
    Look at the HR data and tell me about the contractors.

    Note what it decided you meant. It has to guess at the file, at what "about" means, and at what a contractor is. It will guess capably — that's what makes this shape dangerous rather than useless.

  3. Prompt B — step-by-step. (/clear first.)
    prompt b · step-by-step 
    Open data/2026-Q3/hr_roster.csv. Read the employment_type column. Count how many rows have the value Contractor. Print the number.

    You'll likely get the right number. Now ask yourself the expensive question: how much did I have to already know to write that prompt? You had to know the path, the column name, and the exact spelling of the value. That knowledge doesn't transfer — next quarter's file, next question, you're back to square one.

  4. Prompt C — intent with verification. (/clear first.)
    prompt c · intent + verification 
    I need to know how many contractors are in Meridian's Q3 HR roster, so I can size the contractor-access problem.

Constraints: use the files under data/2026-Q3/ — don't paste the file contents into your reply. Don't modify any file.

Verification: tell me the total row count as well as the contractor count, name the exact column and value you counted, and say how you handled the header row. If the data is ambiguous, say so rather than picking for me.

    Same task. But now the answer arrives with its own audit trail — you can check the column, the total, and the header handling without opening anything. You didn't need to know the schema in advance, and the reply tells you enough to trust or reject it.

Stuck?

All three gave me 117. So what was the point? That's the common outcome, and it is the point. Ask instead: which reply could you hand to an auditor? Which could you rerun on next quarter's data without rewriting? Which would have told you if it had been wrong? On a small task the shapes converge — that's why learning the difference here is cheap.
