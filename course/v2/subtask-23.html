Build one specialist that can't write anything

Depends on: Sub-task 22 — you need the MCP tools and your blast-radius table Time: ≈ 75 min Type: building block #4
First appearance
Subagents context isolation tool restriction tools:

Building block four of six. The deliverable is a refusal — on purpose.

One agent has been doing everything: gathering facts, reading policy, forming a verdict, producing structured output. It works on one account. It will not survive 166.

The reason is context. Every fact gathered, every tool result, every policy quotation accumulates in one conversation, and by account forty the model is reasoning about a contractor's SOW while carrying thirty-nine previous accounts' worth of irrelevant Vault grants. Quality degrades, cost climbs, and the failures are hard to attribute.

Subagents fix that, and they bring a second property that is arguably more valuable: each one gets its own tool list.

What you'll understand and do

  • Explain what a subagent is and where it lives on disk
  • Author ledger-reader with MCP and Read and nothing else
  • Prove it refuses to write — and understand exactly what enforced that
  • Say what tool restriction does and does not protect you from

Concept

The one idea

A subagent is a specialist with its own context and its own tool list.

A subagent is a Markdown file. Frontmatter declares its name, a description that governs when it gets delegated to, and optionally a restricted tool list. Everything after the frontmatter is its system prompt.

What is a subagent?

.claude/agents/ledger-reader.md

Context isolation. It runs in its own conversation. What it reads doesn't accumulate in the parent's context; what comes back is its result, not its transcript. That is what makes 166 accounts tractable.

Tool restriction. A tools: field lists what it may use. Omitting the field inherits everything — every built-in tool and every MCP server you have configured. Restriction is opt-in, so the default is an agent with your full blast radius.

Description drives delegation. Same as Skills: that line is what the orchestrator reads when deciding whether this specialist is the right one. Write it in the third person and say when to use it.

The watcher quirk, one last time. Creating the top-level .claude/agents/ directory mid-session means the first agent file isn't discovered until you restart. You have now hit this with Skills and MCP config; create the directory before you need it.

Why ledger-reader first. It is the component with the clearest possible answer to "what does it need?" Its job is to answer questions about one account by consulting Meridian's systems. It needs the MCP lookups. It needs Read for your own reconciled artifacts. It needs nothing else, and every extra tool is pure added blast radius on a component whose entire purpose is observation.

What tool restriction actually enforces

It is a real, harness-level constraint, not an instruction the model is asked to respect. The tool simply isn't in the list the model sees, so there is nothing to call. The model can want to write; there is no mechanism by which it can.

Which makes it worth being exact about the limit. Restriction controls which capabilities, never which arguments. An agent with Write can write anywhere. That gap is what building block five closes, and you found it yourself in sub-task 20.

Do this

Task 1

Author the specialist

  1. Create .claude/agents/ and restart before writing anything into it.

    Why: the watcher. Do it first and the rest of this sub-task is uneventful.

  2. Write ledger-reader.md with frontmatter and a restricted tool list.

    Why: the tools: line is the point of the exercise. List the seven meridian-systems tools and Read. Nothing else — no Write, no Edit, and specifically no Bash, which would silently restore every capability you just removed.

    shape — write your own description and body 
    ---
name: ledger-reader
description: <what it gathers, and when the orchestrator should use it>
tools: Read, mcp__meridian-systems__get_account, …
---

<system prompt: what a complete account picture contains,
 and that it reports facts rather than verdicts>

    Check the exact MCP tool names against what your session reports — the naming convention is stable but the server name is yours. A typo here doesn't error; it silently removes the tool.

  3. Write the body so it gathers facts and stops.

    Why: the division of labour only holds if each specialist stays in its lane. This one assembles the picture — grants, person, tickets, prior review, application metadata — and reports it. It does not decide whether anything is a finding; that's policy-applier's job in sub-task 24, and it has the Skills for it.

    Two things worth putting in the body. State the facts a complete picture contains, so the output is consistent enough for the next stage to rely on. And tell it to report absence explicitly — "no approving ticket" rather than silence — because a missing fact and an absent fact read very differently downstream, and "no ticket" is half of the Privileged Access Standard's test.

  4. Delegate a real account to it and check the output.

    Why: run it on A000012 and compare against the seven responses you collected by hand in sub-task 21. It should find the same things — 13 grants including Vault/Admin, no tickets, five prior reviews none of which is Vault, Vault as crown-tier with Admin privileged, and gabriel.villa not a registered service account.

Stuck?

The agent isn't discovered. Restart. Then check the file is directly in .claude/agents/ with a .md extension and valid frontmatter — a malformed YAML block makes the file unparseable and it's skipped.

It says it doesn't have a tool it needs. Name mismatch in tools:. Have your session list the exact MCP tool names and copy them.

It returned a verdict instead of facts. The body isn't scoped tightly enough, or the description implies judgment. Both are worth fixing — the orchestrator routes on the description, so a description that sounds like "reviews accounts" will get it the wrong work.

Task 2

Get it to refuse — the actual deliverable

  1. Ask ledger-reader to write its findings to a file.

    Why: an entirely reasonable-sounding request. "Look up A000012 and save what you find to account.json." Nothing about it signals danger, which is the point — you're testing whether the boundary holds against ordinary requests, not adversarial ones.

  2. Capture what happens, exactly.

    Why: expect it to report that it lacks the capability, or to do the lookup and hand the content back for someone else to write. What you must not see is a file appearing. Check the filesystem — don't take its word for it.

    terminal 
    ls -la account.json    # should not exist
git status --short     # nothing new
  3. Be precise about what stopped it.

    Why: this distinction is the whole lesson and it is the one people get wrong. It did not decline. It was not persuaded by its system prompt. There was no Write tool in the list it was given, so there was no call it could emit. The constraint is structural.

    Test the distinction directly: take a copy of the agent, delete the tools: line entirely, and ask again. It inherits everything, including Write, and the file appears. Same prompt, same body, same model. The only difference is one line of frontmatter. Delete the copy afterwards.

  4. Write down what this does and doesn't protect you from.

    Why: overclaiming here is how people build systems that feel safe. Tool restriction is genuinely strong against the failure it addresses and completely blind to the one it doesn't.

    What tool restriction bought me

    Sub-task 26 builds the layer that covers the gap, and sub-task 28 attacks both. Be honest here.

    Saved in this browser
  5. Commit.

    .claude/agents/ is source. Commit the agent, not the unrestricted copy.

Stuck?

It wrote the file anyway. Then the restriction isn't in force. Check the tools: line parses as YAML, that you restarted, and above all that Bash isn't in the list — Bash can write files, so granting it while withholding Write restricts nothing.

It refused but I can't tell why. Ask it to list the tools it has. If Write is absent, the restriction is real. If it's present and it declined anyway, you're relying on the model's judgment rather than on the harness — which works until it doesn't.

Isn't this over-engineering for a review that only reads data? The opposite — a system that only reads is exactly where a read-only guarantee is cheap to make and easy to state. The value shows up in the sentence you can say to a client: this component cannot modify anything, structurally, and here is the file that says so.
