Emit a schema-valid finding, then break the schema on purpose

The last sub-task in Theme B. At the end of it, test_ledger.py goes fully green.

Everything you've built so far lives in your own head and your own column names. This sub-task attaches it to something that doesn't care about either: a schema someone else wrote, which will be validated by a grader you will never meet.

You'll produce the first real finding — a genuine separation-of-duties conflict, derived entirely from code — validate it against the contract, and then deliberately break it two different ways so you know what failure looks like before it happens to you at a bad moment.

What you'll understand and do

  • Read a JSON Schema and say what it will and won't accept
  • Derive a real SoD finding deterministically, exemptions included
  • Break validation on purpose, twice, and recognize both error messages

Concept

The one idea

A schema is a promise to someone who isn't in the room.

Until now every artifact you've made was for you. ledger.csv can have any columns you like; the tests are deliberately lenient about names. findings.json is different. It's read by run_review(), which is imported and called by a grader that has never seen your code and will not adapt to it.

The frozen contract

src/meridian_capstone/contract/run_review.py exposes exactly one function:

run_review(export_dir: Path, limit: int | None = None) -> list[dict]

The signature does not change. Ever. Your CLAUDE.md from sub-task 7 already says so, which is a rule that is about to earn its place.

limit caps how many candidates reach the agent layer. With limit=5 you can iterate in seconds instead of minutes; grading calls it with None. It exists purely so that developing this system is affordable — which is context economics again, aimed at your own time this time.

The findings schema is strict in the two ways that matter. Twelve fields are required on every finding. And additionalProperties is false — a field the schema doesn't know about is an error, not a bonus. You cannot bolt on a finding_id or a notes field because it seemed useful.

Read that as a constraint on your design rather than an annoyance. Anything the schema won't hold has to live somewhere else — which is why exemptions go in a separate exemptions.json rather than as a flag on a finding.

Structured output isn't just for compliance

It would be easy to read this sub-task as an audit-paperwork detour. It isn't. Fixing the shape of a model's output is one of the highest-leverage moves available in any agentic system, for reasons that have nothing to do with regulators:

It makes output composable. A structured finding can be sorted, counted, diffed against last quarter, and fed to the next stage. Prose can only be read by a human, once.

It makes output testable. "Did the model produce something valid?" becomes a boolean rather than an opinion. That's the difference between a pipeline you can put in CI and one you have to babysit.

It constrains the model usefully. A required evidence array with at least one entry means a finding without a citation cannot be represented at all. The schema doesn't ask for rigour — it makes the alternative unexpressible.

It forces the ontology early. The category enum has ten values. Deciding those ten is real design work, and a schema makes you do it in week one rather than discovering in week six that you have forty ad-hoc labels meaning six things.

When you take this home: define the output shape before you write the prompt. It will change the prompt, and it will change it for the better.

    Why: it's under 60 lines and it's the specification for every finding you will produce for the rest of the course. Reading it now is cheaper than discovering it through error messages later.

  2. Answer these five without re-opening the file.

    Why: if you can't, you didn't read it — you skimmed it.

    check yourself

3. What are the three legal values of `recommendation`?

  3. Apply the exemption — and record what you suppressed.

    Why: the same sod_matrix.json carries an exemptions entry: clause ACP-4.2 permits this pair for a Controller in Finance & Accounting, on the basis of a compensating control — a quarterly manual payment review by the CFO. A000384 is a Ranger/warden in Field Services who was terminated on 2026-07-07 and still holds both roles in the finance system. The exemption is nowhere near them.

    Why: category is sod_conflict, severity is critical because the matrix says so, and evidence must cite where each part came from — the ledger rows for the role pair, the matrix entry for the rule. Cite the file, not your memory of it.

Stuck?

I found more or fewer than 5 holders. Check you're grouping within Atlas ERP only, and that you're using the de-duplicated ledger. Both roles must be held by the same account_id, not merely by the same person across two accounts — though that second case is worth a thought for a future quarter.

I exempted the wrong people. The exemption needs both title Controller and department Finance & Accounting. A001115 has the department but not the title. Compare case-insensitively — sub-task 10's normalization is what makes that reliable.

Should terminated A000384 be an SoD finding or a termination finding? Genuinely both, and it's a good question to sit with. The kit expects it under sod_conflict here. In a real report you'd likely raise it once, at the highest severity, and mention the second dimension in the rationale.

Task 3

Validate — then break it twice, deliberately

  1. Validate findings.json against the schema and see it pass.

    Why: jsonschema is already installed — the kit's own tests use it.

    terminal 
    python -c "
import json, jsonschema
schema = json.load(open('src/meridian_capstone/contract/findings.schema.json'))
jsonschema.validate(json.load(open('findings.json')), schema)
print('valid')
"
  2. Break it the first way: delete a required field.

    Why: take a copy, remove policy_citations from one finding, and validate the copy. Read the error carefully — note that it tells you which array index failed and which property is missing. Learning to read this message when you caused it is much easier than learning to read it at 6pm on a deadline.

    expected error 
    jsonschema.exceptions.ValidationError: 'policy_citations' is a required property

Failed validating 'required' in schema['items']:
On instance[0]: {...}
  3. Break it the second way: add a field that isn't in the schema.

    Why: add "finding_id": "F-001" to a finding — exactly the sort of thing that feels harmless and useful. Validate. It fails, because additionalProperties is false.

    expected error 
    jsonschema.exceptions.ValidationError: Additional properties are not allowed
('finding_id' was unexpected)

    This is the more instructive of the two failures. A missing field is obviously your mistake. An extra field feels like an improvement, and the contract rejects it anyway — because a downstream consumer that has to cope with fields it didn't ask for isn't a contract at all. Restore your valid file before moving on.

Stuck?

Removing a field didn't fail. You removed one of the optional ones, or you edited a copy and validated the original. Only the twelve names in required are mandatory.

The error is enormous and unreadable. Normal — it prints the whole failing instance. Read the first line and the On instance[N] line; ignore the rest. Or use jsonschema.Draft202012Validator(schema).iter_errors(data) to get them one at a time, which is what you'd want in a real pipeline.
