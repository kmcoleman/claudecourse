Get a bench you can prove works

Depends on: Sub-task 1 — you need your headache note first Time: ≈ 90 min Type: installation + verification
First appearance
terminal VS Code git commit

The three tools every later sub-task assumes, plus the one habit that makes the rest of the course safe to experiment in.

You can't learn to direct an agentic system by reading about it. You need a bench — a place to run things, see them fail, and try again. This sub-task builds that bench and, more importantly, proves it works rather than assuming it does.

Three tools, in order: a terminal to type commands into, VS Code to read and edit files in, and git to record snapshots of your work. The first two are obvious. The third is the one that changes how boldly you can experiment for the rest of the course.

What you'll understand and do

  • Open a terminal and run a command that tells you whether a tool is installed
  • Explain what git is actually for — and why a commit is a safety net rather than paperwork
  • Make your own first commit and see it in your own history

Concept

The one idea

A commit is permission to break things.

Most people meet git as bureaucracy — a thing you're made to do before your work counts. That framing is backwards, and it will cost you badly in this course.

Here is the useful framing. Over the next thirty-odd sub-tasks you'll be pointing a capable, occasionally over-eager assistant at your files and telling it to change them. Sometimes it will do something you didn't want. If your last known-good state is saved, that's a shrug and one command. If it isn't, it's your afternoon. Committing often is what makes it safe to be bold — and being bold is how you learn what these systems actually do.

What is a terminal?

A window where you type commands as text instead of clicking buttons. It's called Terminal on a Mac and PowerShell on Windows. Everything you do there could in principle be done with a mouse; the reason we use text is that text can be copied, pasted, shared, and — critically — checked. When something goes wrong in this course, the terminal will tell you exactly what, in a form you can paste to someone else.

The $ or > you see at the start of a line is the prompt — the computer saying it's ready. You never type it. In this course, code blocks show only what you type.

What is VS Code?

A free text editor built for code. You could use any editor, but VS Code is what the course assumes: it shows a file tree down the left, opens a terminal inside the same window, and understands the file types you'll be working with. You'll spend most of the course reading files in it rather than writing them.

What is git — and what is a commit?

git is a system that records snapshots of a folder over time. A commit is one snapshot, with a message saying what changed and why. Together they give you a history you can read, and any point in it you can return to.

Two things git is not: it isn't a backup service (it lives on your machine until you deliberately push it somewhere), and it isn't GitHub (GitHub is one website that hosts git repositories — you don't need an account for anything in this course).

A note on how this course handles git from here. This is the only sub-task that walks through git in full. From here on, sub-tasks will simply say "commit your progress" and expect you to run the add/commit pair you're about to learn. If you ever forget it, come back to this page.

Do this

Task 1

Open a terminal and find out what you already have

  1. Open your terminal.

    Why: before installing anything, find out what's already there. Macs ship with git surprisingly often; Windows machines almost never do.

    macOS: press ⌘ + Space, type Terminal, press Enter.
    Windows: press the Start key, type PowerShell, press Enter.

  2. Ask each tool to state its version.

    Why: --version is the universal "are you there?" question. A version number means installed. An error means not installed — and that error is information, not failure.

    terminal 
    git --version
python3 --version
code --version

    Run them one line at a time. Expect a mix of hits and misses — that's the normal starting point, and the next tasks fill the gaps.

Stuck?

"command not found" / "not recognized as the name of a cmdlet". That's the expected answer for a tool you haven't installed yet. Note it and move on — Task 2 installs it.

macOS pops up a box offering to install developer tools. Accept it. That's Apple's Command Line Tools, and it includes git. It takes a few minutes.

python3 works but python doesn't (or vice versa). Normal, and it differs by platform. Use whichever one answered. On Windows that's usually python; on macOS it's python3.

Task 2

Install whatever was missing

  1. Install git, if git --version failed.

    Why: git is the safety net. Nothing else in the course is optional without it.

    macOS: run the command below and accept the dialog that appears.

    terminal · macos 
    xcode-select --install

    Windows: download and run the installer from git-scm.com/downloads. Accept every default. Close PowerShell and reopen it afterwards, or it won't see the new tool.

  2. Install VS Code, if you don't have it.

    Why: you need somewhere to read files. Download from code.visualstudio.com and accept the defaults.

    macOS users: to make the code command work in your terminal, open VS Code, press ⌘ + Shift + P, type shell command, and choose Install 'code' command in PATH. This is convenient but not required — you can always open VS Code by clicking it.

  3. Tell git who you are.

    Why: every commit is signed with a name and email. git refuses to commit until you've set them. These are labels in your local history — use your work email, and note they'd be visible to anyone you later shared the repository with.

    terminal 
    git config --global user.name "Your Name"
git config --global user.email "you@example.com"
git config --global init.defaultBranch main

    The third line sets the default name for the first branch in new repositories. Without it git prints a long advisory notice every time you start one.

Stuck?

I installed it but the terminal still says "command not found". Close the terminal window completely and open a new one. A terminal reads the list of available programs when it starts and doesn't notice later additions.

The macOS install dialog says the software can't be found on the server. Apple's installer is occasionally flaky. Install git from git-scm.com/downloads instead — the download works the same way as it does on Windows.

Do I need a GitHub account? No. Nothing in this course pushes anything anywhere. git works entirely on your own machine.

Task 3

Make one commit, in a folder you don't care about

  1. Create a throwaway folder and start tracking it.

    Why: practise on something disposable. You'll delete this afterwards; the point is the muscle memory, not the folder.

    terminal 
    mkdir git-practice
cd git-practice
git init

    mkdir makes a folder, cd moves you into it, and git init tells git to start recording this folder's history. You should see something like Initialized empty Git repository.

  2. Create a file, then ask git what it sees.

    Why: git status is the question you'll ask more than any other. It answers "what has changed, and what am I about to record?"

    terminal 
    echo "my first tracked file" > notes.txt
git status

    git reports notes.txt as untracked — it can see the file but isn't recording it yet. That distinction matters enormously in sub-task 4, when you deliberately keep a secret untracked.

  3. Stage it, then commit it.

    Why: this is the two-step you'll repeat for the rest of the course. git add chooses what goes in the snapshot; git commit takes it. Two steps, because you often want to record some changes and not others.

    terminal 
    git add notes.txt
git commit -m "Add my first tracked file"

    The -m flag carries the message. Write messages for the version of you who returns in three weeks with no memory of today.

  4. Read your own history back.
    terminal 
    git log --oneline

    One line, starting with a short string of letters and numbers — the commit's unique ID — followed by your message. That line is the artifact this sub-task exists to produce. Press q if the output takes over your terminal and won't give it back.

Stuck?

"Please tell me who you are." You skipped the git config step in Task 2. Run those two lines, then commit again.

My terminal is stuck in a screen I can't escape. That's a pager showing long output. Press q. If you're in a text editor git opened because you forgot -m, press Esc then type :wq and Enter.

"nothing to commit, working tree clean". git has already recorded everything — you probably ran the commit twice. Harmless. Check git log --oneline.

Where did the folder go? Run pwd (macOS) or Get-Location (Windows) to print where you currently are. Terminals start in your home folder, so git-practice is most likely directly inside it.

You're done when

git log --oneline prints a commit that you made, with a message you wrote. Something like:

a3f9c21 Add my first tracked file

Plus: git --version and python3 --version both answer, and VS Code opens. That's the bench.

You can delete the git-practice folder now — it did its job.
