Theme H opens by naming everything you can measure without an answer key — then builds the cheapest one today.

You have a complete quarterly review. Nine findings, five exemptions, every citation real. You believe it's right because you checked it by hand against numbers this course gave you.

On a real engagement nobody gives you the numbers. The client doesn't know the answer — that's why they hired you. So the question that governs the rest of this theme is: what can you measure when you can't measure accuracy?

The answer is: quite a lot, in seven distinct ways. This sub-task names all seven and builds the one that costs nothing.

What you'll understand and do

  • Name the seven evaluations you can run without an answer key, and the one you can't
  • Separate effectiveness questions from efficiency questions
  • Build a validator that fails loudly on malformed or degenerate output
  • Find at least one way a run can be schema-valid and still worthless

Concept

The one idea

You never see the key. Build the seven things that don't need it.

Meridian's data was generated with a seed, and the generator can emit an answer key classifying every account. Your instructor has it. You don't, and you won't — because a real client cannot hand you one either. That constraint is the whole design of Theme H.

The eighth evaluation, and why it isn't yours

Accuracy against ground truth. Precision, recall, F1 against a known answer key. It is the most informative measurement available and you cannot run it. The instructor can, and will.

Everything below is what remains — and the point of this theme is that what remains is enough to catch most real failures.

Split them by the question they answer. Effectiveness asks whether the output is any good. Efficiency asks what it cost to get. Both go in front of a client, and the second is usually the one that decides whether there's a second phase.

The seven, and where each one gets built

Effectiveness

1. Schema and coverage validation — is the output well-formed, and is its distribution plausible? Free, deterministic, runs in a second. Today.

2. Self-consistency — does the same input produce the same answer twice? Sub-task 30.

3. Hand-labelled micro-key — the only ground truth you're allowed is the ground truth you make. Sub-task 31.

4. Escalation rate — what fraction the system declines to decide, and whether that's calibrated. Sub-task 32.

5. LLM-as-judge on defensibility — are the rationales evidence-grounded and policy-cited? Needs no key at all. Sub-task 33.

Efficiency

6. Cost and latency — per review, per finding, wall clock. Sub-task 34.

7. Configuration deltas — what changes when you change the model tier, or turn on caching and batching. Sub-tasks 35 and 36.

Today's is the cheapest and the most under-appreciated. Schema validation you already have. What you don't have is a coverage check — and the failure it catches is the one that looks most like success.

A run that returns zero findings is schema-valid. So is a run where all nine findings are the same category, or every confidence is exactly 1.0, or every recommendation is revoke. Those are degenerate distributions: technically conforming, obviously broken to a human, and completely invisible to jsonschema.validate.

A gap in your own contract, worth finding today

Open findings.schema.json and look at policy_citations. It's an array of strings with no minimum length. An empty array validates.

So a finding with no citation at all passes your contract, and every argument you've made since sub-task 15 about audit-defensibility rests on something the schema does not enforce. That is exactly the class of thing a coverage check exists to catch.

Task 2

Build the validator

  1. Start with schema validation, and make failure loud.

    Why: you have this from sub-task 12. What you may not have is a runner that exits non-zero and prints every error rather than the first. Use iter_errors rather than validate so one run tells you everything that's wrong.

    terminal 
    python -c "
import json, jsonschema
schema = json.load(open('src/meridian_capstone/contract/findings.schema.json'))
data = json.load(open('findings.json'))
errs = list(jsonschema.Draft202012Validator(schema).iter_errors(data))
for e in errs: print(list(e.absolute_path), e.message)
print(len(errs), 'errors')
"
  2. Add the coverage checks — the ones the schema can't express.

    Why: these are assertions about the distribution, not about any individual record. Each one names a way a run can be technically fine and actually broken.

    the checks worth having 
    not empty            zero findings on 166 candidates is a bug, not a clean bill
citations present    every finding has ≥1 non-blank citation
                     (the schema does NOT require this — check it yourself)
citations real       every citation is one of the 5 clause numbers
                     or 5 document titles from sub-task 16
categories vary      more than one category present
severities vary      not every finding at the same severity
confidence varies    not every finding at exactly 1.0
recommendations vary not everything "revoke"
evidence non-trivial every evidence entry names a real source file
exemptions recorded  suppressions land in exemptions.json, not nowhere
accounts unique      no account flagged twice in the same category

    On your 2026-Q3 run these should all pass: three categories present out of ten in the enum, nine findings spread across them, five exemptions recorded separately. The value isn't today's pass — it's the run in three months where a prompt change quietly collapses everything to one category.

  3. Prove each check works by breaking the file.

    Why: a check you've never seen fail is a check you don't know works. Take a copy of findings.json and, one at a time: empty it, blank a citation, set every severity to high, set every confidence to 1.0. Each should trip exactly one check with a message that tells you which.

    The blanked-citation case is the one to dwell on. It passes jsonschema.validate and fails your coverage check — which is the concrete demonstration that schema validity and usefulness are different properties.

  4. Wire it in so it runs without being remembered.

    Why: an eval you have to remember to run is an eval that runs the day you write it. Make it a test, a make target, or the last thing run_review() does before returning. Cheapest and most reliable is to let it fail your existing pytest run.

  5. Run it against the real quarter and commit.

    Why: it should pass. Note the numbers it reports — findings per category, severity spread, confidence range — because sub-task 30 diffs against them.

Stuck?

How strict should "categories vary" be? Careful here. A quarter legitimately might produce findings in one category only, so a hard requirement for three is wrong. The useful version is a warning rather than a failure, or a check against the previous run's distribution — a sudden collapse from three categories to one is much more suspicious than one category in isolation.

My citation-realness check is brittle. Then make it a set membership test against the ten legitimate identifiers from sub-task 16 rather than a regex. Ten strings, exact match, no ambiguity — and it fails loudly when someone adds a policy without updating the list, which is correct behaviour.

Is this really an eval, or just validation? Fair challenge. It doesn't measure quality; it detects catastrophe. That's still the highest return per minute of any check in this theme, because the failures it catches are total rather than marginal.

You're done when
  • All seven evaluation types named, with what each catches and misses
  • A validator that checks the contract and the distribution
  • Every coverage check observed failing on a deliberately broken file
  • At least one case found that is schema-valid and worthless — the empty policy_citations array is the obvious one
  • The validator running automatically, and passing on 2026-Q3

You can now detect a run that has gone catastrophically wrong. What you cannot detect is a run that has gone slightly wrong — or one that disagrees with the run you did yesterday.
